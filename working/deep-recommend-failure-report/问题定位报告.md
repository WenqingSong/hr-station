# 岗位推荐「生成深度推荐」失败 — 问题定位报告（修正版）

> 生成时间：2026-09-18
> 定位范围：仅后端（Go）代码 + 运行时日志 + 数据库状态 + LLM 连通性验证
> 未修改任何代码，未改动前端。

---

## 〇、修正说明（重要）

第一版报告曾把根因归为「API Key 失效」。经用户提供 TokenHub 实测（同一 token 在 `tokenhub.tencentmaas.com` 调用成功）复核后，**修正结论如下**：

> **Token 是有效的，真正的根因是后端配置的 LLM 端点（base URL）指向了错误的平台。**
> 当前 token 是 **TokenHub**（`tokenhub.tencentmaas.com`）的 token，但后端配置却指向 **LKEAP**（`api.lkeap.cloud.tencent.com`），导致 LKEAP 返回 `401 not authorized`，所有深度推荐 LLM 链路中断，最终返回 500。

---

## 一、结论摘要（TL;DR）

**根因：`/workspace/.env` 中 LLM 端点配置错误——`LLM_PROVIDER=hy3` 且 `LLM_BASE_URL` / `LLM_HY3_BASE_URL` 都指向 LKEAP（`api.lkeap.cloud.tencent.com`），而实际的 token 属于 TokenHub（`tokenhub.tencentmaas.com`）。token 在 LKEAP 上鉴权失败（401），深度推荐的三条 LLM 链路全部失败；叠加 `ENABLE_MOCK_AGENT=false`、`LLM_FALLBACK_ENABLE=false` 的「不兜底」配置，后端返回 500，前端据此显示「暂时生成失败」。**

一句话：**不是 token 失效，也不是业务代码 bug，是「token 平台」和「配置的调用地址」不匹配。**

---

### 4.1 配置层：provider 决定走哪个客户端、哪个 URL

`main.go` 根据 `LLM_PROVIDER` 选择客户端：

URL 解析逻辑（`config.go`）：

```118:128:server/internal/config/config.go

	if provider == "hy3" && c.Hy3BaseURL != "" { return c.Hy3BaseURL }
```

### 4.2 当前 `.env` 的实际值（问题所在）

```
LLM_ENABLE=true
LLM_PROVIDER=hy3                                    ← 走 Hy3Client（LKEAP 客户端）
LLM_BASE_URL=https://api.lkeap.cloud.tencent.com/plan/v3/chat/completions     ← LKEAP
LLM_HY3_BASE_URL=https://api.lkeap.cloud.tencent.com/plan/v3/chat/completions ← LKEAP
LLM_API_KEY=sk-kpy...（TokenHub 的 token）
LLM_QUALITY_MODEL=hy4-preview
ENABLE_MOCK_AGENT=false
LLM_FALLBACK_ENABLE=false
```

结论链条：
1. `LLM_PROVIDER=hy3` → `newLLMClient` 走 `Hy3Client`；
2. `Hy3Client` 用 `ResolveBaseURL("hy3")` → `LLM_HY3_BASE_URL` → **LKEAP**；
3. `Hy3Client` 用 `ResolveAPIKey("hy3")` → 因 `LLM_HY3_API_KEY` 为空，回退到 `LLM_API_KEY` → **TokenHub token**；
4. 「LKEAP 端点」 + 「TokenHub token」 → LKEAP 返回 **401 not authorized**。

即：**token 的平台（TokenHub）与配置的调用地址（LKEAP）不一致**。

### 4.4 为什么最终是 500 而不是 503/504

前端错误分类：

```32:40:web/src/app/pages/JobRecommendationPage.tsx
function classifyDeepError(err: any): DeepErrorType {
  const msg = JSON.stringify(err).toLowerCase();
  if (/504|gateway timeout|gateway-timeout/i.test(msg)) return "GATEWAY_TIMEOUT";
  if (/503|模型未启用|大模型服务|服务未配置|深度推荐需要|llm unavailable|not available/i.test(msg)) return "LLM_UNAVAILABLE";
  if (/401|unauthorized|token/i.test(msg)) return "UNKNOWN";
  if (/timeout|fetch failed|network/i.test(msg)) return "NETWORK_ERROR";
  return "GENERATION_FAILED";
}
```

后端返回的是 500（`LLM failed and fallback disabled: llm_api_key_missing`），不匹配 503/504/401/网络任何分支 → `GENERATION_FAILED`。

## 五、修复方案（需改配置，无需改业务代码）

### 5.1 首选：把端点改成 TokenHub

修改 `/workspace/.env`：

```diff
- LLM_PROVIDER=hy3
- LLM_BASE_URL=https://api.lkeap.cloud.tencent.com/plan/v3/chat/completions
- LLM_HY3_BASE_URL=https://api.lkeap.cloud.tencent.com/plan/v3/chat/completions
+ LLM_PROVIDER=tokenhub          # 或 hunyuan / deepseek，均走 OpenAI 兼容客户端
+ LLM_BASE_URL=https://tokenhub.tencentmaas.com/v1/chat/completions
```

说明：
- `LLM_PROVIDER` 改为 `tokenhub`（或 `hunyuan` / `deepseek`）后，`newLLMClient` 走 `HunyuanClient`（OpenAI 兼容），使用 `LLM_BASE_URL`；
- `HunyuanClient` 不会发送 LKEAP 特有的 `extra_body.chat_template_kwargs.reasoning_effort`，发送标准 OpenAI 请求体（实测 HTTP 200）；
- `LLM_HY3_BASE_URL` 仅在 `provider=hy3` 时生效，切走后不再使用，可保留不动。

### 5.2 可选：保持 `hy3` provider，但把 hy3 地址也指向 TokenHub

若确需保留 `provider=hy3`（Hy3Client 的 `reasoning_effort` 能力），则需把 `LLM_HY3_BASE_URL` 也改成 TokenHub 地址。但注意：实测 `Hy3Client` 往 TokenHub 发送 `extra_body.chat_template_kwargs.reasoning_effort=high` 会触发超长 reasoning 导致超时（30s 无响应），**不推荐**。TokenHub 的 `hy4-preview` 本身是 reasoning 模型，标准 OpenAI 请求即自带 `reasoning_content`，无需额外 reasoning_effort 参数。

### 5.3 验证方法

改完 `.env` 后重启服务，再用以下命令验证（应返回 200）：

```bash
curl -X POST 'https://tokenhub.tencentmaas.com/v1/chat/completions' \
  -H "Authorization: Bearer <LLM_API_KEY>" \
  -H 'Content-Type: application/json' \
  -d '{"model":"hy4-preview","messages":[{"role":"user","content":"hi"}],"stream":false}'
```

或在后端日志中确认不再出现 `[LLM-Hy3] http 401`。

## 六、次要问题（非阻断，但值得一并关注）

1. **错误码命名误导**：`hy3_client.go#errorFromHTTPStatus` 把 401/403 映射成 `ErrLLMAPIKeyMissing`（「Key 缺失」），但此处是「Key 存在但平台不匹配」，日志与告警易误判为「Key 无效」。

2. **质量画像 stale 无法自愈**：resume 8 的 `quality` 档 `resume_profiles` 为 `stale`（2026-06-12），异步重建依赖 LLM，端点错误期间永远无法回到 ready。虽然 `Recommend()` 已做「quality→fast」降级未阻断请求，但属于同一根因的连带表现。

3. **前端提示与后端实际行为不一致**：提示「已为你保留快速推荐结果」，但后端实际返回 500；「快速推荐结果」是前端 state 缓存的 `fastResult`，并非后端主动保留，易误导排查。

4. **配置组合放大影响**：`ENABLE_MOCK_AGENT=false` + `LLM_FALLBACK_ENABLE=false` 意味着「LLM 一挂就 500，不给任何兜底」。若希望体验可接受降级，应至少放开其一。

## 八、一句话结论

> 深度推荐失败的直接原因是 **后端 LLM 端点配置错误**：token 是 TokenHub 的 token，但 `LLM_PROVIDER=hy3` 且 `LLM_BASE_URL`/`LLM_HY3_BASE_URL` 指向 LKEAP，导致所有 LLM 调用 401。把 `LLM_PROVIDER` 改为 `tokenhub`、`LLM_BASE_URL` 改为 `https://tokenhub.tencentmaas.com/v1/chat/completions` 即可恢复，无需改业务代码。
