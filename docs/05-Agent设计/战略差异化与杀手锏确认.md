# 战略差异化与杀手锏确认

> 创建时间：2026-05-30
> 所属阶段：4-3.5.B
> 依据文档：说明书、项目状态、阶段4-3方案、岗位匹配Agent、岗位推荐Agent、Agent总览、Prompt模板、JSON输出规范、失败兜底与Mock回退策略

## 1. 背景

当前项目已完成阶段 4-3.5（推荐接口联调与 fallback 验收），具备以下能力：

- MatchAnalysisAgent LLM Pipeline 优先 + Mock fallback
- RecommendationAgent LLM Pipeline 优先 + Mock fallback
- 匹配分析接口稳定性验收通过
- 推荐接口稳定性验收通过
- 候选岗位白名单校验、job_id 过滤、Mock fallback 均已验证

在进入下一阶段之前，需要明确项目的战略定位和差异化方向。

## 2. 当前风险：与官网 Offer捕手 同质化

腾讯校招官网已有 Offer捕手 类 AI 交互入口，能够做岗位问答和基础岗位推荐。

**风险**：如果本项目仍以"根据简历推荐岗位"作为唯一核心卖点，将与官网 Offer捕手 做同质化定位，缺乏差异化竞争力。

**但注意**：

- 不攻击或贬低腾讯官网能力
- 不写"腾讯官网做得不好"
- 不写"我们替代 Offer捕手"
- Offer捕手 是官网的问答和推荐入口，定位是帮助学生在官网内了解岗位

**正确表达**：

> 本项目不与官网 Offer捕手 做同质化定位，而是将能力下沉到学生投递前的深度决策和简历初筛优化环节。

## 3. 新产品定位

本项目定位为：

**面向学生的投递前决策与简历初筛优化系统**

或：

**基于真实岗位 JD 与学生简历证据的 AI 求职决策工作台**

核心一句话：

> 官方 Offer捕手 告诉学生可以了解什么岗位；
> Offer 捕手帮助学生判断为什么投、先投哪个、哪里有风险、简历怎么改、优化到什么时候可以停止。

## 4. 不做什么

| 不做 | 原因 |
|------|------|
| 不与 Offer捕手 做同质化岗位推荐问答 | 官网已有，做同质化无竞争力 |
| 不做职业规划系统 | 超出课题主旨 |
| 不做人格判断系统 | 不评价人格、家庭、隐私、敏感属性 |
| 不替用户编造虚假简历 | AI 不能替用户编造经历 |
| 不做官网 Offer捕手 的替代品 | 定位不同，能力下沉到投递前决策 |

## 5. Demo 新主线

学生填写 / 输入简历资料
→ 系统基于真实岗位 JD 推荐岗位
→ 用户选择目标岗位
→ 系统做 JD 证据链匹配分析
→ 系统给出简历初筛优化建议
→ 系统判断当前是否可以投递
→ 系统告诉用户优化到什么程度可以停止

**对比旧主线**：

| 旧主线 | 新主线 |
|--------|--------|
| 上传简历 → AI 推荐几个岗位 → 结束 | 简历 → 推荐岗位 → 选择目标 → JD 证据链匹配 → 简历优化 → 投递边界判断 → 优化停止条件 |
| 只给结论 | 给证据、给边界、给可核实建议 |
| 推荐完就结束 | 推荐只是起点，后续有完整的决策和优化闭环 |

## 6. 杀手锏一：投递边界与优化停止条件

学生的痛点不是只缺少优化建议，而是不知道优化到什么时候可以停止。

如果 AI 永远建议继续学习、继续补简历，产品会变成无底洞。

### 6.1 apply_readiness

建议枚举：

| 值 | 含义 |
|----|------|
| `ready_to_apply` | 当前简历已能证明目标岗位核心能力，建议投递 |
| `quick_fix_before_apply` | 有少量可快速修复的问题，修复后即可投递 |
| `not_ready_for_this_role` | 当前简历与目标岗位存在显著差距，不建议立即投递 |
| `insufficient_information` | 简历信息不足，无法做出可靠判断 |

### 6.2 optimization_stop_signal

建议枚举：

| 值 | 含义 |
|----|------|
| `stop_and_apply` | 当前简历已满足核心要求，不需要继续优化，建议投递 |
| `fix_top_3_then_apply` | 修复 3 个关键问题后即可投递，不要无限优化 |
| `needs_more_evidence` | 需要补充更多真实经历或项目证据，但这不是无限优化 |
| `target_role_mismatch` | 当前简历与目标岗位方向不匹配，建议考虑其他岗位 |

### 6.3 核心原则

> 优化不是越多越好。
> 当简历已能证明目标岗位核心能力，且无明显格式、真实性和方向问题时，应建议用户投递，而不是继续无限优化。

## 7. 杀手锏二：JD 证据链匹配

系统不只给"适合/不适合"结论，而要把岗位 JD 要求、简历证据、差距和行动建议串起来。

### 7.1 证据链结构

```
JD 要求
→ 简历证据
→ 匹配判断
→ 风险 / 差距
→ 投递建议
→ 简历优化动作
```

### 7.2 示例

```
岗位要求：Go 后端开发、数据库、缓存、接口开发
简历证据：GoFrame 项目、MySQL、Redis、权限模块
判断：核心技能匹配
差距：缺少压测结果、线上问题处理、业务指标
建议：补充项目中个人负责模块和可核实结果
```

### 7.3 核心原则

> 每条建议都要尽量绑定 JD 和简历证据。
> 不要输出泛泛建议。
> 不要脱离岗位要求做职业规划式回答。

## 8. 杀手锏三：Agent 输出 Quality Gate

LLM 生成内容不一定可靠，尤其在求职场景中可能出现编造经历、泛化建议、无限优化、过度承诺等问题。

### 8.1 设计

```
Generator Agent
→ Quality Gate / Critic
→ 通过则返回
→ 不通过则重试一次或保守 fallback
```

**本阶段不实现，只做设计确认。**

### 8.2 Quality Gate 检查项

| 序号 | 检查项 | 说明 |
|------|--------|------|
| 1 | 是否基于真实 JD | 不能脱离输入岗位数据编造内容 |
| 2 | 是否基于用户简历证据 | 不能编造用户不存在的经历 |
| 3 | 是否编造经历 | 不允许 AI 替用户编造项目、指标、实习 |
| 4 | 是否编造岗位 | 推荐岗位必须来自候选集 |
| 5 | 是否给出投递边界 | 是否有 apply_readiness 判断 |
| 6 | 是否给出优化停止条件 | 是否有 optimization_stop_signal |
| 7 | 是否使用"示例参考"而非"必须照写" | 改写建议必须是参考，不是指令 |
| 8 | 是否提醒用户 AI 可能出错，需要自行核实 | verification_notice |
| 9 | 是否包含自查问题或学习关键词 | self_check_question / learn_more_query |
| 10 | 是否没有评价人格、家庭、隐私、敏感属性 | 不做人格判断 |
| 11 | 是否符合 JSON Schema | 结构合法性 |
| 12 | 是否可被前端稳定展示 | 前端消费可行性 |

### 8.3 核心约束

> Quality Gate 不是为了让模型无限自我反省。
> 最多重试一次。
> 仍不合格则输出保守结果或 fallback。

## 9. 简历优化表达原则：示例参考而非必须照写

AI 不能替用户编造经历。AI 给出的改写只能作为表达参考。用户必须基于真实经历核实后再使用。

### 9.1 标准输出结构

| 字段 | 说明 |
|------|------|
| 原表达 | 用户当前的简历表达 |
| 问题 | 影响初筛的表述问题 |
| 影响初筛的原因 | 为什么这个问题会影响 HR 初筛 |
| 优化方向 | 应该怎么调整表达 |
| 示例参考 | 基于 STAR-T 方法的改写参考 |
| 使用前请核实 | 用户必须结合真实经历核实 |
| 自查问题 | 帮助用户确认是否适用 |
| 学习关键词 | 用户可进一步学习的方向 |

### 9.2 术语替换

| 旧术语 | 新术语 | 原因 |
|--------|--------|------|
| "建议改为" | "示例参考" | 避免暗示用户必须照抄 |
| "优化后" | "参考表达" | 不暗示这是用户应该使用的最终版本 |
| "可以写" | "可以考虑这样表达" | 强调是参考，不是指令 |

## 10. START / STAR-T 技术岗表达法

### 10.1 方法

| 要素 | 说明 |
|------|------|
| Situation | 场景：在什么背景下 |
| Task | 任务：要解决什么问题 |
| Action | 行动：做了什么 |
| Result | 结果：取得了什么成效 |
| Tech | 技术栈 / 方法：使用了什么技术或方法 |

或称 **STAR-T 技术岗简历表达法**。

### 10.2 系统职责

系统帮助用户检查经历中缺少 S/T/A/R/Tech 哪一部分，而不是简单替用户写一段更漂亮的话。

示例：

```
当前表达："参与了 GoFrame 项目的开发"
→ 缺少 Task：具体要解决什么问题？
→ 缺少 Result：取得了什么成效？
→ 缺少 Tech：使用了 GoFrame 的哪些模块？
→ 示例参考："在 XX 系统重构中（S），负责权限模块的设计与实现（T），使用 GoFrame 框架实现 RBAC 权限控制（A/Tech），上线后权限相关工单减少 40%（R）"
→ 使用前请核实：请确认上述数据是否真实，AI 可能理解错误
```

## 11. 建议可核实机制

AI 建议不应该让学生盲目照抄，而应帮助学生知道自己接下来该核实什么、学习什么、补充什么。

### 11.1 建议字段

| 字段 | 说明 |
|------|------|
| `self_check_question` | 帮助用户确认建议是否适用的自查问题 |
| `learn_more_query` | 用户可进一步搜索学习的方向或关键词 |
| `verification_notice` | 提醒用户 AI 建议仅供参考，需自行核实 |

### 11.2 示例

**self_check_question**:

> 请确认你是否确实独立负责过该模块，而不是团队整体成果。

**learn_more_query**:

> Go 后端实习 简历 项目经历 STAR 写法

**verification_notice**:

> 以下示例仅供表达参考，AI 可能理解错误，请结合真实经历核实后使用。

## 12. 极端场景处理边界

本项目只围绕课题主旨：**帮助学生有效匹配合适岗位；提升对心仪岗位的简历初筛命中率。**

| 极端场景 | 处理方式 |
|----------|----------|
| 信息不足 | 暂不建议做强推荐，提示补充关键经历 |
| 简历很弱 | 给出投递前最小改进项 |
| 岗位不匹配 | 解释当前岗位初筛风险 |
| 海外 / 地点问题 | 回到岗位地点与候选人意向匹配 |
| 候选人过强 | 建议优先考虑更能发挥经历优势的岗位类型，但不做长期职业规划 |
