## 5. Prompt 资产目录设计

### 5.1 推荐目录

```
server/prompts/
  match_analysis_v1.md         # 匹配分析 Prompt（P0 优先打磨）
  recommendation_v1.md         # 岗位推荐 Prompt
  resume_optimization_v1.md    # 简历优化 Prompt
  json_repair_v1.md            # JSON 修复 Prompt
  schema/
    match_analysis_schema.json     # 匹配分析输出 Schema
    recommendation_schema.json     # 推荐输出 Schema
    resume_optimization_schema.json # 简历优化输出 Schema
```

### 5.2 设计原则

1. **Prompt 不放 SQL** — Prompt 是产品资产，不属于数据层
2. **Prompt 不写死在 Go 代码里** — 代码中用 `os.ReadFile` 或 `embed` 读取，便于独立迭代
3. **Prompt 作为产品资产单独管理** — 独立版本号，独立变更记录
4. **4-1.4.1 开始创建具体 Prompt 文件** — 当前 4-1.4.0 只设计目录，不创建目录
5. **Schema 与 Prompt 配套** — 每个 Prompt 对应一个 JSON Schema 用于输出校验

### 5.3 与现有目录的关系

当前 `server/internal/agent/prompts/` 目录在 Prompt模板.md 文档中规划但未创建。4-1.4 将采用 `server/prompts/` 作为 Prompt 资产目录，原因：

- `server/internal/agent/prompts/` 属于 Go internal 包，不方便外部工具直接引用
- `server/prompts/` 更直观，可作为独立资产管理
- Prompt 文件可被 Go 代码通过 `embed` 或 `os.ReadFile` 读取
- Schema JSON 文件可被前端、测试脚本等多种工具引用

## 6. Agent 职责边界

### 6.1 当前 Agent 采用 Stateless 单次请求模式

```
一次请求输入一次上下文
→ 模型生成一次 JSON 结果
→ 不做长期记忆
→ 不做 MCP 记忆
→ 不做多轮规划
```

### 6.2 不做事项

| 不做 | 原因 |
|------|------|
| MCP 记忆 | Demo 阶段不需要，增加复杂度 |
| 多轮 Agent | 单次请求即可满足推荐/匹配需求 |
| Agent 自主调用工具 | 用 JSON 输出约束替代 |
| 流式输出 | 当前同步返回即可 |
| Function Calling | 用 Prompt 约束 + JSON Schema 替代 |

### 6.3 后续模型调用链目标（4-2 实现）

```
简历版本 + 腾讯岗位完整 JD + 输出 Schema
→ Prompt 模板
→ Hunyuan / LLM
→ JSON 输出
→ JSON 校验
→ 成功返回 llm_agent
→ 失败回退 mock_agent
```

注意：这是后续 4-2 的目标链路。4-1.4 只做 Prompt 和 Schema 设计，不做代码调用。

## 7. 单次请求 Agent 设计原则

1. **输入明确**：每次请求包含完整的简历上下文 + 岗位上下文 + 业务约束
2. **输出确定**：每次输出是固定结构的 JSON，不做自由文本
3. **无副作用**：Agent 不修改数据库，不调用外部接口，不修改用户数据
4. **可回退**：任何失败都可回退到 Mock Agent，用户无感知
5. **可追溯**：通过 generated_by 字段标识结果来源

## 8. Prompt 类型规划

### 8.1 匹配分析 Prompt — P0（最高优先级）

**用途**：基于简历和腾讯岗位完整 JD，输出匹配分数、证据链、风险点、P0/P1/P2 简历优化建议、面试追问预测。

**它是 Demo 的核心杀手锏。**

**优先级 P0 的原因**：
- 岗位匹配分析最直接对应"提升初筛命中率"
- 是 Demo 冲前 10 的关键展示点
- 输入最明确（一份简历 + 一个岗位 JD），输出最结构化
- 与 Mock Agent 的 evidence_chain 设计完全对照

**匹配分析 Prompt 应输出**：
- match_score（0-100）
- screening_result（highly_likely / likely / possible / risky）
- evidence_chain（JD 要求 → 简历证据 → 判断）
- match_highlights
- risk_points
- optimization_suggestions（P0 / P1 / P2）
- interview_questions（面试追问预测，可选）
- authenticity_notice

### 8.2 岗位推荐 Prompt — P1

**用途**：基于简历和候选岗位列表，输出推荐岗位排序、推荐理由、风险点、投递策略。

**与匹配分析的区别**：
- 匹配分析：1 简历 + 1 岗位 → 深度分析
- 岗位推荐：1 简历 + N 岗位 → 排序筛选

**推荐 Prompt 应输出**：
- recommended_jobs（排序后的岗位列表）
- 每个岗位的 priority / recommendation_score / recommendation_reason
- match_highlights / risk_points / suggested_action
- summary

### 8.3 简历优化 Prompt — P1

**用途**：基于某个目标岗位和当前简历，输出 P0/P1/P2 优化动作。

**简历优化 Prompt 应输出**：
- optimization_items（P0/P1/P2 分级）
- 每项包含 title / reason / action / before_after_example（可选）
- overall_assessment
- authenticity_notice

### 8.4 JSON 修复 Prompt — P2

**用途**：当模型输出非标准 JSON 时，用于尝试修复为合法 JSON。

**JSON 修复 Prompt 应输出**：
- 修复后的合法 JSON
- 修复说明（哪些地方做了修正）

**使用场景**：
- LLM 输出包含 Markdown 代码块包裹
- LLM 输出 JSON 中有尾逗号、缺少引号等语法问题
- LLM 输出 JSON 中有注释
- LLM 输出截断

**必须明确**：
- 4-1.4 优先打磨匹配分析 Prompt
- 岗位推荐 Prompt 在匹配分析 Prompt 稳定后再设计
- 简历优化 Prompt 和 JSON 修复 Prompt 在 4-2 之后按需设计

## 9. 输入上下文组装规范

### 9.1 简历上下文

Prompt 输入中应包含以下简历字段（映射自 resume_versions 表）：

|-------------------|---------|------|
| resume_id | id | 简历版本 ID |
| version_id | id | 版本 ID（同 resume_id） |

| experience | experience_json | 工作/实习经历（JSON 数组） |
| self_evaluation | self_evaluation | 自我评价 |

**补充说明**：
- resume_versions 表中无 strengths / weaknesses 字段，后续按现有字段映射
- project_json / experience_json / education_json 是 JSON 数组，Prompt 中应展示完整内容
- skills_json 是技能关键词数组，Prompt 中应直接展示

### 9.2 岗位上下文

Prompt 输入中应包含以下岗位字段（映射自 jobs 表）：

| Prompt 中的字段名 | 来源字段 | 说明 |
|-------------------|---------|------|
| job_id | id | 岗位 ID |
| title | title | 岗位名称 |
| department | department | 部门 |
| city | city | 城市 |
| category | category | 方向分类 |
| job_type | job_type | 岗位类型 |
| description | description | 岗位职责描述（腾讯完整 JD） |
| requirements | requirements | 任职要求（腾讯完整 JD） |
| external_source | external_source | 数据来源标识 |
| external_id | external_id | 外部岗位 ID |
| data_quality | data_quality | 数据质量标记 |
| source_url | source_url | 公开详情页 URL |

**补充说明**：
- description 和 requirements 是匹配分析 Prompt 的核心输入
- data_quality 用于 Prompt 差异化处理：full_jd 执行完整分析，summary_only 返回降级提示
- source_url 可在输出中引用，方便用户查看原始岗位

### 9.3 业务约束上下文

Prompt 中应包含以下业务约束：

```
目标：提升初筛命中率
要求：基于证据链，不编造经历
要求：不能建议用户虚构项目
要求：输出必须是 JSON
要求：建议要具体、可执行
要求：区分 P0/P1/P2 优先级
要求：分数必须是 0-100 整数
要求：枚举值必须固定（screening_result / priority / judgement）
要求：证据链必须引用 JD 和简历中的真实内容
要求：包含真实性提示（authenticity_notice）
要求：不输出 Markdown、不输出解释性前后缀、不输出代码块
```

## 10. 输出 JSON Schema 设计原则

### 10.1 核心原则

1. **所有 LLM 输出必须是严格 JSON** — 不允许 Markdown 包裹，不允许多余解释
2. **不允许 Markdown 包裹** — 不要 ` ```json ... ``` ` 
3. **不允许多余解释** — 不要"以下是分析结果："等前后缀
4. **必填字段必须存在** — 每种 Agent 有明确的必填字段列表
5. **分数必须是 0-100** — 整数，超范围截断
6. **枚举值必须固定** — screening_result / priority / judgement 等枚举值不可自创
7. **数组长度必须限制** — evidence_chain 至少 1 项，optimization_suggestions 至少 1 项
8. **字段缺失时后端应兜底** — 后端校验发现缺失时回退 Mock
9. **JSON parse 失败则回退 Mock** — 不尝试修复超过一次

### 10.2 与 Mock Agent 输出结构的对齐

匹配分析 Prompt 输出应与 `model.MatchAnalysisResult` 对齐：

| Mock Agent 输出字段 | Prompt 应输出字段 | 说明 |
|--------------------|-------------------|------|
| MatchScore | match_score | 0-100 |
| ScreeningResult | screening_result | highly_likely / likely / possible / risky |
| EvidenceChain | evidence_chain | 数组，每项含 requirement / resume_point / judgement |
| MatchHighlights | match_highlights | 字符串数组 |
| RiskPoints | risk_points | 字符串数组 |
| OptimizationSuggestions | optimization_suggestions | 数组，每项含 priority / title / reason / action |
| NextSteps | next_steps | 字符串数组 |
| AuthenticityNotice | authenticity_notice | 真实性提示 |

推荐 Prompt 输出应与 `model.RecommendedJob` 对齐：

| Mock Agent 输出字段 | Prompt 应输出字段 | 说明 |
|--------------------|-------------------|------|
| JobID | job_id | 与输入岗位 ID 一致 |
| Priority | priority | strong_recommend / recommend / try |
| RecommendationScore | recommendation_score | 0-100 |
| RecommendationReason | recommendation_reason | 非空 |
| MatchHighlights | match_highlights | 字符串数组 |
| RiskPoints | risk_points | 字符串数组 |
| SuggestedAction | suggested_action | 非空 |

### 10.3 Prompt 新增字段方向

Prompt 输出可在 Mock Agent 基础上新增以下字段（4-1.4.2 固定 Schema 时确认）：

**匹配分析新增方向**：
- `interview_questions`：面试追问预测（可选）
- `optimization_suggestions[].priority` 增加 `P2` 级别
- `jd_key_requirements`：JD 核心要求摘要
- `resume_evidence`：简历核心证据摘要

**推荐新增方向**：
- `suggested_action` 更具体的投递策略

### 10.4 Schema 文件格式

Schema 文件使用 JSON Schema 格式，存放在 `server/prompts/schema/` 目录：

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "MatchAnalysisOutput",
  "type": "object",
  "required": ["match_score", "screening_result", "evidence_chain", ...],
  "properties": {
    "match_score": { "type": "integer", "minimum": 0, "maximum": 100 },
    "screening_result": { "type": "string", "enum": ["highly_likely", "likely", "possible", "risky"] },
    ...
  }
}
```

4-1.4.2 将创建完整 Schema 文件，4-1.4.0 只定义原则。

| 指标 | 通过标准 |

| 是否避免建议造假 | 不出现"可以虚构"相关表述 |
| 是否适合 Demo 展示 | 输出有产品感，便于前端展示 |

## 13. 失败兜底与 Mock 回退原则

### 13.1 失败场景设计

| 序号 | 失败场景 | 严重度 | 说明 |
|------|---------|--------|------|
| 1 | 模型超时 | 🟡 | 请求超过 LLM_TIMEOUT_SECONDS |
| 2 | 模型返回非 JSON | 🔴 | LLM 输出不是合法 JSON |
| 3 | JSON 字段缺失 | 🟡 | 必填字段不存在 |
| 4 | JSON 类型错误 | 🟡 | 字段类型与 Schema 不匹配 |
| 5 | 分数超范围 | 🟢 | match_score > 100 或 < 0 |
| 6 | 输出过长 | 🟢 | 超过 max_tokens 截断 |
| 7 | 内容明显幻觉 | 🔴 | 出现简历中不存在的经历 |
| 8 | Hunyuan 不可用 | 🟡 | HTTP 5xx / 网络错误 |
| 9 | LLM 配置未开启 | 🟢 | ENABLE_LLM_AGENT=false |

### 13.2 处理策略

```
1. 优先校验 JSON
   → json.Unmarshal 成功？
   → 否：尝试一次 JSON repair（去除 Markdown 包裹等）
   → repair 仍失败：回退 Mock Agent

2. JSON 校验通过后校验字段
   → 必填字段存在？
   → 枚举值合法？
   → 分数在 0-100？
   → 字段缺失 / 类型错误：回退 Mock Agent
   → 分数超范围：截断到 0-100，不回退

3. 内容校验
   → 是否包含虚构经历？
   → 是否建议造假？
   → 是：回退 Mock Agent

4. 回退 Mock Agent 时
   → generated_by = "llm_agent_fallback"
   → 日志记录失败原因
   → 不阻断用户操作
```

### 13.3 回退优先级

| 条件 | 行为 | generated_by |
|------|------|-------------|
| ENABLE_LLM_AGENT=false | 始终使用 Mock Agent | `mock_agent` |
| ENABLE_LLM_AGENT=true 且 LLM 成功 | 使用 LLM 结果 | `llm_agent` |
| ENABLE_LLM_AGENT=true 且 LLM 失败 且 ENABLE_LLM_FALLBACK=true | 回退 Mock Agent | `llm_agent_fallback` |
| ENABLE_LLM_AGENT=true 且 LLM 失败 且 ENABLE_LLM_FALLBACK=false | 返回错误 | — |

## 14. generated_by 标记规范

| 值 | 含义 | 场景 |
|----|------|------|
| `mock_agent` | 完全使用当前 Mock Agent | ENABLE_LLM_AGENT=false 或未配置 LLM |
| `llm_agent` | 模型正常生成并通过 JSON 校验 | ENABLE_LLM_AGENT=true，LLM 调用成功，JSON 合法 |
| `llm_agent_fallback` | 模型调用失败或 JSON 校验失败后回退 Mock | ENABLE_LLM_AGENT=true，LLM 失败，ENABLE_LLM_FALLBACK=true |

当前代码中 generated_by 硬编码为 `"mock_agent"`：
- `recommendation_service.go:119`：`GeneratedBy: "mock_agent"`
- `match_service.go:93`：`GeneratedBy: "mock_agent"`

4-2 实现 LLM Client 后，将根据上述规范动态设置 generated_by。

## 15. 4-1.4 与 4-2 的边界

### 15.1 边界定义

| 阶段 | 范围 | 产物 |
|------|------|------|
| 4-1.4 | Prompt 资产、Schema、离线测试、兜底策略 | Prompt 文件、JSON Schema、测试记录、方案文档 |

### 15.2 为什么先做 4-1.4

**Prompt 是产品大脑，LLM Client 只是调用通道。先固定 Prompt 和输出结构，再写模型调用代码，可以减少返工并提升 Demo 输出质量。**

具体原因：

1. Prompt 质量直接决定 Demo 效果，需先验证可行性
2. JSON Schema 不稳定会导致 LLM Client 代码频繁修改
3. 离线测试可在不写代码的情况下验证模型输出质量
4. Mock Agent 输出结构已稳定，完全可对照设计 Prompt
5. config.go 缺少 EnableLLMAgent / EnableLLMFallback 等 7 个配置字段，直接进 4-2 需先改配置层
6. server/internal/llm/ 为空，从零写 Client 工作量大于先验证 Prompt

### 15.3 4-2 依赖 4-1.4 的产物

| 4-2 依赖 | 4-1.4 产物 |
