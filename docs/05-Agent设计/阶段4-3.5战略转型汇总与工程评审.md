## 1. 背景

项目在完成 4-3.5（推荐接口联调与 fallback 验收）后，发现腾讯校招官网已有 Offer鹅 类 AI 交互入口，能做岗位问答和基础岗位推荐。

为此，项目暂停原计划，插入 4-3.5.B ~ 4-3.5.G 做战略差异化校准。经过 6 个子任务的设计，战略方向已经明确。

本次 4-3.5.H 的核心任务是对 4-3.5.B ~ 4-3.5.G 做阶段汇总，并评审是否需要立即进行工程改造。

## 2. 为什么要插入战略转型阶段

原计划在 4-3.5 之后直接进入 4-3.6（ResumeOptimizationAgent 现状核对），但如果项目与官网 Offer鹅 做同质化定位，就没有差异化竞争力。

插入战略转型阶段的目的是：

1. **明确项目新定位**：不再做"岗位推荐工具"，升级为"投递前决策与简历初筛优化系统"
2. **设计三个核心杀手锏**：投递边界、JD 证据链、Quality Gate
3. **定义极端情况处理边界**：防止 Agent 在特殊场景下输出不当内容
4. **设计灵活简历输入层**：ResumeContextText 作为所有 Agent 判断的输入基础

如果不做这些设计，后续所有 Agent 输出都会缺乏战略方向的统一约束。

## 4. 4-3.5.B 战略差异化与杀手锏确认汇总

**核心结论**：

- 项目不与官网 Offer鹅 做同质化岗位推荐
- 新定位为：面向学生的投递前决策与简历初筛优化系统
- 核心差异从"推荐岗位"升级为"投递前判断、证据链、优化停止条件、可核实建议"

**三个核心杀手锏**：

1. 投递边界与优化停止条件：告诉学生什么时候可以投、先改再投、不建议投
2. JD 证据链匹配：每条结论都有 JD 要求 → 简历证据 → 匹配判断 → 差距风险 → 示例参考 → 用户核实提醒
3. Agent 输出 Quality Gate：JSON Schema 只保证结构合法，Quality Gate 负责内容质量和业务边界

**对 Prompt / Schema / Agent 的影响方向**：

- 后续 Prompt / Schema / Agent 输出需围绕"给证据、边界、可核实建议"升级
- 不立即修改 Prompt / Schema / 代码，只登记方向

## 5. 4-3.5.C 投递边界与优化停止条件汇总

**核心定义**：

- `apply_readiness`：ready_to_apply / quick_fix_before_apply / not_ready_for_this_role / insufficient_information
- `optimization_stop_signal`：stop_and_apply / fix_top_3_then_apply / needs_more_evidence / target_role_mismatch

**核心原则**：

- 优化不是无底洞
- 当简历已经能证明目标岗位核心能力时，应建议投递，而不是继续无限优化
- 区分 Top 3 快速优化项（可立即执行）和长期提升项（后续阶段）

**对 Agent 的影响**：

- 匹配分析 Agent 必须输出 apply_readiness 和 optimization_stop_signal
- 推荐 Agent 必须为每个推荐岗位给出推荐优先级和投递准备度
- apply_readiness 与 optimization_stop_signal 暂作为后续优化方向登记，不立即改 Schema

## 6. 4-3.5.D JD 证据链匹配与 START 规则汇总

**核心定义**：

- `jd_evidence_chain`：JD 要求 → 简历证据 → 匹配判断 → 差距风险 → 示例参考 → 用户核实提醒
- `evidence_strength`：strong / partial / weak / missing
- `match_judgement`：well_matched / partially_matched / gap_identified / missing
- `screening_risk`：high / medium / low

**引入 START / STAR-T 技术岗表达法**：

- Situation → Task → Action → Result → Tech
- 检查简历项目经历中是否缺失某个维度，给出补充方向

**"示例参考"替代"建议改为"**：

- 不使用"建议改为 XXX"的语气
- 使用"示例参考：如果你在项目中使用了 Go，可以这样表达……"
- 用户自行判断是否采用，不是必须照抄

**JD 证据链与 START 规则暂作为后续 Prompt / Schema / Agent 改造方向登记，不立即改工程**

## 7. 4-3.5.E Agent 输出 Quality Gate 汇总

**核心定义**：

- `quality_gate_result`：pass / revise_required / fallback_required / manual_review_suggested
- 十项检查维度：JD grounding / resume evidence / fabrication / apply boundary / optimization stop / example reference / verification / safety tone / consistency / schema display

**关键规则**：

- JSON Schema 只保证结构合法，Quality Gate 负责内容质量和业务边界
- revise once 约束：最多修改一次，修改后仍不通过则 fallback
- conservative_fallback：输出过于激进时回退到保守版本
- mock_fallback：无法修复时回退到 Mock Agent 输出

**Quality Gate 评审结论：不立即实现完整 LLM Critic，后续如落地优先考虑轻量规则版**

## 8. 4-3.5.F 学生求职极端情况处理边界汇总

**核心定义**：

- `candidate_case_type`：normal_case / insufficient_information / weak_resume / target_role_mismatch / overseas_or_location_risk / high_potential_research_or_deep_tech / unclear_job_intention / authenticity_risk / over_optimization_risk / unsafe_user_request
- `case_risk_level`：low / medium / high / critical
- `case_handling_strategy`：normal_response / clarify_before_recommendation / quick_fix_then_apply / recommend_alternative_jobs / conservative_advice / refuse_fabrication / manual_review_suggested

**核心原则**：

- 极端情况处理仍围绕：岗位匹配、初筛命中率、当前简历 × 当前岗位 JD
- 不判断"这个学生行不行"，只判断"当前简历 × 当前岗位 JD 的适配情况"
- 每种极端情况明确了触发条件、推荐输出、禁止表达、与 apply_readiness / Quality Gate 的关系

**candidate_case_type、case_risk_level、case_handling_strategy 暂作为后续优化方向登记**

## 9. 4-3.5.G 灵活在线简历 Profile 与 Agent 上下文汇总

**核心方案**：

- 不强行复刻招聘官网表单
- 不做 PDF 解析
- 不做完全自由一大段文本
- 采用：少量必填字段 + ResumeProfile + ResumeSection + ResumeContextText + profile_summary + privacy_flags

**ResumeProfile**：

- id / user_id / title / target_roles / expected_locations / accept_relocation / education_summary / contact_info_status / created_at / updated_at
- 存意图和摘要，具体经历内容在 ResumeSection

**ResumeSection**：

- id / profile_id / section_type / section_title / content / sort_order / created_at / updated_at
- 16 种 section_type 枚举：education / project / internship / work / competition / research / paper / open_source / certificate / portfolio / self_evaluation / language / overseas_experience / course_project / custom

**ResumeContextText**：

- 按【求职意向】→【教育背景】→ 各 Section 顺序 →【补充信息】固定顺序拼接
- 不包含隐私字段，Agent 可稳定消费

**ResumeContextPayload**：

- resume_context_text + profile_summary + privacy_flags
- Agent 输入建议统一为 ResumeContextText + profile_summary

**隐私字段处理**：

- 姓名不发给 LLM
- 手机号/邮箱只传布尔标记（contact_info_provided / email_provided / phone_provided）
- 不收集身份证号和精确生日

**ResumeProfile / ResumeSection / ResumeContextText 暂不立即做数据库和前端工程改造，建议放到阶段 5 或后续产品体验阶段评估**

## 13. 工程改造方向 A：立即修改 Prompt / Schema

**内容**：

- 把 apply_readiness、optimization_stop_signal、jd_evidence_chain、quality_gate_result、candidate_case_type、resume_context_text 等字段立即加入 Prompt / Schema

**收益**：

- 能让当前 Agent 输出更贴合新战略

**风险**：

- Prompt / Schema 已经稳定，直接改动可能破坏已通过验收的 Match / Recommendation 链路
- MatchAnalysisAgent 和 RecommendationAgent 已通过接口验收，修改 Prompt 可能导致输出不稳定
- 修改 Schema 可能导致 LLM 输出解析失败，增加 fallback 频率

**结论**：

- **不建议立即全面修改**
- 建议在 4-3.5.H 后单独做 Prompt/Schema 评审或放到 4-4/5 阶段
- 如果用户希望先把 Prompt / Schema 和新战略完全对齐，可插入 4-3.5.I Prompt / Schema 改造评审

## 14. 工程改造方向 B：立即实现 Quality Gate

**内容**：

- 新增 QualityGateAgent 或规则质检模块，接入 Pipeline

**收益**：

- 能体现核心杀手锏

**风险**：

- 会增加 LLM 调用成本（如果用 LLM Critic）
- 会增加接口延迟
- 会增加测试复杂度和 fallback 分支
- 当前 LLM 输出本身就不稳定，再加一层 Critic 可能放大不稳定

**结论**：

- **不建议立即接入完整 LLM Critic**
- 后续如实现，应优先做轻量规则版 Quality Gate（不调用 LLM，只做规则检查）
- 完整 LLM Critic 可放到阶段 5 评估

## 15. 工程改造方向 C：立即改 ResumeProfile / ResumeSection

**内容**：

- 新增 ResumeProfile / ResumeSection 表、接口和前端编辑器

**收益**：

- 输入层更稳定，更适合后续 Agent
- 简历数据不再受固定表单限制

**风险**：

- 涉及数据库、接口、前端，改动面大

- 当前 resume_versions 表仍在使用，需要数据迁移方案

**结论**：

- **不建议现在实现完整工程**
- 可以作为阶段 5 产品体验改造重点
- 当前 ResumeContextText 可以从现有 resume_versions 表生成，不依赖 ResumeProfile / ResumeSection 表
