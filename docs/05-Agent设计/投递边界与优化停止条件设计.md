# 投递边界与优化停止条件设计

> 创建时间：2026-05-30
> 所属阶段：4-3.5.C
> 依据文档：战略差异化与杀手锏确认、阶段4-3方案、岗位匹配Agent、岗位推荐Agent、Agent总览、Prompt模板、JSON输出规范、失败兜底与Mock回退策略

## 1. 背景

4-3.5.B 已完成战略差异化确认，项目定位从"岗位推荐工具"升级为"投递前决策与简历初筛优化系统"。

三个核心杀手锏中，**投递边界与优化停止条件**是杀手锏一，也是本项目与官网 Offer鹅 最核心的差异化能力。

学生真正需要的不只是"继续优化简历"的建议，而是知道**什么时候可以停止优化并开始投递**。如果 AI 永远建议继续学习、继续补项目、继续完善表达，产品就会变成无底洞。

本文档定义投递边界判断和优化停止条件的完整规则。

## 2. 核心问题：优化不是无底洞

学生使用 AI 求职工具时，最怕的不是没有建议，而是永远在优化、永远不够好、永远不敢投。

**产品必须回答的问题**：

1. 什么时候可以投？
2. 什么时候先改再投？
3. 什么时候不建议投这个岗位？
4. 什么时候信息不足无法判断？
5. 什么时候应该停止继续优化？

**核心原则**：

> 优化不是越多越好。
> 当简历已经能够证明目标岗位的核心能力，且不存在明显真实性、方向性、格式性问题时，系统应建议用户投递，而不是继续无限优化。

## 3. 设计目标

1. 让每个匹配分析结果都包含投递准备度判断
2. 让每个匹配分析结果都包含优化停止信号
3. 区分"短期投递优化"和"长期能力提升"
4. 不让学生陷入无限优化循环
5. 每个判断都要基于 JD 要求和简历证据，不能凭感觉
6. 不做人格、价值观、家庭背景判断
7. 不鼓励造假
8. 不承诺一定通过初筛

## 4. 基本原则

### 4.1 投递边界只针对当前岗位，不评价用户整体能力

`apply_readiness` 是针对"当前简历 × 当前岗位 JD"的投递前判断。

它不是对用户个人能力、人格、潜力、职业未来的总体评价。

**禁止表达**：

- 你不适合互联网
- 你不适合腾讯
- 你能力太差
- 你价值观不符

**推荐表达**：

- 当前简历对该岗位的关键要求覆盖不足
- 当前信息不足，无法稳定判断是否适合投递
- 当前岗位要求与简历证据存在较大差距，暂不建议直接投递该岗位

### 4.2 投递判断必须基于 JD 和简历证据

投递边界不能凭感觉判断。每个结论都必须尽量来自：

1. 岗位 JD 要求
2. 简历中已有证据
3. 缺失或不足的证据
4. 可在短时间内修复的表达问题

**不得基于**：

- 性别
- 年龄
- 家庭背景
- 地域偏见
- 学校歧视
- 人格推断
- 未经用户提供的信息

### 4.3 区分"短期投递优化"和"长期能力提升"

系统应区分：

1. 投递前可以快速修改的简历表达问题
2. 需要长期积累的能力或经历问题

**可以快速修改**：

- 项目描述太笼统
- 技术栈没有和职责绑定
- 缺少个人负责模块
- 缺少结果表达
- 简历结构混乱

**不能短期解决**：

- 没有任何相关项目
- 没有编程基础
- 没有目标岗位所需核心能力
- 目标岗位跨度过大

产品输出必须避免把长期能力提升包装成"投递前马上能解决的问题"。

## 5. apply_readiness 枚举设计

### 5.1 定义

`apply_readiness` 表示当前简历对目标岗位的投递准备度。

### 5.2 枚举值

#### 5.2.1 ready_to_apply

**定义**：当前简历已经基本覆盖目标岗位核心要求，可以进入投递。

**触发条件**：

1. 简历中存在与岗位核心要求匹配的经历证据
2. 目标岗位方向与用户经历基本一致
3. 关键技能有明确项目或实习支撑
4. 简历信息完整度中等以上
5. 没有明显真实性风险
6. 没有明显地点 / 投递条件冲突
7. 只存在轻微表达优化空间

**用户下一步**：可以投递。投递前可做轻量润色，但不建议继续无限打磨。

**输出语气**：鼓励但不过度承诺。明确告知可以投递，但投递结果取决于多种因素。

**不应该说什么**：

- 你一定能通过初筛
- 这个岗位稳了
- 你的简历很完美

**示例表达**：

> 当前简历已经能够证明你具备该岗位所需的主要能力，建议进入投递。投递前可优先检查项目经历中个人职责和结果表达是否清晰，不必为了追求"完美简历"而持续延后投递。

---

#### 5.2.2 quick_fix_before_apply

**定义**：当前简历与岗位有一定匹配基础，但存在 2-3 个短时间可修复的问题，建议快速修改后投递。

**触发条件**：

1. 核心技能或经历基本相关
2. 但表达不够清楚
3. 缺少个人职责边界
4. 缺少结果或产出
5. 简历关键词与 JD 对齐不足
6. 问题可在 30-60 分钟内通过表达优化改善

**用户下一步**：先完成 Top 3 快速优化项，再投递。

**输出语气**：务实、可操作。明确列出具体改什么、怎么改、改完就投。

**不应该说什么**：

- 你还需要大量优化
- 你的简历问题很多
- 建议重写整个简历

**示例表达**：

> 当前可以作为投递候选，但建议先完成 2-3 个快速优化点：补充项目中的个人负责模块、明确使用的技术栈，并增加可核实的结果描述。完成这些修改后即可投递，不需要继续做大范围重写。

---

#### 5.2.3 not_ready_for_this_role

**定义**：当前简历与该岗位关键要求存在明显差距，不建议直接投递该岗位。

**触发条件**：

1. 岗位核心要求在简历中几乎没有证据
2. 用户目标方向与岗位要求跨度较大
3. 缺少该岗位必要技能或经历
4. 不是简单改写能解决的问题
5. 强行投递可能初筛通过率较低

**用户下一步**：不建议直接投递该岗位。可以选择更匹配的岗位，或先补充相关项目 / 实习经历。

**输出语气**：客观、不贬低。只评价简历与岗位的匹配度，不评价用户本人。

**不应该说什么**：

- 你不适合这个岗位
- 你的能力不够
- 你不如换个方向

**示例表达**：

> 当前简历中缺少该岗位核心要求的直接证据，问题不是简单改写可以解决的。建议优先选择与现有经历更匹配的岗位，或在补充相关项目经历后再考虑投递该岗位。

**注意**：

- 不要评价用户本人不行
- 只能评价当前简历与当前岗位的匹配不足

---

#### 5.2.4 insufficient_information

**定义**：当前简历信息不足，系统无法稳定判断是否适合投递。

**触发条件**：

1. 简历内容过短
2. 缺少教育经历
3. 缺少项目 / 实习 / 竞赛 / 论文等任一能力证明
4. 工作意向不明确
5. 目标岗位信息不足
6. 用户只填写了非常泛的自我评价

**用户下一步**：先补充必要信息，再进行匹配和优化。

**输出语气**：引导、不施压。告诉用户需要补什么，但不说"你的简历太差"。

**不应该说什么**：

- 你的简历什么都没有
- 你没法投递任何岗位
- 请先完善简历再来

**示例表达**：

> 当前信息不足，系统无法稳定判断你是否适合投递该岗位。建议先补充至少一段项目、实习、竞赛、论文或课程设计经历，并说明你负责了什么、使用了什么方法、产生了什么结果。

### 5.3 枚举汇总

| 值 | 定义 | 投递建议 | 优化范围 |
|---|------|---------|---------|
| `ready_to_apply` | 核心能力已覆盖，可以投递 | 建议投递 | 轻量润色 |
| `quick_fix_before_apply` | 有匹配基础，存在 2-3 个短时可修复问题 | 快速修复后投递 | Top 3 快速优化项 |
| `not_ready_for_this_role` | 与岗位关键要求差距明显 | 不建议投递该岗位 | 选择更匹配岗位或补充经历 |
| `insufficient_information` | 信息不足，无法稳定判断 | 先补充信息 | 补充关键经历 |

## 6. optimization_stop_signal 枚举设计

### 6.1 定义

`optimization_stop_signal` 表示当前简历的优化停止信号，告诉用户是否应该继续优化还是可以投递。

### 6.2 枚举值

#### 6.2.1 stop_and_apply

**定义**：当前不建议继续大幅优化，应该开始投递。

**对应关系**：通常对应 `apply_readiness=ready_to_apply`

**触发条件**：

1. 核心 JD 要求已有简历证据
2. 简历结构清楚
3. 只是存在轻微表达优化
4. 继续打磨的边际收益低
5. 投递时效比继续修改更重要

**示例表达**：

> 当前简历已经能够支撑该岗位投递，继续大幅修改的收益有限。建议停止反复打磨，优先开始投递，同时保留后续根据反馈小步迭代的空间。

---

#### 6.2.2 fix_top_3_then_apply

**定义**：先完成最关键的 2-3 个优化项，然后投递。

**对应关系**：通常对应 `apply_readiness=quick_fix_before_apply`

**触发条件**：

1. 岗位与简历方向基本匹配
2. 有明确短板
3. 短板主要是表达问题，不是经历缺失
4. 可在短时间内完成修改

**示例表达**：

> 建议先修复以下 3 个问题后再投递：项目职责不清、结果表达不足、技术栈与 JD 关键词没有对齐。完成后即可投递，不建议继续扩大修改范围。

---

#### 6.2.3 needs_more_evidence

**定义**：当前不是表达问题，而是缺少能支撑岗位要求的经历证据。

**对应关系**：通常对应 `apply_readiness=not_ready_for_this_role` 或 `insufficient_information`

**触发条件**：

1. 简历中没有相关项目 / 实习 / 竞赛 / 论文证据
2. 目标岗位核心能力缺少支撑
3. 单纯改写会造成夸大或不真实
4. 需要用户补充真实经历，而不是让 AI 改写

**示例表达**：

> 当前主要问题不是简历表达，而是缺少能证明岗位核心能力的经历证据。建议先补充真实项目、课程设计、实习或竞赛经历，再进行简历优化。

---

#### 6.2.4 target_role_mismatch

**定义**：当前目标岗位与简历证据差距较大，建议调整目标岗位或重新选择岗位。

**对应关系**：通常对应 `apply_readiness=not_ready_for_this_role`

**触发条件**：

1. 用户经历与目标岗位能力模型明显不一致
2. 岗位核心要求没有可迁移证据
3. 强行投递初筛风险高
4. 存在更适合当前经历的岗位方向

**示例表达**：

> 当前简历与该岗位核心要求差距较大，继续优化这份简历的收益有限。建议优先考虑与现有经历更接近的岗位方向，或在补充相关能力证明后再投递该岗位。

### 6.3 枚举汇总

| 值 | 定义 | 对应 apply_readiness | 投递建议 |
|---|------|---------------------|---------|
| `stop_and_apply` | 停止优化，开始投递 | ready_to_apply | 直接投递 |
| `fix_top_3_then_apply` | 修复 Top 3 后投递 | quick_fix_before_apply | 快速修复后投递 |
| `needs_more_evidence` | 需要补充经历证据 | not_ready_for_this_role / insufficient_information | 补充真实经历 |
| `target_role_mismatch` | 目标岗位方向不匹配 | not_ready_for_this_role | 考虑其他岗位 |

## 7. apply_readiness 与 optimization_stop_signal 映射关系

### 7.1 默认映射

| apply_readiness | → optimization_stop_signal |
|-----------------|---------------------------|
| `ready_to_apply` | → `stop_and_apply` |
| `quick_fix_before_apply` | → `fix_top_3_then_apply` |
| `not_ready_for_this_role` | → `needs_more_evidence` 或 `target_role_mismatch` |
| `insufficient_information` | → `needs_more_evidence` |

### 7.2 映射规则说明

1. `ready_to_apply` 对应 `stop_and_apply`：核心能力已覆盖，建议停止优化并投递
2. `quick_fix_before_apply` 对应 `fix_top_3_then_apply`：有匹配基础但存在可快速修复的问题
3. `not_ready_for_this_role` 对应 `needs_more_evidence` 或 `target_role_mismatch`：
   - 如果差距是经历不足 → `needs_more_evidence`
   - 如果差距是方向不匹配 → `target_role_mismatch`
4. `insufficient_information` 对应 `needs_more_evidence`：信息不足，需要补充经历

### 7.3 禁止矛盾输出

映射不是绝对规则，后续 Agent 可以结合 JD 与简历证据做细分判断。但系统必须避免出现以下矛盾输出：

| 禁止组合 | 原因 |
|---------|------|
| apply_readiness=ready_to_apply + optimization_stop_signal=needs_more_evidence | 已准备好投递但需要更多证据？矛盾 |
| apply_readiness=ready_to_apply + optimization_stop_signal=target_role_mismatch | 已准备好投递但岗位不匹配？矛盾 |
| apply_readiness=quick_fix_before_apply + optimization_stop_signal=stop_and_apply | 有待修复项但建议直接投递？矛盾 |
| apply_readiness=not_ready_for_this_role + optimization_stop_signal=stop_and_apply | 不建议投递但建议停止优化？矛盾 |

## 8. Top 3 快速优化项设计

### 8.1 定义

当 `apply_readiness=quick_fix_before_apply` 时，系统最多只给 3 个投递前快速优化项。

字段名：`top_fix_items`

### 8.2 约束

1. 不要给 10 条建议
2. 不要让用户陷入无限修改
3. 每个优化项必须是投递前可以快速完成的
4. 不应出现 `long_term` 类型作为主要投递前动作

### 8.3 每个优化项结构

| 字段 | 说明 |
|------|------|
| `issue` | 问题描述 |
| `why_it_matters` | 为什么影响初筛 |
| `action` | 怎么改 |
| `example_reference` | 示例参考（不是"建议改为"） |
| `self_check_question` | 自查问题 |
| `estimated_effort` | 预计耗时 |

### 8.4 estimated_effort 枚举

| 值 | 含义 |
|---|------|
| `within_10_min` | 10 分钟内 |
| `within_30_min` | 30 分钟内 |
| `within_60_min` | 60 分钟内 |
| `long_term` | 长期提升（不是投递前必须完成的） |

### 8.5 约束

`quick_fix_before_apply` 状态下，`top_fix_items` 中不应出现 `long_term` 类型作为主要投递前动作。

`long_term` 应该进入 `long_term_improvement`（见第 9 节），而不是阻止用户投递。

### 8.6 示例

```json
{
  "top_fix_items": [
    {
      "issue": "项目职责不够具体",
      "why_it_matters": "HR 初筛时需要快速判断你的实际贡献，笼统的描述容易被跳过",
      "action": "在项目经历中补充你个人负责的模块和具体产出",
      "example_reference": "负责权限模块设计（S），使用 GoFrame 实现 RBAC（A/Tech），上线后权限工单减少 40%（R）",
      "self_check_question": "请确认你是否确实独立负责过该模块，而不是团队整体成果",
      "estimated_effort": "within_30_min"
    },
    {
      "issue": "技术栈与 JD 关键词对齐不足",
      "why_it_matters": "初筛关键词匹配是机器和 HR 的第一步筛选",
      "action": "检查技能栏是否包含 JD 中明确提到的核心技术关键词",
      "example_reference": "如果 JD 要求 Go / MySQL / Redis，确保技能栏和项目描述中出现了这些词",
      "self_check_question": "这些技术你是否确实使用过？如果没有，不要添加",
      "estimated_effort": "within_10_min"
    },
    {
      "issue": "缺少结果或产出表达",
      "why_it_matters": "初筛关注你能做什么、做了什么效果，不只是你参与了什么",
      "action": "为每个项目补充可核实的成果或指标",
      "example_reference": "优化查询接口响应时间从 2s 降至 200ms（R）",
      "self_check_question": "这些数据是否真实？是否是你个人的贡献？",
      "estimated_effort": "within_30_min"
    }
  ]
}
```

## 9. 长期提升项设计

### 9.1 定义

长期提升项可以给，但不能和投递前快速优化混在一起。

字段名：`long_term_improvement`

### 9.2 约束

长期提升项不是当前这次投递必须完成的条件。

### 9.3 示例

```json
{
  "long_term_improvement": [
    {
      "direction": "建议后续补充高并发压测经验",
      "related_jd_requirement": "岗位要求具备高并发系统设计能力",
      "priority": "low",
      "note": "属于长期提升方向，不建议因为这个点延后当前投递"
    },
    {
      "direction": "建议后续参与开源项目",
      "related_jd_requirement": "岗位优先考虑有开源贡献的候选人",
      "priority": "low",
      "note": "属于长期提升方向，不建议因为这个点延后当前投递"
    }
  ]
}
```

### 9.4 固定提醒

长期提升项必须附带以下提醒：

## 10. 投递边界输出语气规范

### 10.1 语气规则

1. 不羞辱用户
2. 不夸大保证
3. 不承诺一定通过初筛
4. 不鼓励造假
5. 不输出"必须这样写"
6. 使用"示例参考"而不是"建议改为"
7. 明确 AI 可能出错，需要用户核实
8. 不做职业规划式长篇延伸
9. 不评价人格、价值观、家庭背景
10. 不替公司做录用承诺

### 10.2 固定提醒

每条匹配分析或优化建议应附带：

> 以下建议仅作为简历表达和投递策略参考，AI 可能理解错误。请基于你的真实经历核实后使用，不要加入没有实际发生过的经历、指标或职责。

## 11. 安全边界与禁止表达

### 11.1 禁止表达

| 禁止 | 原因 |
|------|------|
| 你不适合互联网 | 人格/价值观判断 |
| 你不适合腾讯 | 整体能力否定 |
| 你能力太差 | 人身攻击 |
| 你价值观不符 | 价值观判断 |
| 建议你转行 | 职业规划越界 |
| 你的学校不够好 | 学校歧视 |
| 你必须这样写 | 指令式表达 |
| 优化后一定能过 | 过度承诺 |

### 11.2 禁止基于的判断维度

- 性别
- 年龄
- 家庭背景
- 地域偏见
- 学校歧视
- 人格推断
- 未经用户提供的信息

### 11.3 边界约束

本项目不是职业规划系统。
本项目不是人格判断系统。
本项目不是替用户写虚假简历的工具。
本项目不是官网 Offer鹅 的替代品。

本项目只围绕课题主旨：**帮助学生有效匹配合适岗位；提升对心仪岗位的简历初筛命中率。**

### 11.4 极端场景处理

| 极端场景 | 处理方式 |
|---------|---------|
| 信息不足 | 暂不建议做强推荐，提示补充关键经历 |
| 简历很弱 | 给出投递前最小改进项 |
| 岗位不匹配 | 解释当前岗位初筛风险 |
| 海外 / 地点问题 | 回到岗位地点与候选人意向匹配 |
| 候选人过强 | 建议优先考虑更能发挥经历优势的岗位类型，但不做长期职业规划 |
