> 最后更新：2026-05-29（阶段 3-1 创建阶段 3 核心业务后端 Mock 方案）

## 当前状态

阶段 3 方案已创建，已明确 6 张业务表范围。当前 `server/sql/init.sql` 仍为占位文件。阶段 3-2 将写入真实表结构和种子数据。本次 3-1 不修改 SQL。

## 迁移策略

Demo 阶段不引入复杂迁移工具（如 golang-migrate），采用单 SQL 初始化文件方案。

### 原因

1. Demo 项目数据量小，单 SQL 文件足以管理
2. 便于频繁 `make reset` 后重新导入
3. 降低开发阶段复杂度
4. 集中维护表结构和种子数据
5. 用户会频繁使用 `make up`、`make down`、`make restart`
6. 清空后可通过单 SQL 文件重新导入
7. 对 Demo 和比赛项目更直观

### 约定

1. 后续数据库表结构统一写入 `server/sql/init.sql`
2. 后续种子数据也写入 `server/sql/init.sql`
3. 频繁重建环境时，通过清空 volume 后重新导入该 SQL
4. 阶段 3-2 将写入 6 张业务表结构
5. 阶段 3-2 将写入岗位种子数据、示例用户、示例简历版本
6. 不要在阶段 2 自动导入 SQL

### 数据卷与数据关系

| 命令 | 是否删除数据 | 说明 |
|------|------------|------|
| `make up` | ❌ 不删除 | 启动容器，保留数据 |
| `make down` | ❌ 不删除 | 停止容器，保留数据卷 |
| `make restart` | ❌ 不删除 | 重启容器，保留数据 |
| `make reset` | ✅ 删除 | 清空 volume，需手动确认 |

### 重要约定

1. `make up` / `make down` / `make restart` 不应清空数据
2. `make reset` 才会清空 volume
3. 后续如果要"清空 volume + 重新导入 init.sql"，需要单独设计明确命令
4. 阶段 3-2 才写真实表结构和种子数据

## 迁移文件

```
server/sql/init.sql    # 数据库初始化脚本（阶段 3-2 填写真实表结构）
```

## 使用方式

```bash
# 1. 清空数据卷（危险操作，需手动确认）
docker compose down -v

# 2. 重新启动 MySQL
make up

# 3. 导入初始化脚本
docker compose exec mysql mysql -uroot -ppassword offer_catcher < server/sql/init.sql
```
