## 六、根因判断

**根因：两类独立问题**

### A. 数据乱码（DB 层）

K8-5-48-E 阶段通过 mysql CLI 直接 INSERT 测试简历时，mysql CLI 默认 `character_set_client=latin1`，导致 UTF-8 中文字节被当作 latin1 解释并重新编码为 UTF-8（双重编码）。id=2 和 id=3 的中文字段全部受损。

Go API 创建的 id=4 因 Go 驱动原生使用 UTF-8，数据正确。

### B. 前端源码乱码（MyResumesPage.tsx）

K8-5-48-C 阶段通过 `write_to_file` 重写 MyResumesPage.tsx（约1390行）时，文件内容中的中文文案被错误编码为 mojibake。

其他前端文件（ResumeManagementPage、Navbar、AI 页面）均未被破坏，中文正常。

## 七、推荐修复方案

### 1. DB 数据修复（id=2,3）

最小修复：删除 K8-5-48-E 阶段通过 mysql CLI 写入的乱码行，使用 Go API 重新创建。

```sql
DELETE FROM resumes WHERE id IN (2, 3);
```

然后通过 `curl -X POST /api/resumes` 重新创建（Go API 编码正确）。

### 2. MyResumesPage.tsx 修复

从 git 历史恢复原文件，或手工修复中文文案。文件约 1390 行，mojibake 集中在 JSX 文案标签中。

建议方案：`git show HEAD:web/src/app/pages/MyResumesPage.tsx` 获取 K8-5-48-C 重构前的原文件，然后只更新数据流部分（versionNo→resumeId、save payload→relational DTO），不对中文文案做全量重写。
