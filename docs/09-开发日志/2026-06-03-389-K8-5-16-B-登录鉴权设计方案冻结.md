## 2. K8-5-16-A 核心发现回顾

```text
1. 项目没有 ProtectedRoute / RequireAuth / AuthGuard。
2. routes.tsx 所有页面裸挂载 Component:，无任何 route guard。
3. Navbar 只做显示层鉴权：有 token 显示"我的简历/退出"，无 token 显示"登录"。
4. 用户直接在地址栏输入 /resumes/new 可绕过 Navbar 进入私有页面。
5. /resumes/new 新增模式不请求 API，未登录可完整填写表单，保存才报 401。
6. 后端 /api/resumes 有 401 保护，前端路由层无保护。
7. client.ts：401 清 token + throw，不跳转登录页。
8. viewModels.ts：loadResumeManagementPageViewModel 401→null，页面误判为"无简历"。
```

## 3. 核心设计结论（设计冻结）

```text
1. 新增 RequireAuth 组件，路径：web/src/app/components/auth/RequireAuth.tsx
2. 先保护简历四页面：/resumes /resumes/new /resumes/edit /resumes/compare
3. 未登录访问私有页面 → 跳转 /login?redirect=<当前路径>
4. AI 三页面（/recommend /match /resume-optimization）放到 D 阶段单独处理
5. 本阶段不改 client.ts 的 401 逻辑
6. 使用 element 包裹方式（方案一），最小改动
7. LoginPage/RegisterPage 登录成功后读取 redirect 参数回到原页面
```

## 4. 页面访问权限分级（冻结）

| 页面 | 路由 | 访问级别 | 需要 RequireAuth | 阶段 | 原因 |
|------|------|---------|:---:|:---:|------|
| 岗位列表 | `/jobs` | 公开 | ❌ | — | 公开浏览 |
| 岗位详情 | `/jobs/:id` | 公开 | ❌ | — | 公开浏览 |
| 登录页 | `/login` | 公开 | ❌ | — | 已登录自动跳转 |
| 注册页 | `/register` | 公开 | ❌ | — | 已登录自动跳转 |
| 简历管理 | `/resumes` | **P0 必须登录** | ✅ | **C** | 私有数据 |
| 新建简历 | `/resumes/new` | **P0 必须登录** | ✅ | **C** | 私有数据，当前未登录可完整填表 |
| 编辑简历 | `/resumes/edit` | **P0 必须登录** | ✅ | **C** | 私有数据 |
| 简历对比 | `/resumes/compare` | **P0 必须登录** | ✅ | **C** | 私有数据 |
| 岗位推荐 | `/recommend` | **P1 建议登录** | ✅ | **D** | 依赖简历 API，需先处理复杂状态 |
| 岗位匹配 | `/match` | **P1 建议登录** | ✅ | **D** | 同上 |
| 简历优化 | `/resume-optimization` | **P1 建议登录** | ✅ | **D** | 同上 |

### AI 三页面为何不放入 C 阶段

AI 三页面（`/recommend` `/match` `/resume-optimization`）都依赖简历数据，从逻辑上应保护。但：

1. 三页面内有 `SelectResumeModal`、`AIProgressState`、`PageError/retry` 等多种复杂状态
2. 三页面通过 URL query params（`resumeId`/`jobId`/`resumeVersionNo`）传递上下文
3. 先做简历四页面保护形成可复用模式，再扩展到 AI 页面
4. C 阶段聚焦最小风险改动，交付后再决策 AI 页面策略

**决策**：C 阶段只保护简历四页面，AI 三页面在 D 阶段单独处理。

## 5. RequireAuth 组件设计（冻结）

### 5.1 位置

```
web/src/app/components/auth/RequireAuth.tsx
```

放在 `auth/` 目录下，与 `AuthDialog.tsx` 同级，语义上同属鉴权模块。

### 5.2 API 签名

```tsx
import React from "react";
import { Navigate, useLocation } from "react-router";
import { getAuthToken } from "../../../api/authStorage";

export type RequireAuthProps = {
  children: React.ReactNode;
};

export function RequireAuth({ children }: RequireAuthProps) {
  const location = useLocation();
  const token = getAuthToken();

  if (!token) {
    const redirect = encodeURIComponent(location.pathname + location.search);
    return <Navigate to={`/login?redirect=${redirect}`} replace />;
  }

  return <>{children}</>;
}
```

### 5.3 设计决策

| 项目 | 冻结方案 | 原因 |
|------|---------|------|
| 是否使用 Navigate | ✅ 是 | 纯路由跳转，刷新安全 |
| 是否带 redirect 参数 | ✅ 是 | 登录后回到原页面 |
| 是否使用 AuthDialog | ❌ 否 | AuthDialog 绑定 Navbar state，不宜复用 |
| 是否需要 loading | ❌ 否 | `getAuthToken()` 同步读取 localStorage，无异步逻辑 |
| token 过期处理 | 暂不处理 | token 过期由后端 401 驱动，属于 E 阶段优化 |
| children 类型 | `React.ReactNode` | 最通用 |

### 5.4 为什么不用 AuthDialog

| 因素 | 分析 |
|------|------|
| AuthDialog 位置 | 在 Navbar 组件内部渲染，state 由 Navbar 管理 |
| open/onOpenChange | Navbar 自己持有 `authDialogOpen` state |
| onLoginSuccess | Navbar 调用 `setIsLoggedIn(Boolean(getAuthToken()))` |
| 职责耦合 | AuthDialog 不懂路由，RequireAuth 不懂弹窗 |
| 成本 | 提取到全局需 refactor Navbar + 新增 context，风险高于收益 |

**结论**：用 `/login?redirect=` 方案，路由清晰、实现简单、刷新安全。

## 6. 未登录处理方式：方案比较与结论

| 方案 | 行为 | 优点 | 风险 | 推荐 |
|------|-----|------|------|:---:|
| **A** | 跳转 `/login?redirect=当前路径` | 简单、路由清晰、刷新安全、LoginPage 已存在 | 不是弹窗体验（但用户感知可接受） | ✅ **推荐** |
| B | 在私有页面直接打开 AuthDialog | 弹窗体验现代 | 需全局化 AuthDialog state / 新增 context、Navbar 需配合、刷新后弹窗状态丢失 | ❌ 不推荐 |

**冻结决策：方案 A — 跳转 `/login?redirect=当前路径`**

## 7. Redirect 设计（冻结）

### 7.1 规则

| 项目 | 规则 |
|------|------|
| 参数名 | `redirect` |
| 编码 | `encodeURIComponent(location.pathname + location.search)` |
| 校验 | 只允许以 `/` 开头的站内路径 |
| 非法 redirect | 回到 `/jobs`（默认首页） |
| 空白 redirect | 回到 `/jobs` |
| 外部 URL | 不允许，回到 `/jobs` |

### 7.2 安全约束（防开放重定向）

```text
redirect 只允许以 "/" 开头。
不包含 "//"（协议相对）。
不包含 "@"（用户信息注入）。
不含外部域名（如 http://evil.com）。
```

### 7.3 LoginPage 改动计划（C 阶段执行）

LoginPage 当前：

```tsx
navigate("/"); // 登录成功直接回首页
```

C 阶段改为：

```tsx
const redirect = new URLSearchParams(location.search).get("redirect");
const safeRedirect = redirect && redirect.startsWith("/") && !redirect.includes("//") ? redirect : "/jobs";
navigate(safeRedirect);
```

### 7.4 RegisterPage 改动计划（C 阶段执行）

RegisterPage 当前：

```tsx
navigate("/"); // 注册成功直接回首页
```

C 阶段同样支持 redirect。

### 7.5 AuthDialog 是否支持 redirect

**C 阶段不支持。** AuthDialog 是 Navbar 内的弹窗体验，登录成功后的回调是 `onLoginSuccess()`，不涉及路由跳转。E 阶段可选优化。

## 8. routes.tsx 包裹方式（冻结）

### 方案比较

| 方案 | 写法 | 优点 | 缺点 | 推荐 |
|------|-----|------|------|:---:|
| **一** | 每个路由单独 element 包裹 | 最小改动、影响面可控 | 四路由重复包裹 | ✅ **推荐（C 阶段）** |
| 二 | RequireAuthLayout 嵌套子路由 | 统一管理、扩展方便 | 改动路由结构大、需重排路由分组 | 备选（如需要可后续迁移） |

### 方案一具体写法（C 阶段执行）

```tsx
import { RequireAuth } from "./components/auth/RequireAuth";

// 在 routes.tsx 中
{
  path: "resumes",
  element: <RequireAuth><ResumeManagementPage /></RequireAuth>,
},
{
  path: "resumes/new",
  element: <RequireAuth><MyResumesPage /></RequireAuth>,
},
{
  path: "resumes/edit",
  element: <RequireAuth><MyResumesPage /></RequireAuth>,
},
{
  path: "resumes/compare",
  element: <RequireAuth><ResumeComparisonPage /></RequireAuth>,
},
```

### 冻结决策

```text
C 阶段用方案一（单路由 element 包裹 4 个简历页面），最小改动。
后续如果私有页面增多（大于 6 个），再抽 RequireAuthLayout 统一管理。
```

## 9. 401 兜底策略（冻结）

### 9.1 当前状态

`client.ts` 收到 401 → `clearAuthToken()` + throw `ApiClientError`，不跳转登录页。

### 9.2 策略

| 场景 | C 阶段策略 | 后续阶段 |
|------|----------|---------|
| 未登录访问页面 | RequireAuth 拦截 → 跳转 /login | C：完成 |
| 已登录但 token 过期（挂载时 401） | 页面显示 PageError + retry | D/E：可改跳登录 |
| 已登录但 token 过期（操作时 401） | client.ts clearAuthToken + 页面显示错误提示 | E：统一 401 redirect |
| 已登录主动退出 | Navbar handleLogout → clearAuthToken + navigate("/") | 已就绪 |

### 冻结决策

```text
C 阶段不改 client.ts。
路由 guard 解决"未登录直接进入"。
token 过期问题由 E 阶段统一处理。
```
