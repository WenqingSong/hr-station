## 4. 兜底链路设计

总体链路：业务请求 → 组装上下文 → 选择 Prompt → 选择 Schema → 判断 LLM 启用 → 调用 LLM → JSON parse → Schema validate → 如果失败调用 JSONRepairAgent 一次 → 如果仍失败回退 Mock Agent → 返回稳定结果

核心约束：
- JSON repair 只尝试一次
- Repair 失败后不继续递归修复
- 不允许无限重试

## 5. 失败场景分类

设计了 20 种错误码，覆盖：
- LLM 配置层：LLM_DISABLED / LLM_CONFIG_MISSING / LLM_API_KEY_MISSING
- LLM 调用层：LLM_TIMEOUT / LLM_HTTP_ERROR / LLM_RATE_LIMIT / LLM_EMPTY_RESPONSE / LLM_CONTEXT_TOO_LONG / LLM_OUTPUT_TRUNCATED
- JSON 解析层：JSON_PARSE_FAILED / JSON_MARKDOWN_WRAPPED
- Schema 校验层：SCHEMA_VALIDATION_FAILED / SCHEMA_REQUIRED_FIELD_MISSING / SCHEMA_ENUM_INVALID / SCHEMA_TYPE_INVALID / SCHEMA_ADDITIONAL_PROPERTY
- JSON repair 层：JSON_REPAIR_FAILED / JSON_REPAIR_SCHEMA_FAILED
- 业务安全层：BUSINESS_SAFETY_RISK
- 未知异常：UNKNOWN_ERROR

核心决策：
- LLM 未启用/配置缺失/超时/HTTP 错误/限流/空响应：直接 Mock
- JSON parse 或 Schema validate 失败：先 repair 一次
- repair 仍失败：Mock
- 业务安全风险：Mock 或安全降级

## 6. JSON Repair 策略

- JSONRepairAgent 只修复结构，不重新做业务分析
- JSONRepairAgent 只执行一次
- repair 成功后 generated_by 仍保持 llm_agent
- repair 失败后进入 Mock fallback
- JSONRepairAgent 不编造岗位、经历、项目指标、系统规模、职责范围

## 7. Mock 回退策略

- Mock Agent 是最终兜底，不是低质量替代
- MatchAnalysisAgent fallback：使用 match_mock.go
- RecommendationAgent fallback：使用 recommendation_mock.go
- ResumeOptimizationAgent fallback：后续实现时需要补齐确定性 Mock
- Mock fallback 不请求外部接口，不调用 Hunyuan

## 8. 标记与日志策略

- generated_by 只有两种值：llm_agent（LLM 正常或 repair 成功）、mock_agent（Mock 兜底）
- 不使用 llm_agent_fallback 作为 generated_by 值
- fallback 状态由外层 agent_status / fallback_reason 表达
- 日志字段：request_id / agent_name / target_output_type / llm_enabled / llm_model / prompt_version / schema_version / call_started_at / call_duration_ms / raw_output_length / json_parse_success / schema_validate_success / repair_attempted / repair_success / fallback_used / fallback_reason / error_code
- 日志不记录 API Key、完整简历、完整 JD、完整模型输出
