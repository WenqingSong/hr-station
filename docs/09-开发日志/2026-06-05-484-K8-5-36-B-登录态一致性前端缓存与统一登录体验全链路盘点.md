## 三、前端登录态来源分析

### 3.1 Token 存储

| 项 | 值 |
|----|-----|
| Token 存储 key | `offer_catcher_auth_token` |
| 存储位置 | `localStorage`（`web/src/api/authStorage.ts`） |
| 存储方式 | 单 key，不存 user 对象 |
| SSR 安全 | ✅ 检查 `typeof window` |

核心 API：
```typescript
// web/src/api/authStorage.ts
const AUTH_TOKEN_KEY = "offer_catcher_auth_token";
export function getAuthToken(): string | null { /* 读 localStorage */ }
export function setAuthToken(token: string): void { /* 写 localStorage */ }
export function clearAuthToken(): void { /* 删 localStorage */ }
```

### 3.2 登录态判断 — 三套来源对比

| 位置 | 登录态来源 | 校验方式 | 问题 |
|------|-----------|---------|------|
| **Navbar** | `localStorage` token | `!!getAuthToken()`（同步读） | 从不调用 `/auth/me` 校验 token 是否仍有效 |
| **AIDecisionWorkspace**（首页右侧 AI） | `localStorage` token | `useState(() => !!getAuthToken())` 初始化一次 | 仅初始化一次；401 后 `isLoggedIn` 仍为 `true`（不刷新） |
| **RequireAuth** | `localStorage` token | `getAuthToken()` 同步读 | 也只检查 localStorage，不校验 token 有效性 |
| **client.ts**（API 层） | `localStorage` token | 自动注入 `Authorization: Bearer <token>` | 401 时调 `clearAuthToken()`，但**不通知 React 组件**重新读取 |
| **各页面**（ResumeManagementPage等） | API 调用的 401 响应 | `getAuthRedirectIf401()` → redirect | 401 后跳转到 `/?auth=login&redirect=...` |

### 3.3 authStore / 全局状态管理

**不存在。** 项目没有任何状态管理库（无 Zustand、无 Pinia、无 Context）。所有登录态判断各自为政。

| `onLoginSuccess` 后调用 `setIsLoggedIn(!!getAuthToken())` | ✅ | 登录成功后会刷新，这是正确的 |

| 状态 | 条件 | 展示内容 |
|------|------|---------|

| 已登录无简历 | `isLoggedIn && !loading && !resumeVm` | "完善简历后开始智能推荐" |
| 已登录有简历 | `isLoggedIn && !loading && resumeVm` | 当前简历卡片 + "推荐适合的岗位" |

## 六、后端登录态机制

### 6.1 JWT + Redis Session 双校验

```
登录 → 生成 sessionID → 写入 Redis (key: auth:session:{userID}:{sessionID})
     → 将 sessionID 写入 JWT claims → 返回 JWT token

请求 → AuthMiddleware → ParseToken (JWT 验签) → ValidateSession (Redis 查询)
     → 两步都通过 → 注入 userID / sessionID 到 context
```

| 检查项 | 结果 |
|--------|------|
| JWT 是否只验签 | ❌ 不只验签，还校验 Redis Session |
| Redis Session 重启后旧 token 是否失效 | ✅ 会失效（Redis 数据丢失，但 JWT 签名仍有效） |
| `/api/auth/me` 是否存在 | ✅ `GET /api/auth/me`（需认证） |
| `/api/auth/logout` 是否存在 | ✅ `POST /api/auth/logout`（销毁 Redis session） |
| 401 返回格式 | `{"code":40100,"message":"unauthorized","data":null}` |

### 6.2 Redis 重启影响

```
CNB 环境重启 → Docker Compose 重启 → Redis 容器重启
  → 如果 volume 保留：Redis session 存活 ✅
  → 如果 reset-up（清 volume）：Redis session 丢失 ❌
  → localStorage token 始终在浏览器中 ❌
  → 前端根据 localStorage token 显示已登录 ❌
  → API 调用时 Redis session 不存在 → 401 ❌
```

## 七、401 处理全链路

### 7.1 API client 层（client.ts）

```typescript
// web/src/api/client.ts:112-116
if (response.status === 401) {
  clearAuthToken();  // 清除 localStorage
}
throw new ApiClientError(...);  // 向上抛出错误
```

- ✅ 清除 localStorage token
- ❌ **不通知任何 React 组件**（无 event、无 callback、无 store）
- ❌ **不做页面跳转**（跳转由各页面自己处理）

### 7.2 页面层 401 处理

各受保护页面（ResumeManagementPage、MyResumesPage、ResumeComparisonPage、JobRecommendationPage 等）在 catch 块中处理 401：

```typescript
// 例如 ResumeManagementPage.tsx:290-296
.catch((err: unknown) => {
  if (isApiClientError(err) && err.status === 401) {
    const redirect = getAuthRedirectIf401(err, location.pathname, location.search);
    if (redirect) { navigate(redirect, { replace: true }); return; }
  }
  setError(true);
})
```

- ✅ `getAuthRedirectIf401` 返回 `/?auth=login&redirect=<当前路径>`
- ✅ 页面跳转到首页 + 自动打开 AuthDialog
- ⚠️ **但 Navbar 和 AIDecisionWorkspace 不会立即感知变化**

### 7.3 401 处理存在页面级差异

| 页面 | 401 处理 | 静默吞 401 |
|------|---------|:---:|
| ResumeManagementPage | redirect ✅ | ❌ |
| MyResumesPage | redirect ✅ | ❌ |
| ResumeComparisonPage | redirect ✅ | ❌ |
| JobRecommendationPage | redirect ✅ | ❌ |
| ResumeOptimizationPage | redirect ✅ | ❌ |
| **AIDecisionWorkspace** | **`catch(() => setResumeVm(null))`** | ⚠️ **YES** |

### 10.1 请求链路

```
浏览器 → http://localhost:8080
       → Nginx (Docker, :80→host:80, 由 docker-compose 映射到 8080)
       → location / → proxy_pass http://host.docker.internal:5173 (Vite)
       → location /api/ → proxy_pass http://host.docker.internal:8080 (Go Server)
```

| 项 | 结果 |
|----|------|
| localhost:8080 页面由谁提供 | Nginx 代理 Vite dev server (5173) |
| 哪个代理 Vite | Nginx（非 Go Server 的 ReverseProxy） |
| Vite 停止后浏览器状态 | Nginx 返回 502 Bad Gateway |
| CNB 重启后如何恢复 | `make up` → Docker Compose (MySQL/Nginx/Redis) + 本地 Go 服务 + Vite |

### 10.2 重启风险

| 操作 | localStorage | Redis Session | 影响 |
|------|:---:|:---:|------|
| `make restart` | 保留 | 保留 | 无影响 |

| Vite 单独重启 | 保留 | 保留 | Vite 重编译期间 Nginx 502 |
| 浏览器 Ctrl+F5 | 保留 | 保留 | 页面重新加载，前端读旧 token → 可能假登录 |
| 浏览器清缓存 | **丢失** | 保留 | 正常状态 |

### 10.3 Vite / 前端缓存风险

| 风险 | 说明 |
|------|------|

## 十一、根因判断

### 核心问题：为什么 Navbar 像已登录，页面卡片又要求登录？

**根因组合：C + A + G + D**

```
过程还原：

1. CNB 环境执行 make reset-up（清空 Redis volume）
   → Redis session 全部丢失
   → 浏览器中 localStorage token 仍然存在

2. 用户访问 http://localhost:8080/?auth=login&redirect=%2Fresumes
   → Navbar mount → getAuthToken() 返回旧 token → isLoggedIn=true
   → 显示 "我的简历 / 退出" ✅ 但 token 已失效

3. Navbar 同时检测到 ?auth=login → 打开 AuthDialog
   → 用户看到 "我的简历/退出" 的同时看到登录弹窗
   （如果用户关闭了弹窗但没登录）

4. AIDecisionWorkspace mount → getAuthToken() 返回旧 token → isLoggedIn=true
   → 触发 API 调用 → /api/resumes/current → 401（Redis session 不存在）
   → client.ts clearAuthToken() → localStorage 清空
   → 但 AIDecisionWorkspace 的 isLoggedIn 仍然是 true
   → resumeVm = null → 显示 "完善简历后开始智能推荐"（状态 B）

5. 或者：AIDecisionWorkspace 在某个时序下 isLoggedIn 已经是 false
   （如页面重载时 localStorage 已被之前的 401 清空）
   → 但 Navbar 的 isLoggedIn 也应该是 false...
   
   另一个可能：用户先看到了 AuthDialog（未登录），关闭了弹窗，
   → 此时 Navbar 重新渲染（location 可能不变）
   → 但 AIDecisionWorkspace 不会重新初始化 isLoggedIn
```

**最可能的用户场景**：

| 步骤 | 组件 | 状态 |
|------|------|------|
| 1 | 页面加载 | localStorage 有旧 token（Redis 已清） |
| 2 | Navbar | 读 localStorage → isLoggedIn=true → 显示"我的简历/退出" |
| 3 | Navbar | 检测到 ?auth=login → 打开 AuthDialog 弹窗 |
| 4 | AIDecisionWorkspace | 也读到 localStorage → isLoggedIn=true |
| 5 | AIDecisionWorkspace | API 调用 → 401 → client.ts 清 localStorage |
| 6 | 用户 | 看到重叠：Navbar 显示"已登录"，但右边可能显示不同状态 |

### 七个可能原因逐一判定

| 原因 | 是否命中 | 说明 |
|------|:---:|------|
| **A**. Navbar 只看 localStorage token | ✅ **命中** | 第 22 行：`setIsLoggedIn(!!getAuthToken())`，无 `/auth/me` 校验 |
| **B**. AI 卡片看 API currentResume | ⚠️ **部分** | 先看 localStorage 初始化，再通过 API 调 currentResume |
| **C**. Redis 重启导致旧 token 失效 | ✅ **命中** | Redis session 丢失但 JWT 签名有效，localStorage 仍存旧 token |
| **D**. 401 没全局清理 | ✅ **命中** | `client.ts` 清 localStorage 但组件不感知 |
| **E**. Vite/CNB 重启状态不同步 | ✅ **命中** | `make reset-up` 清 Redis → 浏览器 localStorage 不动 |
| **F**. URL auth 参数未清理 | ❌ **不命中** | K8-5-36-A 已修复 |
| **G**. 页面组件不同 auth source | ✅ **命中** | Navbar 和 AIDecisionWorkspace 各自独立判断，无全局 store |

## 十三、推荐修复方案

### 方案对比

| 方案 | 做法 | 优点 | 风险 | 推荐 |
|------|------|------|------|:---:|
| **A** | Navbar 和页面都只看 localStorage token | 简单 | 容易假登录（Redis session 丢失但 token 在） | ❌ |
| **B** | App 启动时 auth bootstrap，token 存在就调用 `/auth/me` 校验，失败清 token | 专业稳定 | 需要 authStore/Context 改造 | ✅ **推荐** |
| **C** | 不做 `/auth/me`，只在每次 401 时清 token + Navbar 监听变化 | 中等 | 初始仍可能短暂假登录 | ⚠️ |

### 推荐：方案 B（最小但专业）

**核心思路**：

1. **创建 AuthContext**：作为全局登录态单一来源
2. **App 启动时 auth bootstrap**：
   - 检查 localStorage 是否有 token
   - 有 → 调用 `/api/auth/me` 校验
   - 成功 → 设置 authState = authenticated + user info
   - 失败（401等）→ clearAuthToken() + authState = unauthenticated
3. **Navbar / AIDecisionWorkspace / 所有组件**统一从 AuthContext 读登录态
4. **client.ts 401** 改为 dispatch authState 更新（通过 AuthContext）
5. **AIDecisionWorkspace** 不再自行管理 isLoggedIn

**不需要新增后端接口**：`/api/auth/me` 已存在且可用（已验证）。
