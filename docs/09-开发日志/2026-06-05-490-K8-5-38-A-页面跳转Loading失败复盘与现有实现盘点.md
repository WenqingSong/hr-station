## 七、当前交互场景还原

用户从 `/jobs` 点击跳转到 `/resumes` 时，时间线如下：

```
T=0ms：    用户点击，新旧路由切换
            → RouteProgressBar 启动（0→70%→100%）
            → 旧页面内容仍在 DOM 中

T=90ms：   PageTransitionOverlay 显示
            → bg-slate-50/70 + blur 覆盖 main 区
            → 中央白色胶囊出现
            → 底部新页面 skeleton/PageLoading 已开始渲染
            → 用户看到：遮罩 + 旧内容残影 + 新 skeleton

T=180ms：  RouteProgressBar 到达 100%

T=350ms：  PageTransitionOverlay 消失
            → 页面露出新内容（可能仍有 local skeleton）
            → 如果接口返回慢，skeleton 或 PageLoading 继续

T=380ms：  RouteProgressBar 完全消失
```

**用户主观体验**：
1. 点击后，90ms 内页面不动 → 瞬间模糊 → 中央胶囊弹出 → 像"系统卡住"
2. 遮罩+旧内容残影+新 skeleton → 杂乱叠加
3. 顶部蓝条 + 中央胶囊 + 底部骨架 → 3 层视觉噪声同时发生

## 八、失败原因判断

### 根因分析

| 问题 | 类别 | 判断 |
|------|------|------|
| 遮罩覆盖旧页面让用户感觉"系统卡住" | **C（设计模型不适合）** | Overlay 适合"模态操作"或"系统级阻塞"，不适合普通页面跳转 |
| 遮罩 + 旧残影 + 新 skeleton 三层叠加 | **E（和 skeleton 冲突）** | 每个页面已有 skeleton，overlay 叠在上面是多余层 |
| 顶部蓝条 + 中央胶囊 + 底部骨架同时出现 | **视觉重复** | 用户看到三种不同的 loading 信号，认知负荷过高 |
| location-change 触发，不反映真实数据加载 | **D（触发时机不真实）** | 90ms 后一定弹出，不管接口有没有返回 |
| 中央白色胶囊突兀 | **C（模型不适合）** | 它打断了页面切换的自然过渡，像弹窗而不是过渡 |
| 遮罩仍有色和 blur | **A（视觉参数问题，次要）** | 即使降到 70%/1px，仍然有"雾感" |

### 最终判断

**核心失败原因是 C（overlay 设计模型本身不适合普通页面跳转）+ E（与页面 skeleton 冲突）。**

具体论证：

```
1. Overlay 适合的场景：
   - 模态弹窗的遮罩背景
   - 系统级阻塞（如付款中、文件处理中）
   - 需要阻止用户操作的全局等待
   - React Router Data Router 的 useNavigation().state==="loading"（真实 pending）

2. 不适合的场景：
   - 普通页面跳转（SPA 路由切换）
   - 页面自身已经有 skeleton 的情况
   - 数据加载速度无法预测的情况

3. Offerr鹅 当前场景：
   - 每个页面都有骨架屏或 PageLoading
   - 没有 Data Router，无法获取真实 pending 状态
   - Overlay 与 skeleton 必然叠加
   - 固定的 90/260ms 纯粹是"演戏"，不反映真实加载
```

**专业 SaaS 网页中，普通页面跳转更常用的是：顶部进度条（如 GitHub/Linear/Notion）+ 页面内容自然过渡，而非居中遮罩弹层。**

## 九、方案比较

| 方案 | 做法 | 优点 | 风险 | 推荐 |
|------|------|------|------|:--:|
| **A** | 继续微调 PageTransitionOverlay 参数 | 改动小 | 大方向已证失败，微调治标不治本 | ❌ |
| **B** | 取消中央 overlay，只保留顶部 RouteProgressBar + 页面内容淡入 | 专业、克制、零冲突 | 需移除 overlay，淡入效果需实现 | ✅ **强烈推荐** |
| **C** | 只在 Auth Bootstrap / 首屏加载用全屏 loading，普通页面跳转不用 overlay | 职责清晰 | 页面跳转反馈较弱 | ⚠️ 可结合 B |
| **D** | 不做路由 loading，只保留页面自身 skeleton | 最简单 | 切换反馈不足，用户不知道是否在跳转 | ❌ |
| **E** | React Router Data Router + useNavigation 真实 pending | 最准确 | 工程改动大（需改造整个路由体系），不适合当前阶段 | ❌（远期可考虑） |

### 推荐：方案 B

```
1. 移除 PageTransitionOverlay（`routes.tsx` 中删除导入和渲染）。
2. 保留 RouteProgressBar 作为普通页面跳转唯一全局反馈。
3. 页面自身 skeleton / PageLoading 管好自己的数据加载。
4. 如果希望更丝滑，可以在 page-level 组件添加简单 fade-in：
   - opacity: 0→1，duration: 100-150ms
   - 让新页面"缓出一瞬"而不是"突然出现"
5. AppBootLoading 不变（应用启动）。
6. AIThinkingLoading 不变（AI 生成中）。
```

## 十一、为什么方案 B 更好

### 1. 专业参照

```
GitHub：      顶部细进度条（NProgress 风格），无遮罩
Linear：      顶部进度条，内容淡入
Notion：      顶部细线 loading，无遮罩
Stripe：      顶部进度条，无遮罩
Vercel：      顶部进度条，页面内容淡入
```

没有主流 SaaS 在普通页面跳转时使用"居中遮罩加载胶囊"。

### 2. 视觉噪声

| 当前 | 方案 B |
|------|--------|
| 顶部蓝条 + 中央胶囊 + 底部骨架（3 层） | 顶部蓝条 + 自然骨架（2 层） |
| 遮罩掩盖旧内容但残影 | 无遮罩，Router 直接切换 |
| 用户感觉"被挡住了" | 用户感觉"在过渡" |

### 3. 认知模型

```
当前模型：阻塞型 → "系统正在处理，请等待" → 焦虑感
方案 B 模型：过渡型 → "新页面正在显示" → 期待感
```
