# K7-3：双模型渐进式生成策略重设计冻结

- **日期**：2026-06-03
- **阶段**：K7-3（design freeze, pass）
- **前置**：K7-2（双模型配置与路由完整实现）
- **性质**：read-only design + docs。**零代码修改。**

## 1. 背景

### 1.1 前序阶段回顾

| 阶段 | 结论 |
|------|------|
| K6-5 | flash 主模型（85 分），pro 高质量（76 分） |
| K6-6 | flash 接入完成；Core + Compare LLM success |
| K7-1 | 双模型分层策略设计冻结 |
| K7-2 | 双模型配置 + 路由代码实现（fastRunner / qualityRunner） |

### 1.2 旧设计跑偏点

K7-1 / K7-2 的设计是：

```
功能级固定模型路由：
  岗位推荐     → fastRunner（flash）
  岗位匹配分析 → qualityRunner（pro）
  简历优化     → qualityRunner（pro）
  版本对比     → qualityRunner（pro）
```

**这个设计的根本问题**：把一个功能永久绑定在一个模型上。用户无法在同一个功能内获得"快速预览"和"深度分析"两种体验。

### 1.3 K7-3 如何纠偏

从：

```
按功能分模型（固定路由）
```

纠正为：

```
按同一功能内的内容层级分模型（请求级路由）
```

新的核心原则：

```
每个核心功能都支持两层结果：
  - Fast Result：默认、快速、先展示
  - Quality Result：按需、深度、用户点击后生成
```

## 2. 新设计目标

1. 每个核心功能默认走 Fast（flash），快速出结果
2. 用户点击"高质量分析/深度对比"后，走 Quality（pro），生成深度结果
3. 保留 K7-2 已实现的 `fastRunner` / `qualityRunner` 底层能力
4. 新增强求参数 `generation_tier` 控制模型选择
5. 不破坏旧接口兼容性

## 3. 四主功能保障声明

无论后续如何改模型策略，以下四个核心功能**全部保留**、**全部可实现**：

| # | 核心功能 | 业务目标 |
|---|----------|----------|
| 1 | 简历版本对比 | 比较不同简历版本的变化、提升点和风险点 |
| 2 | 岗位智能推荐 | 基于当前简历推荐更适合投递的岗位 |
| 3 | 岗位匹配分析 | 分析当前简历与当前岗位 JD 的匹配度 |
| 4 | 简历优化建议 | 针对目标岗位给出可执行的简历修改建议 |

渐进式生成策略强化（而非削弱）这四项功能：用户既能快速看到结果，又能按需获得深度分析。

## 4. 模型层级定义

| 层级 | 模型名 | 定位 | 触发方式 |
|------|--------|------|----------|
| **Fast** | `deepseek-v4-flash` | 快速响应、初筛、摘要、粗粒度评分、低成本 | **默认**（请求提交即触发） |
| **Quality** | `deepseek-v4-pro-202606` | 深度分析、证据链、真实性约束、高质量输出 | **按需**（用户点击高质量按钮后触发） |
| **Fallback** | Mock Agent | 任何层级 LLM 失败时兜底 | 自动 |

## 5. 四主功能 Fast / Quality 返回内容表

### 5.1 简历版本对比

| 层级 | 应包含内容 | 目标 |
|------|-----------|------|
| **Fast** | 总体结论、变化摘要、主要提升点概览、主要风险点概览、初步建议、是否值得使用新版、简短评分 | 让用户快速知道：新版是否更好，主要变化 |
| **Quality** | 分模块对比、旧版→新版变化证据、每个变化为什么更好/更差、提升点深度分析、风险点深度分析、真实性/过度包装风险、ATS/初筛影响、下一版修改计划、面试追问风险 | 让用户明确知道：哪里真的变强，哪里仍有风险，下一版怎么改 |

### 5.2 岗位智能推荐

| 层级 | 应包含内容 | 目标 |
|------|-----------|------|
| **Fast** | 推荐岗位列表、初步匹配分、推荐理由、岗位方向标签、投递优先级、简单风险标签、快速建议 | 让用户快速知道：我现在适合投哪些岗位 |
| **Quality** | 每个岗位详细匹配解释、简历证据如何支撑推荐、岗位优先级排序理由、竞争风险分析、简历补强建议、投递策略、主攻/备选/冲刺岗位组合、不推荐岗位原因 | 让用户知道：为什么这些最适合我，该按什么顺序投 |

### 5.3 岗位匹配分析

| 层级 | 应包含内容 | 目标 |
|------|-----------|------|
| **Fast** | 总匹配分、匹配结论、已匹配能力点、缺失能力点、初步风险、快速补强建议、是否建议投递 | 让用户快速判断：这个岗位值不值得投 |
| **Quality** | JD 要求拆解、简历证据映射、维度评分、优势证据、短板原因、风险优先级、补强路径、简历修改建议、面试追问风险、最终投递建议 | 让用户知道：我和 JD 到底差在哪，怎么提高初筛命中率 |

### 5.4 简历优化建议

**项目最核心的高价值功能，必须强调真实性约束。**

| 层级 | 应包含内容 | 目标 |
|------|-----------|------|
| **Fast** | 优化摘要、Top Fix Items、关键词缺口、快速行动建议、投递准备度、是否需要用户补充信息、stop signal | 让用户马上知道：这份简历最该先改哪里 |
| **Quality** | 逐条修改建议（含 issue / why_it_matters / action / example_reference / self_check_question）、原文→优化后示例、真实性检查、JD 证据链、长期补强建议、最终投递检查清单、面试追问风险、用户需确认的信息、不允许虚构的边界 | 让用户拿到可直接执行、可解释、不过度包装的方案 |

#### 5.4.1 Optimization Core 新定位

旧定位（K7-1/K7-2）：Optimization Core 固定绑定 qualityRunner（pro）。

**新定位**：

```
Optimization Core = 简历优化建议的一条业务链路（mode=core）。
它不再固定绑定 qualityRunner。
而是：
  - 标准优化 fast  → 快速优化建议
  - 标准优化 quality → 高质量优化建议
  - Core fast  → 快速 Core 建议（2-3 条关键项）
  - Core quality → 高质量 Core 建议 + 证据链 + 真实性约束
```

## 6. 接口参数设计

### 6.1 新增 `generation_tier`

```json
{
  "generation_tier": "fast"
}
```

| 字段 | 类型 | 可选值 | 默认 | 语义 |
|------|------|--------|------|------|
| `generation_tier` | string | `"fast"`, `"quality"` | `"fast"` | 控制模型质量层级 |

### 6.2 映射关系

| generation_tier | 模型 | K7-2 Runner |
|-----------------|------|-------------|
| `"fast"` | `deepseek-v4-flash` | `fastRunner` |
| `"quality"` | `deepseek-v4-pro-202606` | `qualityRunner` |

### 6.3 与 `mode` 的关系

| 参数 | 作用 | 示例 |
|------|------|------|
| `mode` | 控制**业务链路**（standard / core） | `"mode": "core"` |
| `generation_tier` | 控制**模型质量层级**（fast / quality） | `"generation_tier": "quality"` |

两者正交，互不干扰：

```json
// 标准优化 + Quality Model
{"mode": 省略/不传, "generation_tier": "quality"}

// Core 优化 + Quality Model
{"mode": "core", "generation_tier": "quality"}

// 标准优化 + Fast Model（默认）
{"mode": 省略/不传}   // generation_tier 默认 fast
```

### 6.4 兼容规则

```
1. 不传 generation_tier → 默认 "fast"
2. 旧接口（无此字段）→ 自动走 fast → 不破坏旧行为
3. 简历优化已有 mode:"core" → 与 generation_tier 独立
4. 后端 K7-2 实现的 fastRunner/qualityRunner 保留 → 只需改调度逻辑
```

## 7. 前端交互设计

### 7.1 统一交互模式

```
1. 用户提交输入（提交按钮）
2. 后端默认 generation_tier=fast
3. 前端立刻展示 Fast 快速结果
4. Fast 结果区域下方出现按钮：
   - 「生成高质量分析」
   - 「深度匹配分析」
   - 「高质量优化」
   - 「生成深度版本对比」
5. 用户点击按钮
6. 后端 generation_tier=quality
7. 前端展示 Quality 结果（替换或追加到 Fast 结果下方）
```

### 7.2 各功能按钮文案

| 功能 | 高质量按钮文案 |
|------|-------------|
| 简历版本对比 | 生成深度版本对比 |
| 岗位智能推荐 | 生成高质量推荐分析 |
| 岗位匹配分析 | 生成深度匹配分析 |
| 简历优化建议 | 生成高质量优化建议 |
| Optimization Core | 生成 Core 高质量优化 |

### 7.3 前端展示原则

```
先有结果，再增强质量。
```

- 不要让用户首次提交就等 pro 的长时间响应
- Fast 结果先渲染，Quality 按钮在结果出现后显示
- Quality 结果可以替换 Fast 结果，或作为独立区域展示在下方
- fallback 结果不显示 Quality 按钮（或按钮置灰 + 提示）

## 8. 后端实现方向建议

### 8.1 从固定路由改为请求级路由

```
旧（K7-2）：
  recommendationService → fastRunner（硬绑定）

新（K7-3 实现时）：
  每个 Agent → 根据请求 generation_tier 动态选 runner
    fast   → fastRunner
    quality → qualityRunner
    不传   → fastRunner（默认）
```

### 8.2 保留 K7-2 底层能力

```
LLM_FAST_MODEL=deepseek-v4-flash       ✅ 保留
LLM_QUALITY_MODEL=deepseek-v4-pro-202606  ✅ 保留
fastRunner / qualityRunner              ✅ 保留（只改调度逻辑）
```

### 8.3 实现要点（本次不写代码）

1. Handler 层解析 `generation_tier` 参数
2. Service 层接收 tier，传给 Agent
3. Agent 层根据 tier 选择 fastRunner 或 qualityRunner
4. 响应中返回 `generation_tier` 字段，前端据此展示对应层级标记

## 9. fallback 策略

```
Fast 失败   → Mock Agent（fast 级别 mock）
Quality 失败 → Mock Agent（quality 级别 mock）
```

暂时不做：

```
Fast 失败 → 自动 quality → Mock
Fast 初稿 → 自动 quality 增强
```

原因：
- 会增加调用成本、延迟、排查复杂度
- 渐进式生成由用户显式触发（点击按钮），不是隐式自动升级
