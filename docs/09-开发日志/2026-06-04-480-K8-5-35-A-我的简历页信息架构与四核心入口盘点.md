# K8-5-35-A：我的简历页信息架构与四核心入口盘点

## 一、本阶段目标

只读盘点：查清 `/resumes` 当前页面现状、四核心 AI 功能入口与参数、9 份示范简历用途映射，并给出信息架构建议。

## 二、/resumes 当前页面现状

| 项 | 结果 |
|---|------|
| 路由 | `/resumes` → `RequireAuth` → `ResumeManagementPage` |
| 数据源 | `getResumeVersions()` → `GET /api/resumes/versions` |
| 展示内容 | 页面标题 + "共 X 份简历" + 9 行简历名称 |
| 操作入口 | 每行"编辑 →"跳转 `/resumes/edit`；顶部"添加简历"按钮 |
| 四核心功能入口 | ❌ **无**。页面没有任何 AI 功能入口 |
| Navbar 导航 | 仅 "岗位广场" (`/jobs`) 和 "我的简历" (`/resumes`) 两个链接 |

**当前页面结构（仅 117 行）**：
```
[我的简历]                     [添加简历]
共 9 份简历

+------------------------------------+
| 01-算法研究生-岗位匹配          编辑 →|
| 02-211后台开发-岗位匹配          编辑 →|
| ...                                |
| 09-211后台开发-基础薄弱版-简历优化 编辑 →|
+------------------------------------+
```

**结论**：当前页面是**纯简历名称列表**，没有任何四核心 AI 功能入口。评委进入后只能看到名称，不知道每份简历该用来体验什么功能。

## 三、四核心功能入口现状

| 功能 | 路由 | 页面组件 | 当前入口 |
|------|------|---------|---------|
| 岗位智能推荐 | `/recommend` | `JobRecommendationPage` | ❌ 无直达入口。只能通过直接 URL 访问，或从 `JobDetailAIDecision` 跳转 |
| 岗位匹配分析 | `/match` | `JobMatchAnalysisPage` | ❌ 无直达入口。必须从岗位详情页 `JobDetailAIDecision` 跳转，需传 `jobId` |
| 简历优化建议 | `/resume-optimization` | `ResumeOptimizationPage` | ❌ 无直达入口。必须从岗位详情页 `JobDetailAIDecision` 跳转，需传 `jobId` |
| 简历版本对比 | `/resumes/compare` | `ResumeComparisonPage` | 间接：旧版页面底部曾有 `/resumes/compare` 链接（K8-5-34-C 移除）。可直接 URL 访问，不需额外参数 |

## 四、四核心 API 参数全览

| 功能 | 前端调用 | 后端 API | 必要参数 | 简历参数名 |
|------|---------|---------|---------|-----------|
| 岗位推荐 | `runRecommendation()` | `POST /api/jobs/recommend` | `resume_version_no` (int body), `limit` | `resume_version_no` |
| 岗位匹配 | `runMatchAnalysis()` | `POST /api/jobs/{jobId}/match` | `jobId` (URL path) + `resume_version_no` (int body) | `resume_version_no` |
| 简历优化 | `runResumeOptimization()` | `POST /api/resumes/optimize` | `jobId` (URL param 或 `target_job.job_id`) + `resume_text` (即时拼接文本) | ⚠️ **不传 version_no，传 resume_text** |
| 版本对比 | `compareResumes()` | `GET /api/resumes/versions/compare?from=X&to=Y` | `from`/`to` (query, int) | `from` / `to` |

**关键发现**：
- 推荐和匹配使用 `resume_version_no` 引用后端完整的 version 数据
- 优化**不使用** `resume_version_no`，而是前端拼接 `resume_text` 文本传过去
- 所有命名均为 **snake_case**（`resume_version_no`、`target_job`、`generation_tier`）

## 五、简历 / 岗位选择链路

| 链路 | 当前状态 |
|------|---------|
| 简历版本选择 | `SelectResumeModal` 仅用于 `JobDetailAIDecision`（岗位详情页）。四个 AI 页面内部均**无**切换简历的 UI 控件 |
| 推荐/匹配/优化选择简历 | 页面加载时自动选：URL query 参数 `resumeVersionNo`/`resumeId` 匹配 → 默认第一个（最新版本） |
| 版本对比选择简历 | 页面内两个 `<Select>` 下拉框手动切换 base/target |
| 岗位选择 | 匹配和优化需要 `jobId`，通过岗位详情页的 `JobDetailAIDecision` → `navigate` 传入 URL 参数 |
| 从我的简历页直达匹配/优化 | ❌ 缺少 `jobId`。需要先选岗位或指定默认岗位 |
| 从我的简历页直达推荐 | ✅ 只需 `resume_version_no`，不需要 `jobId` |
| 从我的简历页直达对比 | ✅ 只需 `from`/`to` version_no，已有数据 |

## 七、信息架构问题判断

### 为什么当前设计不专业？

1. **无功能入口**：评委看到 9 份简历后，需要记住路由 `/recommend`、`/match` 才能体验功能
2. **无引导说明**：不知道每份简历该用来体验什么。为什么有"岗位推荐"命名的简历却不能一键推荐？
3. **角色混淆**：页面只扮演了"简历管理"，但这 9 份是种子数据 → 应该扮演 **Demo 体验中控台**
4. **缺少叙事线**：没有"选择一份简历 → 点击对应 AI 功能 → 回到简历列表"的闭环流程
5. **路由隐式耦合**：从我的简历页跳转到 `/recommend` 需要手动拼接 `?resumeVersionNo=4`，这是不暴露给用户的内部细节

### 为什么不能把所有功能都塞成按钮堆？

- 9 份简历 × 4 个功能按钮 → 36 个操作入口 → 严重视觉噪声
- 每份简历有其"最佳体验功能"，不需要全功能入口
- 四核心功能的入口应集中在**简历列表上方**，单份简历只需 1-2 个主要操作

### 推荐角色：C — 简历管理 + AI 功能入口页

结合比赛/Demo 场景，`/resumes` 页应升级为 **Demo 体验中控台**：
- 保留简历列表管理能力
- 在简历列表上方增加 AI 功能入口区
- 每份简历右侧提供"推荐用途"标签和主操作按钮
- 整体作为评委登录后的"第一站"

### 设计要点

| 区域 | 内容 |
|------|------|
| 标题区 | "我的简历" + "共 9 份简历" + "添加简历"按钮 |
| Demo 功能区 | 4 个 icon+文字 按钮横向排列。当前选中简历高亮传递 version_no |
| 简历列表区 | 每行：名称（主）+ 用途标签（轻量 badge）+ 主操作按钮（1 个，根据用途映射）|
| 用途标签 | 🏷 匹配分析 / 🏷 岗位推荐 / 🏷 版本对比 / 🏷 简历优化 |
| 主操作 | 每份简历只显示最核心的 1 个操作（立即匹配 / 开始推荐 / 开始对比 / 开始优化）|
| 编辑入口 | 保留，降级为次操作或 icon-only |

| 方案 | 做法 | 优点 | 风险 | 推荐 |

额外可配：Navbar 增加 "岗位推荐"、"匹配分析" 等顶级入口（后续阶段）。
