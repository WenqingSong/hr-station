# K7-1：双模型分层策略设计冻结

- **日期**：2026-06-02
- **阶段**：K7-1（design freeze, pass）
- **前置**：K6-6（deepseek-v4-flash 接入 pass）
- **性质**：read-only design + docs。**零代码修改。**

## 1. 背景与动机

### 1.1 前置状态

| 阶段 | 结论 |
|------|------|
| K6-5 | flash 主模型（85 分），pro 高质量（76 分），Hy3 备选 |
| K6-6 | flash 已接入；Core + Compare LLM 成功；推荐/匹配/标准优化仍 fallback |

### 1.2 为什么从单模型改为双模型分层

K6-6 回归发现核心矛盾：

- **flash 成功场景**：简历版本对比、Optimization Core（较短 prompt、中等 schema 复杂度）→ real LLM success ✅
- **flash fallback 场景**：岗位推荐、岗位匹配分析、简历优化标准模式（长 prompt、复杂 JSON schema）→ LLM failed → Mock 兜底

结论：**一个模型不能同时满足「低成本高频调用」和「高质量深度分析」。**

因此冻结双模型分层策略：

```
Fast Model：   deepseek-v4-flash       — 高频、轻量、成本敏感
Quality Model：deepseek-v4-pro-202606  — 深度分析、高质量输出、Demo 展示
```

### 1.3 双模型分层解决的核心问题

| 问题 | flash 单模型 | 双模型分层 |
|------|:--:|:--:|
| 推荐/匹配/优化仍 fallback | 只有 Mock 兜底 | pro 大概率 success（K6-4 已验证 Core 成功）|
| Demo 演示时评委感知质量 | flash JSON 不稳定 | pro 提供深度分析、真实性约束 |
| 成本控制 | 全部 flash（低） | 高频 flash + 深度 pro（合理） |
| 高频岗位推荐成本 | 低 | 低（flash） |

## 2. 模型层级定义

### 2.1 模型清单

| 模型层级 | 模型名 | 定位 | 成本（约/次） |
|----------|--------|------|:--:|
| **Fast Model** | `deepseek-v4-flash` | 高频、轻量、初筛、成本敏感 | $0.00112 |
| **Quality Model** | `deepseek-v4-pro-202606` | 深度分析、复杂推理、Demo 展示 | $0.00348 |
| **Fallback** | Mock Agent | 任何模型失败时兜底 | 免费 |

### 2.2 Fast Model 定位

**用于**：高频、轻量、成本敏感、初筛、简单结构化生成、页面快速响应。

**推荐场景**：

| 任务 | 原因 |
|------|------|
| 岗位智能推荐 | 高频调用，需返回多个岗位列表，简单结构化 |
| 简历关键词提取（未来） | 轻量 NLP，1M 上下文可处理长简历 |
| 岗位标签/摘要（未来） | 简单结构化 |
| 低风险预判（未来） | 不影响最终结果 |

### 2.3 Quality Model 定位

**用于**：深度分析、复杂推理、真实性约束、高质量输出、Demo 关键展示结果、评委能明显感知质量的链路。

**推荐场景**：

| 任务 | 原因 |
|------|------|
| 岗位匹配分析 | 需精确评分、证据链、风险判断 |
| 简历优化标准模式 | 需高质量表达改写、真实性约束 |
| Optimization Core | 首屏核心建议需简洁精准（已验证 pro 成功） |
| 简历版本对比 | 差异识别 + 字段变化 + 深度分析 |
| 风险/边界判断（未来） | 需要更严谨的推理能力 |

|---|----------|----------|----------|----------|:--:|
| 1 | 简历版本对比 | 比较不同版本变化、提升点和风险点 | **Quality（pro）** | Mock Agent | ✅ |
| 2 | 岗位智能推荐 | 基于当前简历推荐更适合投递的岗位 | **Fast（flash）** | Mock Agent | ✅ |
| 3 | 岗位匹配分析 | 分析简历与岗位 JD 的匹配度 | **Quality（pro）** | Mock Agent | ✅ |
| 4 | 简历优化建议 | 针对目标岗位给出可执行修改建议 | **Quality（pro）** | Mock Agent | ✅ |

### 3.1 简历优化子模式

| 子模式 | 模型层级 | 说明 |
|--------|----------|------|
| 标准优化（不传 mode） | Quality（pro） | 完整优化路径：top_fix_items + keyword_alignment + rewrite |
| Optimization Core（mode: "core"） | Quality（pro） | 首屏 2-3 条核心建议 + apply_readiness |

**原则**：简历优化是 Demo 核心展示功能，统一用 pro 保证输出质量。

## 5. 配置设计建议（未来实现）

### 5.1 推荐环境变量

```env
# ── 基础 LLM 配置（不变） ──
LLM_ENABLE=true
LLM_PROVIDER=deepseek
LLM_BASE_URL=https://tokenhub.tencentmaas.com/v1/chat/completions
LLM_API_KEY=your_api_key_here

# ── 双模型分层配置（新增） ──
LLM_FAST_MODEL=deepseek-v4-flash
LLM_QUALITY_MODEL=deepseek-v4-pro-202606
LLM_DEFAULT_TIER=fast

# ── 兼容旧配置 ──
LLM_MODEL=deepseek-v4-flash
```

### 5.2 兼容规则

```text
1. 优先读取 LLM_FAST_MODEL / LLM_QUALITY_MODEL。
2. 如果 LLM_FAST_MODEL 缺失，回退到 LLM_MODEL。
3. 如果 LLM_QUALITY_MODEL 缺失，回退到 LLM_MODEL。
4. 如果 LLM_MODEL 也缺失，则走 Mock fallback。
5. 两个 tier 独立失败 → 各自 fallback 到 Mock Agent。
```

### 5.3 Go 配置结构（建议）

```go
// LLMTierConfig 模型层级配置
type LLMTierConfig struct {
    FastModel    string  // LLM_FAST_MODEL
    QualityModel string  // LLM_QUALITY_MODEL
    DefaultTier  string  // LLM_DEFAULT_TIER
}
```

### 5.4 双 client 方案（建议）

```
main.go 创建两个 llm.Client：
  - fastClient: 使用 LLM_FAST_MODEL
  - qualityClient: 使用 LLM_QUALITY_MODEL

pipelineRunner 按 agent 类型选择 client：
  - recommendation → fastClient
  - match_analysis → qualityClient
  - resume_optimization → qualityClient
  - version_compare → qualityClient
```

## 6. fallback 策略

### 6.1 当前阶段冻结策略

```text
Fast Model 调用失败     → Mock Agent
Quality Model 调用失败  → Mock Agent
```

两个层级独立 fallback，互不依赖。

### 6.2 为什么不实现「flash 失败 → pro → Mock」多级降级

| 原因 | 说明 |
|------|------|
| 增加调用成本 | 每次 fallback 会多一次 pro 调用 |
| 增加延迟 | 多次 LLM 调用串行累加延迟 |
| 增加排查复杂度 | 两个模型都可能失败，定位问题更困难 |
| 当前链路不适合 | 项目仍有前端和联调问题待解决 |

### 6.3 保留为未来增强方向

```text
flash 初筛 → pro 增强  （两级生成流水线）
```

未来增强场景：
- 岗位推荐：flash 快速筛选候选 → pro 补充推荐理由和风险分析
- 但需要额外一次 LLM 调用 + 更复杂的 prompt/schema 设计

**本阶段不实现。**

## 7. 本次不做两级生成流水线

明确区分：

### 7.1 本次冻结：模型分层

```
不同功能选择不同模型。

岗位推荐     → flash
岗位匹配分析 → pro
简历优化     → pro
版本对比     → pro
```

### 7.2 本次不做：两级生成流水线

```
flash 先生成初稿 → pro 再增强（❌ 本次不做）
```

原因：
- 会改动业务链路
- 会多一次 LLM 调用（增加延迟和成本）
- JSON schema 复杂度翻倍
- fallback 排查难度翻倍
- 当前任务是战略设计冻结，不是代码实现
