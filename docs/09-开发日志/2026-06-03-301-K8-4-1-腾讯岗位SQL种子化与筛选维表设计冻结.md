# K8-4-1：腾讯岗位 SQL 种子化与筛选维表设计冻结

- **日期**：2026-06-03
- **阶段**：K8-4-1（design freeze，设计冻结）
- **性质**：岗位数据模型 + 筛选维表 + facets 接口 + SQL seed 策略全部冻结设计

## 1. 背景

K8-3 已修复岗位数据主链路：`tencent-campus-jobs.json` → `import_jobs` Go 工具 → MySQL。当前数据库有 46 条完整腾讯岗位数据。

但当前存在以下问题：
1. **仅靠运行时 JSON 导入不够稳定** — `make reset` 清空 volume 后需靠 `up.sh` Step 6b 重新执行 `go run` 导入，依赖 Go 编译链
2. **筛选栏结构不合理** — 当前 API `/api/jobs/facets` 返回 46 个 category、28 个 direction、50+ 个 skills，直接堆在前端导致筛选栏过长
3. **筛选维表不存在** — 当前依赖 `import_jobs` Go 工具动态生成关联表（`job_locations`/`job_business_groups`/`job_skills`），但没有产品化的筛选分组元数据表

## 2. 当前状态确认

### 2.1 K8-3 后的数据链路

```
resources/jobs/tencent-campus-jobs.json (46 条)
    → server/cmd/import_jobs --replace
    → MySQL: jobs(46) + job_locations(180) + job_business_groups(194) + job_skills(1402)
    → GET /api/jobs (列表), GET /api/jobs/:id (详情), GET /api/jobs/facets (筛选聚合)
```

### 2.2 为什么还需要 SQL 种子化

| 问题 | 现状 | SQL种子化后的改善 |
|------|------|-----------------|
| 导入方式 | 运行时 `go run` 编译+执行 | 直接 `mysql < seed.sql`，零编译依赖 |
| 可复现性 | 依赖 Go 工具 + JSON 文件 | SQL 文件即数据快照，版本可追踪 |
| Docker 环境 | Go 链不在容器内，需宿主机执行 | Docker 容器内可直接导入 SQL |
| 启动性能 | 需编译 Go 代码 + 验证 JSON | 纯 SQL 导入，更快更稳定 |
| 数据版本 | JSON 只有文件时间戳 | SQL 可附带 `seed_version` 元数据 |

### 2.3 当前筛选栏为何不合理

| 问题 | 当前状态 | 根因 |
|------|---------|------|
| 分类维度过多 | facets 返回 46 个 category（每个岗位一个独立值） | facets 直接聚合 jobs 表，无产品级分组 |
| 技能关键词过长 | 50+ 个技能全部平铺在前端 | 无默认展示上限、无搜索过滤 |
| 筛选顺序混乱 | direction 28 个 + category 46 个无序排列 | 无 `display_order` 排序字段 |
| 不支持多选 | `JobFilters` 使用单值 `?: string` | UI 和 API 都只支持单值筛选 |
| 无父子层级 | 城市、类别无层级关系 | 无 `parent_option_id` 结构 |

### 3.3 结论

**当前 4 张表已足以支持岗位列表和详情的数据展示**，无需新增额外的数据关联表。

但**筛选维表是缺失的**——当前 facets API 直接聚合业务数据，缺少产品化的分组元数据。

## 4. 推荐数据模型

### 4.1 总体策略

```
保留现有 4 张表不变（jobs / job_locations / job_business_groups / job_skills）
新增 3 张筛选维表（元数据表，不存业务数据）
SQL seed 生成时同时写入业务数据 + 筛选维表数据
```

### 4.2 表结构设计

#### 已有表（保持不变）

| 表 | 作用 | 关键字段 | 是否新增 |
|----|------|----------|:--:|
| `jobs` | 岗位主表 | id, title, direction, category, job_type, application_type, application_project, summary, description, requirements, *_json 等 | ❌ 已有 |
| `job_locations` | 岗位-城市多对多 | job_id, city | ❌ 已有 |
| `job_business_groups` | 岗位-事业群多对多 | job_id, code, name | ❌ 已有 |
| `job_skills` | 岗位-技能多对多 | job_id, skill | ❌ 已有 |

#### 新增筛选维表

| 表 | 作用 | 关键字段 | 是否新增 |
|----|------|----------|:--:|
| `job_filter_groups` | 筛选分组元数据 | id, code, name, display_order, default_expanded, max_visible_options, visible | ✅ 新增 |
| `job_filter_options` | 筛选选项元数据 | id, group_id, code, label, value, display_order, parent_option_id, visible | ✅ 新增 |
| `job_filter_option_relations` | 岗位-选项多对多 | job_id, option_id | ✅ 新增 |

### 4.3 详细 DDL 设计

```sql
-- 筛选分组表
CREATE TABLE `job_filter_groups` (
  `id`                  INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `code`                VARCHAR(64)  NOT NULL COMMENT '分组代码: application_project/category/city/interview_city/business_group/skill',
  `name`                VARCHAR(64)  NOT NULL COMMENT '显示名称: 应聘项目/岗位类别/工作城市/面试地点/事业群/技能关键词',
  `display_order`       INT          NOT NULL DEFAULT 0,
  `default_expanded`    TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '默认展开',
  `max_visible_options` INT          NOT NULL DEFAULT 6 COMMENT '默认最大展示条目数',
  `visible`             TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '是否在筛选栏显示',
  `created_at`          DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_filter_group_code` (`code`)
) ENGINE=InnoDB;

-- 筛选选项元数据表
CREATE TABLE `job_filter_options` (
  `id`               INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `group_id`         INT UNSIGNED NOT NULL,
  `code`             VARCHAR(128) NOT NULL COMMENT '唯一标识',
  `label`            VARCHAR(128) NOT NULL COMMENT '前端显示文本',
  `value`            VARCHAR(128) NOT NULL COMMENT '用于 URL query 参数的值',
  `display_order`    INT          NOT NULL DEFAULT 0,
  `parent_option_id` INT UNSIGNED NULL COMMENT '父选项（用于层级结构）',
  `visible`          TINYINT(1)  NOT NULL DEFAULT 1,
  `created_at`       DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_option_group_code` (`group_id`, `code`),
  KEY `idx_option_parent` (`parent_option_id`),
  CONSTRAINT `fk_option_group` FOREIGN KEY (`group_id`) REFERENCES `job_filter_groups` (`id`)
) ENGINE=InnoDB;

-- 岗位-筛选选项关联表（多对多）
CREATE TABLE `job_filter_option_relations` (
  `job_id`    BIGINT UNSIGNED NOT NULL,
  `option_id` INT UNSIGNED   NOT NULL,
  `created_at` DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`job_id`, `option_id`),
  CONSTRAINT `fk_rel_job` FOREIGN KEY (`job_id`) REFERENCES `jobs` (`id`),
  CONSTRAINT `fk_rel_option` FOREIGN KEY (`option_id`) REFERENCES `job_filter_options` (`id`)
) ENGINE=InnoDB;
```

## 5. 筛选分组设计

### 5.1 分组定义

| 分组 | code | 默认展开 | 最大默认展示数 | 是否多选 | 数据来源 |
|------|------|:--:|------:|:--:|------|
| 应聘项目 | `application_project` | ✅ 展开 | 8 | 单选 | `job_filter_options`（固定少量选项） |
| 岗位类别 | `job_category` | ✅ 展开 | 8 | 单选 | `job_filter_options`（按 `display_order` 排序，截断 8） |
| 工作城市 | `city` | ✅ 展开 | 8 | 多选 | `job_filter_options`（按岗位数降序，截断 8） |
| 面试地点 | `interview_city` | ❌ 收起 | 6 | 多选 | `job_filter_options` |
| 事业群 | `business_group` | ❌ 收起 | 6 | 多选 | `job_filter_options`（8 个 BG 全部显示） |
| 技能关键词 | `skill` | ❌ 收起 | 10 | 多选 | `job_filter_options`（按频次降序，截断 10，含搜索） |

### 5.2 分组展开/收起规则

| 行为 | 说明 |
|------|------|
| 默认展开 | "应聘项目"、"岗位类别"、"工作城市" — 用户最常用 |
| 默认收起 | "面试地点"、"事业群"、"技能关键词" — 二级筛选维度 |
| 收起态选中有值 | 在标题旁显示选中项名称（当前 K8-1 已实现） |
| 超出上限 | 显示"展开更多（+N 项）"链接 |

### 5.3 为何"岗位类别 46 个"不合理

当前 facets 返回 `categories[]` 包含 46 个唯一值（每个岗位几乎都有不同的 `category`）。这与腾讯招聘实际产品体验不符——腾讯招聘侧通过几个大类（技术/产品/设计/市场/职能）组织 2000+ 岗位，而非平铺每个岗位的 tag。

**方案**：将 46 个 `category` 值映射到父级分类：
- job_type（5 个大类）：技术(26)、产品(7)、设计(4)、市场(6)、职能(3)
- 每大类下再展开子类别

使用 `parent_option_id` 实现父子层级：
```
岗位类别 (展开)
  ├── 技术 (26) ← 父选项
  │   ├── 后台开发 (1)
  │   ├── 前端开发 (1)
  │   ├── 算法 (8)
  │   ├── ...
  ├── 产品 (7)
  │   ├── 产品策划 (1)
  │   └── 产品运营 (1)
  └── ...
```

### 5.4 "求职方向"保留决策

`direction` 字段在 JSON 中为 28 个值，与 `category` 有高度重叠（如 "软件开发" direction 下有"后台开发""前端开发""全栈开发"等多个 category）。

**建议**：前端筛选栏不再单独展示"求职方向"维度。将 `direction` 作为岗位卡片的展示字段（已有 K8-2 实现），但不作为独立筛选分组。用户通过"岗位类别"父子层级即可完成方向性筛选。

## 9. SQL seed 生成策略

### 9.1 生成链路

```
resources/jobs/tencent-campus-jobs.json (原始主数据，手动整理)
    ↓
scripts/dev/generate_tencent_jobs_seed.sh (Go 生成脚本)
    ↓
server/sql/seed/tencent_jobs.sql (可重复导入的 SQL 种子产物)
    ↓
make up / make reset 导入
```

### 9.2 关键决策

| 决策点 | 结论 | 原因 |
|--------|------|------|
| 生成脚本用什么语言 | Go（复用现有 `server/cmd/import_jobs` 代码） | 已有字段结构定义、校验逻辑、JSON 解析代码 |
| SQL 是否提交到仓库 | ✅ 是，作为种子产物 | 便于版本追踪、无需编译环境即可导入 |
| JSON 是否保留 | ✅ 是，作为原始数据源 | 保留可编辑的主数据源，SQL 是生成产物 |
| 如何保证幂等 | `INSERT ... ON DUPLICATE KEY UPDATE` 或 `DELETE WHERE external_source='manual_curated'` + `INSERT` | 可重复执行 |
| 如何避免手写 SQL | Go 脚本生成，模板化输出 | 人力不可靠、格式错误风险 |
| 处理转义 | Go 的 `database/sql` 参数化或 JSON 转义 | 原生安全 |

### 9.3 生成脚本设计

```bash
scripts/dev/generate_tencent_jobs_seed.sh
```

逻辑：
1. 读取 `resources/jobs/tencent-campus-jobs.json`
2. 校验 JSON 结构完整性
3. 遍历 46 个岗位，生成：
   a. `INSERT INTO jobs ...` 语句（主表字段）
   b. `INSERT INTO job_locations ...` 语句
   c. `INSERT INTO job_business_groups ...` 语句
   d. `INSERT INTO job_skills ...` 语句
   e. `INSERT INTO job_filter_options ...` 语句（统计去重）
   f. `INSERT INTO job_filter_option_relations ...` 语句
4. 输出到 `server/sql/seed/tencent_jobs.sql`
5. 附带 `-- seed_version: 2026-06-03-001` 注记

### 9.4 SQL 文件结构

```sql
-- ============================================================
-- 腾讯校园招聘岗位 Seed 数据
-- 生成时间: 2026-06-03T00:00:00Z
-- seed_version: 2026-06-03-001
-- 数据源: resources/jobs/tencent-campus-jobs.json
-- 岗位数量: 46
-- ============================================================

-- 1. 清理旧 curated 数据
DELETE FROM job_skills WHERE job_id IN (SELECT id FROM jobs WHERE external_source = 'manual_curated');
DELETE FROM job_locations WHERE job_id IN (SELECT id FROM jobs WHERE external_source = 'manual_curated');
DELETE FROM job_business_groups WHERE job_id IN (SELECT id FROM jobs WHERE external_source = 'manual_curated');
DELETE FROM jobs WHERE external_source = 'manual_curated';

-- 2. 写入岗位主表
```

## 10. make up / make reset 导入策略

### 10.1 make reset 行为

```
make reset CONFIRM=yes:
  1. 停止所有服务
  2. 清空 Docker volume
  3. docker-compose up（启动 MySQL）
  4. 导入 init.sql（基础表结构 + 用户/简历种子）
  5. 导入 server/sql/seed/tencent_jobs.sql（46 条腾讯岗位 + 筛选维表）
  6. 启动后端 + 前端
```

### 10.2 make up 行为

```
make up:
  └─ up.sh Step 6: 检查核心表是否存在
      ├─ 不存在 → 导入 init.sql → Step 6b
      └─ 存在 → Step 6b
  └─ up.sh Step 6b: 检查腾讯岗位数据
      ├─ manual_curated 已存在 → 跳过
      ├─ 仅 local_mock 且 ≤10 条 → 导入 tencent_jobs.sql
      └─ 其他情况 → 跳过，提示手动执行
```

### 10.4 seed_version 设计

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|:--:|
| SQL 文件头部注释版本号 | 简单、可读 | 需手动更新 | ✅ |
| 独立 `seed_version` 表 | 可程序化查询 | 增加复杂度 | ❌ |

## 11. 对四个核心功能的影响评估

| 核心功能 | 影响 | 说明 |
|----------|:--:|------|
| 简历版本对比 | ✅ 无影响 | 不依赖岗位数据 |
| 岗位智能推荐 | ✅ 正面影响 | 46 条真人岗位替代 8 条 mock，推荐质量更高 |
| 岗位匹配分析 | ⚠️ 需注意 | `match_analyses` 的 `job_id` FK 在 seed 重新导入时会被清理（旧关联失效），用户需重新执行匹配分析 |
| 简历优化建议 | ⚠️ 需注意 | `resume_optimization_results` 的 `job_id=0` 不受影响，但引用具体 job_id 的记录在 seed 重新导入时仍然有效（新 job 的 id 不变，因为 SQL seed 使用固定 id） |

**关键保护措施**：SQL seed 中使用固定 `id` 值（而非 AUTO_INCREMENT），确保每次导入的 job_id 保持一致。`import_jobs` 工具当前不保证固定 id（使用 AUTO_INCREMENT），因此 SQL seed 方案在 data consistency 上优于纯 Go 导入。

## 12. 推荐方案与备选方案对比

### 推荐方案：SQL seed 化 + 筛选维表

```
优点：
  - 零 Go 编译依赖，Docker 环境可用
  - SQL 文件可版本追踪、diff review
  - 固定 job_id，保证推荐/匹配分析记录不失效
  - 筛选维表提供产品化筛选体验
  - make reset 一键恢复完整数据

缺点：
  - 需新增筛选维表 3 张
  - 需新写生成脚本（可从 import_jobs 改造）
  - SQL 文件较大（约 5000+ 行 INSERT）

文件清单：
  - 新增: server/sql/seed/tencent_jobs.sql
  - 新增: scripts/dev/generate_tencent_jobs_seed.sh
  - 修改: scripts/dev/up.sh (Step 6b 改为导入 SQL)
  - 修改: init.sql (新增 3 张维表 DDL + 移除旧 local_mock INSERT)
  - 修改: Makefile (新增 jobs-seed-generate / jobs-seed-apply)
  - 修改: server/internal/service/job_service.go (facets 读维表)
  - 修改: 前端 JobFilterSidebar (消费新 facets 格式)
```

### 备选方案：保留 Go import_jobs + 仅优化 facets

```
优点：
  - 改动最小
  - 复用现有代码
  - 不新增 SQL 文件

缺点：
  - 编译依赖仍在
  - job_id 不稳定（每次导入自增变化）
  - 筛选维表仍需从 Go 代码中动态写入，增加复杂度
  - 无 productized 筛选分组

文件清单：
  - 修改: server/internal/service/job_service.go (facets 优化)
  - 修改: 前端 JobFilterSidebar (消费新 facets)
  - 修改: scripts/dev/up.sh (微调)
```

### 对比矩阵

| 维度 | 推荐方案 | 备选方案 |
|------|:--:|:--:|
| 启动稳定性 | ✅ 纯 SQL，零依赖 | ⚠️ 依赖 Go 编译链 |
| 实现复杂度 | ⚠️ 新增表 + 脚本，约 5-8 文件 | ✅ 改动小，约 2-3 文件 |
| 数据可追踪性 | ✅ SQL 文件可 diff review | ❌ 运行时生成 |
| Demo 稳定性 | ✅ 固定 job_id | ❌ 每次变化 |
| 后续维护 | ✅ 新增岗位 = 改 JSON → 重新生成 SQL | ✅ 改 JSON → 重新 go run |
| 四核心功能保护 | ✅ 固定 id，推荐/分析结果不失效 | ❌ id 变化，旧结果关联断 |

**结论：推荐方案更优**。虽然新增了筛选维表和生成脚本的工作量（约 5-8 文件），但换来了长期的数据稳定性、Docker 兼容性和固定 job_id 的保护。
