## 四、路由 / Auth / API Loading 现状

| 链路 | 当前状态 | 问题 |
|--|--|--|
| **路由方案** | `createBrowserRouter` + `RouterProvider`（无 route lazy/suspense） | ⚠️ **所有页面组件在路由定义时全量 import，无代码分割，无 Suspense fallback，无路由跳转 loading** |
| **页面跳转 loading** | 无任何过渡 loading | ⚠️ **从 /jobs 跳转到 /jobs/10001 或 /recommend 时，无统一 loading 反馈。React Router 默认同步切换，新页面数据加载期间无提示** |
| **useNavigation** | 未使用 | ⚠️ **React Router 提供 `useNavigation().state === "loading"` 作路由级 loading bar，当前全站未接入** |
| **Auth Bootstrap** | `App.tsx` → `AuthBoot` → `bootstrapAuth()`（调用 `/auth/me` 校验 token） | ⚠️ **AuthBoot 返回 null，不渲染任何 loading。`bootstrapAuth` 是异步但无 visual feedback。启动瞬间 `isAuthReady=false`，Router 已挂载** |
| **RequireAuth 等待鉴权** | `isAuthReady=false` → `PageLoading("正在验证登录状态…")` | ✅ **已有 loading，但仅在受保护路由触发。未登录用户访问公开页面时看不到任何 auth loading** |
| **页面跳转后数据加载** | 各页面内部管理 `loading` state | ⚠️ **存在风险：新页面 mount 时可能短暂显示旧状态或空白，随后才替换为 loading 或数据。取决于组件实现** |
| **API 请求 401** | `client.ts` 401 → `clearAuthToken()` + `dispatchEvent("offerr-auth-expired")` + store 更新 | ✅ 链路完整 |
| **Navbar 与页面状态一致性** | Navbar 通过 `useAuth().isAuthenticated` 响应式判断 | ✅ **K8-5-36-C 已修复，统一 auth source** |

## 六、Vite / CNB / Nginx 链路风险

| 风险 | 当前表现 | 建议 |
|--|--|--|
| **Vite 5173 停止** | `make up` 自动启动 `npm run dev`（`scripts/dev/frontend.sh`）。若 Vite 崩溃，Nginx 无回退到静态 dist | ⚠️ Nginx 配置仅 `proxy_pass http://host.docker.internal:5173`，Vite 停止时页面白屏/502 |
| **npm run build 与运行时关系** | `npm run build` 生成本地 `dist/` 静态产物，但当前不为线上环境所用（开发态走 Vite dev proxy） | Nginx 未配置静态 file serving，dist 仅用于 CI/部署时 |
| **Nginx 代理链路** | `docker-compose.yml`：Nginx:80 → `host.docker.internal:5173`（Vite dev）+ `host.docker.internal:8080`（Go backend） | API 路径 `/api/*` proxy 到 Go:8080，前端资源 proxy 到 Vite:5173 |
| **浏览器页面异常** | Vite 停止 → 浏览器显示网络错误或白屏 | 可考虑 Nginx 增加 `proxy_intercept_errors` + 静态错误页提示"开发服务器未就绪" |

**风险等级：中等。开发环境下 Vite 停止导致完全白屏，用户体验差。但这是一个已知的开发环境 tradeoff。**

## 七、Loading 分层设计建议

### 1. App Boot Loading（应用启动层）

| 项目 | 建议 |
|--|--|
| 是否需要全屏 loading？ | ✅ 需要。应用启动瞬间至 Auth Bootstrap 完成前，应显示全屏 Logo loading |
| 是否需要展示 logo？ | ✅ 建议 Offerr鹅 logo + 品牌色背景 |
| 文案 | "Offerr鹅" / "正在启动…" |
| 持续多久才显示？ | 延迟 100-200ms 防闪烁（如果 `bootstrapAuth` 完成太快则不显示） |

### 2. Route Transition Loading（路由过渡层）

| 项目 | 建议 |
|--|--|
| 是否使用顶部细进度条？ | ✅ 推荐。类似 NProgress 风格的顶部 2-3px 品牌色进度条 |
| 是否使用页面级 skeleton？ | ✅ 配合使用。进度条用于"跳转进行中"，skeleton 用于"新页面数据加载中" |
| 是否需要延迟防闪烁？ | ✅ 150ms 延迟：如果数据在 150ms 内加载完成则不显示 loading |
| 实现方式 | React Router `useNavigation().state === "loading"` → 触发全局 RouteProgressBar |

### 3. Page Data Loading（页面数据层）

| 项目 | 建议 |
|--|--|
| 用 skeleton 还是 spinner？ | skeleton 优先，spinner 作为通用兜底 |
| 不同页面是否用统一 PageLoading？ | ✅ 统一 `PageLoading` 组件，匹配/优化页需从内联文本迁移到 PageLoading |

### 4. AI Task Loading（AI 任务层）

| 项目 | 建议 |
|--|--|
| 是否需要专门 AIThinkingLoading？ | ✅ 推荐。不同于普通数据 loading，AI 任务需要展示"思考中"的提示和可能的步骤 |
| 是否显示步骤文案？ | ✅ 可选。如"正在分析岗位 JD…" → "正在匹配简历技能…" → "正在生成优化建议…" |
| 是否显示预计耗时？ | ❌ 不建议。AI 耗时不可预测，显示预估时长反而降低体验 |
| 是否允许取消？ | ⚠️ 当前不建议，Agent 调用不易中断。后续可考虑 AbortController |

### 5. Button Loading（按钮层）

| 项目 | 建议 |
|--|--|
| 按钮内部 spinner 文案如何统一？ | 统一模式：`{Loader2} {动作中}…`，如"登录中…""注册中…""正在进入…""保存中…" |

## 八、推荐方案

### 方案比较

| 方案 | 做法 | 优点 | 风险 | 推荐 |
|--|--|--|--|--|
| A | 只补几个页面的 loading | 快 | 不统一，后续继续乱 | ❌ |
| **B** | 新增统一 Loading 组件体系：AppLoading / PageLoading / Skeleton / ButtonLoading / AIThinkingLoading | **专业可复用** | 中等工作量 | ✅ **强烈推荐** |
| C | 引入第三方 loading 库 | 快 | 增依赖，不必要，与现有设计脱节 | ❌ |

### 推荐方案 B 的具体组件体系

```text
组件体系：
├── AppBootLoading        # 全屏启动 loading（logo + 品牌色背景）
├── RouteProgressBar      # 路由跳转顶部进度条（2-3px 品牌色）
├── PageLoading           # 已有，保持不变（页面级 spinner + 文案）
├── PageSkeleton          # 已有骨架屏体系（DetailSkeleton / ResumeSkeleton / JobListSkeleton）
├── AIThinkingLoading     # 新增：AI 任务专属 loading（带步骤提示）
└── ButtonLoading         # 按钮级 loading（已有 Loader2 模式，统一文案规范）
```
