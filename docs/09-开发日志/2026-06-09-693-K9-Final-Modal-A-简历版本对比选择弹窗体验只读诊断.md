## 二、当前弹窗实现详细诊断

### 2.1 弹窗结构与尺寸

| 检查项 | 当前实现 | 问题 |
| ---- | ---- | ---- |
| 弹窗宽度 | `max-w-3xl`（~768px） | 合理，不算过窄 |
| 弹窗最大高度 | `maxHeight: "min(760px, calc(100vh - 64px))"` | 760px 对于 9 份简历+搜索+header+footer 偏小 |
| 是否内部滚动 | **是**，Body 区域使用 `overflow-y-auto` | **滚轮明显**，核心问题 |
| 滚动区域位置 | Body div（L255）：`min-h-0 flex-1 overflow-y-auto px-6 py-4` | 浏览器原生滚动条，视觉粗糙 |
| 候选简历卡片高度 | `px-4 py-3` + 3 行文字（名称/方向标签/时间项目）≈ 90px | 信息密度低，单行利用率不足 |
| 是否使用 grid | **否**，使用 `space-y-2` 纵向单列 | 浪费横向空间 |
| 是否使用 list | **是**，纵向长列表 | 9 份简历 ≈ 810px > 可用空间 → 滚轮 |
| 选择标识方式 | compare 模式：数字 1 / 2（L334 `idx + 1`） | 不专业，无“旧版/新版”角色 |
| 是否区分旧版/新版 | **否** | 用户体验盲区 |
| 是否说明选择顺序影响 | **否** | 用户不知道 `ids[0]`=旧版, `ids[1]`=新版 |
| 是否支持交换顺序 | **否** | — |
| 是否支持取消某个选择 | 部分支持（再次点击取消，但无法单独取消某一项） | 不够直观 |
| 是否支持搜索 | **是**（Search 输入框 L244） | 正常 |
| 是否支持空态 | **是**（无简历 / 搜索无结果两种空态） | 正常 |
| 是否支持移动端 | 弹窗宽度 768px，移动端会溢出 | 需要响应式适配 |

## 三、滚轮问题诊断

### 3.1 根因分析

| 问题 | 当前原因 | 建议 |
| ---- | ---- | ---- |
| 弹窗高度太小 | `maxHeight: 760px`，但 header(~76px) + search(~56px) + footer(~60px) + padding ≈ 200px 固定高度 | 弹窗高度可适度增加到 85vh 或 800px |
| 列表项高度太大 | 每张卡片 `px-4 py-3` + 3 行信息行，约 90px 每张 | 改为紧凑卡片（50-60px），或 2 列 grid 布局 |
| 候选简历过多缺少分组/精简 | 全量 9 份展示，无任何截断或分页 | 改为 max 6-8 份展示 + 搜索过滤更多 |
| 应改为两栏布局 | 单列竖向占满 768px 宽度但纵向无限延伸 | 2 列 grid 可让 9 份简历在 5 行内展示 |
| 应改为"旧版槽位 + 新版槽位 + 简历池" | 没有角色槽位，全部混在同一个列表 | 顶部 2 槽位占用固定空间，下方简历池紧凑展示 |
| 应分页或最多展示最近 6 份 | 无数量限制 | 默认展示最近 6 份，更多通过搜索查找 |
| 滚动条视觉粗笨 | 浏览器原生 `overflow-y-auto` 滚动条 | 可保留滚动但缩小可用空间 → 改为 grid 减少滚动需求，或自定义细滚动条 |

### 3.2 滚轮产生过程

```
固定高度占用:
  Header:      ~76px  (title + description)
  Search bar:  ~56px  (输入框 + padding)
  Footer:      ~60px  (按钮 + padding)

可用滚动区域 = 760px - 192px = 568px

9 份简历 × 90px = 810px > 568px → 滚轮出现 ❌
```

**结论**：滚轮根因不是单一因素，是 **垂直列表布局 + 卡片高度偏高 + 弹窗总高度受限** 三个因素叠加。如果改为 2 列 grid，9 份简历只需 5 行 × 90px = 450px < 568px，滚轮自然消失。

## 四、选择交互方案评估

| 方案 | 是否推荐 | 理由 | 风险 |
| ---- | ---- | ---- | ---- |
| A：保留多选列表，数字改"旧版/新版" | ❌ 不推荐 | 改动最小，但仍然是普通多选列表；用户不理解"旧版/新版"顺序来自点击顺序；卡片布局不变滚轮仍在 | 体验问题不根治，选择顺序仍不明确 |
| B：顶部两槽位 + 下方简历池 | ✅ **强烈推荐** | 角色区分最清晰（旧版/新版各一个槽位）；简历池可 compact card grid；支持交换顺序；接近"专业对比工具"体验；改动适中 | 需要重构 ResumePickerModal 内部布局 + compare 模式下角色管理状态，但组件能力已预留 `selectionMode="compare"` |
| C：双列对比选择器 | ⚠️ 次推荐 | 角色直观（左旧版/右新版各选一份）；但 768px 分两列比较拥挤；对比场景不需要同时看到两份简历的完整信息 | 移动端无法适配双列；信息重复 |
| D：步骤式选择 | ❌ 不推荐 | 步骤清晰但交互冗余（3 步 vs 1 步）；用户选第一份后不知道第二份角色 | 多步交互体验差，不符合"两选一弹窗"的产品需求 |

### 推荐：方案 B

**理由**：
1. 产品语义最清晰：顶部"旧版"和"新版"两个可视化槽位，用户一眼看出角色
2. 下方简历卡片池：可 compact 为 2 列 grid，消除滚轮
3. 支持交换顺序：一键交换旧版/新版
4. 改动范围可控：仅修改 `ResumePickerModal` 的 compare 模式渲染逻辑
5. 不改 API / DB / 路由参数

## 五、推荐新弹窗产品设计

| 区域 | 设计 |
| ---- | ---- |
| 标题 | "选择两份简历进行版本对比" |
| 副标题 | "先选择旧版（对比基线），再选择新版（迭代后版本）。系统会分析新版相比旧版的提升、风险和下一代优化建议。" |
| 旧版槽位 | 左上角带"旧版简历"标签的虚线/实线卡片（hover 提示"点击下方简历设为旧版"）。已选择时：显示简历名称 + 方向 + 更新时间 + X 移除。未选择时：虚线框 + "点击下方简历设为旧版"文字。 |
| 新版槽位 | 右上角带"新版简历"标签的虚线/实线卡片。已选择时同旧版。未选择时：虚线框 + "点击下方简历设为新版"文字。 |
| 简历池 | 下方 2 列 grid 紧凑卡片，每张显示：名称 + 方向 + 更新时间。点击后根据当前缺失槽位自动填入（优先填入旧版，旧版已有则填入新版）。若两个槽位均已满，点击替换（点击时弹出 mini 选择：替换旧版 / 替换新版）。 |
| 选中状态 | 槽位中卡片显示蓝色实线边框 + 浅蓝背景，简历池中对应卡片显示蓝色边框 + "旧版"或"新版"小标签。 |
| 交换顺序 | 两个槽位之间的 `⇄` 交换按钮（仅两个槽位均已选择时显示），hover 提示"交换旧版与新版顺序"。 |
| 搜索 | 保留搜索框，过滤下方简历池。搜索结果实时更新。 |
| 空态 | 无简历时："还没有可用于对比的简历" + "去添加简历"链接。搜索无结果时："没有找到匹配的简历，换个关键词试试" + "清空搜索"按钮。 |
| 底部按钮 | 左侧："管理我的简历"链接。右侧："取消" + "开始对比"（disabled 直到两个槽位均已选择）。 |
| 移动端 | 槽位改为上下排列（旧版在上，新版在下，交换按钮在右侧）。简历池改为单列。 |

## 六、是否需要修改数据结构

| 层级 | 是否需要改 | 理由 |
| ---- | ---- | ---- |
| DB | **不需要** | 不涉及任何表结构或 seed 数据变更 |
| 后端 API | **不需要** | 简历列表 API 不变，对比 API 不变 |
| 前端状态结构 | **需要改**（局部） | compare 模式下 `selectedIds` 的数组顺序需要替换为 `{oldId, newId}` 对象结构，以便明确槽位角色 |
| 前端 UI 组件 | **需要改**（resumePickerModal） | compare 模式的渲染逻辑需要重构为"槽位 + 简历池"布局 |
| 路由参数 | **不需要** | 仍使用 `fromResumeId` / `toResumeId`，内部字段不变，用户可见文案改为"旧版/新版" |

### 关键判断

```text
不改 DB ✅
不改后端 API ✅
仍然使用 fromResumeId / toResumeId 作为路由参数 ✅
用户可见文案改为"旧版 / 新版"，但路由 query 参数不变 ✅
前端状态：selectedIds: number[] → { oldId: number | null; newId: number | null } ✅
```
