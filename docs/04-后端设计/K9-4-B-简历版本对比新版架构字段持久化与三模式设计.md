见 [K9-4-A 只读诊断报告](../../09-开发日志/2026-06-07-610-K9-4-A-简历版本对比功能现状与重构边界只读诊断.md)。

## 2. 彻底重构决策

| 旧设计 | 新决策 | 原因 |
|---|---|---|
| GET 方法获取对比结果 | **POST** 生成 + GET latest 读取 | 对齐 K9-1/K9-3 模式，支持 Fast/Deep |
| 无 generation_tier | **Fast / Deep 双阶段** | 对齐 K9-1/K9-2/K9-3 标准 |
| 无 metadata 持久化 | **完整 metadata 列** | generation_tier/generated_by/status |
| 无 mode 概念 | **general / target_direction / target_job 三模式** | 对齐 K9-3 三模式设计 |
| 不消费 ResumeProfile | **消费 from/to 两份 Profile** | 方向一致性判断、画像清晰度对比 |
| 不复用 K9-3 优化结果 | **引用 optimization latest 作为输入** | 避免建议冲突、提升可解释性 |
| 旧 GET 接口 | **废弃为 deprecated adapter** | 新版主链路用 POST |

| 绝不恢复 | 原因 |
|---|---|
| `resume_versions` 表 | 已彻底迁到 `resumes` |
| `version_no` 字段 | 已废弃 |
| 单 resume_id 版本对比 | 本质是多简历对比，非单简历版本 |

## 3. 输入模型设计

### 核心输入

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `from_resume_id` | uint64 | ✅ | 原版本（旧版）简历 ID |
| `to_resume_id` | uint64 | ✅ | 目标版本（新版）简历 ID |
| `comparison_mode` | string | 默认 general | general / target_direction / target_job |
| `generation_tier` | string | 默认 fast | fast / quality |
| `target_direction` | string | target_direction 模式必填 | 目标求职方向 |
| `job_id` | uint64 | target_job 模式必填 | 目标岗位 ID |

### 校验规则

```
1. from_resume_id ≠ to_resume_id
2. 两份简历必须都属于当前用户
3. comparison_mode ∈ {general, target_direction, target_job}
4. generation_tier ∈ {fast, quality}
5. target_direction 模式 → target_direction 必填
6. target_job 模式 → job_id 必填且存在
```

### 方向语义

```
from_resume_id=1, to_resume_id=2 与 from_resume_id=2, to_resume_id=1 视为不同查询。
因为对比文案中有"原版本"/"目标版本"的方向含义，
latest 查询严格按 from/to 顺序匹配。
```

## 4. 三种对比模式

### 4.1 general：通用对比

**输入**: `comparison_mode=general`（仅 from/to）

**适用场景**: 用户想比较两份简历整体质量，无特定目标方向/岗位。

**判断重点**:
- 结构完整度对比
- 项目表达清晰度
- 技能证据密度
- 方向清晰度
- 可读性
- 投递准备度

**Profile 消费**: 使用两份简历的 `dominant_profile` 判断方向一致性。

---

### 4.2 target_direction：目标方向对比

**输入**: `comparison_mode=target_direction` + `target_direction=backend_engineering`

**适用场景**: 用户想比较哪一版更适合某个求职方向。

**判断重点**:
- 方向关键词覆盖度
- 方向证据密度
- 项目按方向排序
- 技能匹配
- 目标方向短板

**Profile 消费**: 两份简历的 dominant_profile + primary_tags 与 target_direction 匹配对比。

---

### 4.3 target_job：目标岗位对比

**输入**: `comparison_mode=target_job` + `job_id=10001`

**适用场景**: 用户想比较哪一版更适合投递具体岗位。

**判断重点**:
- 岗位 JD 覆盖度
- 匹配证据强度
- 风险点
- 可投递程度
- 改写建议

**复用 K9-2 匹配分析**: 可引用两份简历对该岗位的 match_analyses 结果作为输入参考。

**复用 K9-3 优化结果**: 可引用两份简历对该岗位的 optimization 结果作为输入参考。

## 5. 数据库表结构设计

### 5.1 当前表（开发库直接 ALTER，不修改 init.sql）

```sql
-- 当前表
CREATE TABLE `resume_compare_results` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `user_id` bigint unsigned NOT NULL,
  `from_resume_id` bigint unsigned NOT NULL,
  `to_resume_id` bigint unsigned NOT NULL,
  `result_json` json NOT NULL,
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_compare_user_created` (`user_id`,`created_at`),
  KEY `idx_compare_from_to` (`from_resume_id`,`to_resume_id`),
  KEY `fk_compare_to` (`to_resume_id`),
  -- 外键省略
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 5.2 增量 ALTER（开发库执行）

```sql
-- 核心 metadata 三件套（对齐 K9-1 recommendation_results 模式）
ALTER TABLE resume_compare_results
  ADD COLUMN comparison_mode VARCHAR(30) NOT NULL DEFAULT 'general' COMMENT 'general / target_direction / target_job',
  ADD COLUMN generation_tier  VARCHAR(20) NOT NULL DEFAULT 'fast'    COMMENT 'fast / quality',
  ADD COLUMN generated_by     VARCHAR(50) NOT NULL DEFAULT 'mock_agent' COMMENT 'mock_agent / mock_quality / llm_agent',
  ADD COLUMN status           VARCHAR(20) NOT NULL DEFAULT 'ready'   COMMENT 'ready / error';

-- 对比模式额外维度
ALTER TABLE resume_compare_results
  ADD COLUMN target_direction VARCHAR(50) NULL COMMENT 'target_direction 模式的目标方向',
  ADD COLUMN job_id           BIGINT UNSIGNED NULL COMMENT 'target_job 模式的目标岗位';

-- 两份简历的 Profile 元数据
ALTER TABLE resume_compare_results
  ADD COLUMN from_profile_type            VARCHAR(20) NULL,
  ADD COLUMN from_profile_dominant_profile VARCHAR(50) NULL,
  ADD COLUMN to_profile_type              VARCHAR(20) NULL,
  ADD COLUMN to_profile_dominant_profile   VARCHAR(50) NULL;

-- updated_at
ALTER TABLE resume_compare_results
  ADD COLUMN updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP;

-- 索引
CREATE INDEX idx_compare_user_pair_mode_created
  ON resume_compare_results (user_id, from_resume_id, to_resume_id, comparison_mode, created_at);

CREATE INDEX idx_compare_user_pair_dir_created
  ON resume_compare_results (user_id, from_resume_id, to_resume_id, target_direction, created_at);

CREATE INDEX idx_compare_user_pair_job_created
  ON resume_compare_results (user_id, from_resume_id, to_resume_id, job_id, created_at);
```

### 5.3 保存规则

```
1. 每次生成 INSERT 新行（Append-Only，不 UPDATE）
2. 失败不保存（status != 'ready' 不写入）
3. result_json 保存完整对比分析 JSON
4. 表头 metadata 字段必须与 result_json 内部一致
5. from/to_profile_* 从 EnsureProfile 获取并写入
```

## 9. ResumeProfile 消费设计

### 9.1 获取两份 Profile

```
POST compare → 对 from_resume_id 和 to_resume_id 分别调用 EnsureProfile(profileType)
  → 需要 deep 则 quality，不需要则 fast
  → profile 不存在则同步生成 fast
```

### 9.2 Profile 用途

```
1. 从 dominant_profile 判断方向一致性（一致/迁移/分化）
2. 从 primary_tags 提取两版技能差异
3. 从 risk_tags 提取两版风险差异
4. 从 candidate_tags 提取证据变化
5. 方向一致性判断影响 compare_score 和 winner 判定
6. target_direction 模式：哪个 Profile 更匹配目标方向
7. target_job 模式：结合岗位 JD 判断 Profile 匹配度
```

### 9.3 当 Profile 不存在

```
1. EnsureProfile 生成 fast profile（同步，1-3秒）
2. 生成失败 → profile_dominant = ""，continue
3. 不应让页面 pending 等待
4. 后端在 EnsureProfile 调用失败时记录日志并降级
```

## 10. K9-3 优化结果复用设计

### 10.1 复用方式

```
对 from_resume_id / to_resume_id 分别查询 latest optimization：
  - comparison_mode=target_job → 查对应 job_id 的 target_job optimization
  - comparison_mode=target_direction → 查对应 direction 的 target_direction optimization
  - comparison_mode=general → 查 general optimization

将 quick_fix_items / evidence_fix_items / risk_points / rewrite_examples
作为 compare agent 输入参考（非硬性依赖，缺失不阻塞）。
```

### 10.2 用途

```
1. 提升对比结果可解释性（引用 K9-3 的优化分析）
2. 避免 K9-4 和 K9-3 建议互相打架
3. 让"版本对比"能指出下一版该怎么合并两版优点
4. rewrite_examples 可作为 Deep 对比中的"改写示例"参考源
```

## 11. Mock Agent 与 LLM Agent 分层

### Fast (Mock Agent)

```
不调 LLM。
规则引擎对比两版简历的：
  - 结构完整度（模块数量/字段密度）
  - 主导方向（dominant_profile 一致性）
  - 关键差异（字段级变更）
  - 分数差异
返回 compare_score / winner / key_differences / delivery_advice 简要结果。
```

### Deep (LLM Agent / Mock Quality)

```
LLM 优先：传入两版简历 JSON + Profile + optimization 结果
  → 完整分析差异、保留项、合并策略、改写建议
Mock 兜底：规则引擎增强版，生成更详细的差异分析
```

## 12. 数据流总图

```
POST /api/resumes/compare
  → 校验 from_id/to_id/mode/tier
  → EnsureProfile(from) + EnsureProfile(to)  // 确保两版 Profile ready
  → [可选] 查询 K9-3 optimization latest  // target_job/direction 模式
  → selectRunner(tier)
  → [LLM] VersionCompareLLMAgent.Compare(from, to, mode, profiles, optimizations)
  → [Mock fallback] VersionCompareMockAgent.Compare(from, to, mode)
  → INSERT INTO resume_compare_results  // 含 metadata + result_json
  → Response

GET /api/resumes/compare/latest
  → 校验 from_id/to_id/mode + direction/job_id
  → SELECT ... WHERE user_id=? AND from_resume_id=? AND to_resume_id=?
    AND comparison_mode=? AND status='ready'
    [+ AND target_direction=? / AND job_id=?]
    ORDER BY created_at DESC LIMIT 1
  → 无结果 → {has_result: false}
  → 有结果 → {has_result: true, ...}
```
