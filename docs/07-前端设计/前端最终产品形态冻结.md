# 前端最终产品形态冻结

> 冻结时间：2026-05-31
> 所属阶段：5-UX.0.1-A
> 状态：**已冻结**
> 依据：Figma Make 新一轮前端产品形态设计 + 阶段 4 后端能力闭环

## 1. 产品最终定位

Offer 捕手不是普通 AI 聊天助手，也不是后台管理系统，
而是在真实校园招聘岗位浏览和投递流程上增加一层 AI 投递前决策能力。

核心产品叙事：

```text
传统招聘网站解决"岗位展示"的问题，
Offer 捕手解决学生投递前最关键的三个判断：

1. 我适合哪些岗位？
2. 这个岗位我现在能不能投？
3. 投之前我的简历最应该改哪里？
```

## 2. 最终产品形态

```text
腾讯校园招聘风格岗位浏览
+
右侧 AI 投递决策工作台
+
岗位推荐 / 岗位匹配分析 / 简历优化三条结构化路径
+
我的简历管理
+
轻量简历版本比较
```

## 3. 全局 Navbar 规则冻结

### 3.1 Navbar 固定内容

**左侧**：

```text
「Offer 捕手」学生求职匹配智能体
```

**右侧**：

```text
我的简历
```

### 3.2 Navbar 禁止内容

以下内容不允许出现在 Navbar：

```text
岗位浏览
岗位推荐
首页
查公司
招聘活动
关键问答
实习生
中文/En
帮助 Anchor
头像
用户名
下拉菜单
Beta
多余图标
重复品牌区
```

### 3.3 导航规则

- Navbar 只允许一条，不允许出现两层 Navbar
- 如果页面需要返回岗位列表、返回我的简历、返回岗位详情，只能放在页面内容区（页面标题区、面包屑、弱链接、按钮），不能放进 Navbar
- Navbar 不承担主流程导航
- 主流程通过页面内按钮完成

## 5. 页面关系冻结

### 5.1 页面跳转关系

```text
岗位列表页
  → 岗位推荐页

岗位列表页
  → 岗位详情页
  → 岗位匹配分析页
  → 简历优化页

Navbar：我的简历
  → 我的简历管理首页
  → 修改简历
  → 添加简历
  → 历史简历比较

岗位推荐 / 岗位匹配分析前
  → 选择简历弹窗
  → 确认并开始分析
```

### 5.2 简历优化页入口

简历优化页不直接从 Navbar 进入。简历优化页的入口在岗位匹配分析页中，即用户完成匹配分析后点击：

```text
针对该岗位优化简历
```

**页面结构**：


## 5-UX.0.1-B 核验结论引用

阶段 `5-UX.0.1-B 阅读当前前端状况，确定后端需要修改的任务和要添加或者修改的接口` 已完成。

核验结论如下：

1. 当前后端 P0 接口能力基本可支撑阶段 5 前端产品形态。
2. 后端已具备岗位列表 / 岗位详情、岗位推荐、岗位匹配分析、简历优化、当前简历、简历版本、简历详情、简历创建、简历版本比较等基础能力。
3. 当前主要缺口不在后端，而在前端侧。
4. 前端当前仍以静态 Mock 为主，缺少统一 API Client、统一 TypeScript 类型、统一 Mock 数据目录和页面级接口接入。
5. 后续阶段不应优先进行后端大规模改造，而应优先推进前端数据契约、Mock 标准化、API Client 接入和页面数据对接。
6. 后端后续只做必要的接口核验、字段适配、文档补齐和少量兼容修正。

因此，阶段 5 的后续实现重心调整为：

- 前端 types / mocks 标准化；
- 前端 API Client 建立；
- 页面从静态 Mock 逐步切换到接口数据；
- 保持 `data.result + data.meta` 的统一消费；
- 后端仅在前端联调发现真实缺口时进行最小补齐。
