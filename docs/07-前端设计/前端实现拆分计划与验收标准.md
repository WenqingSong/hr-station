## 3. 后续阶段总路线

### 3.1 为什么进入 4-4

**推荐将后续前端产品化实现从 4-3 拆出，进入 4-4 前端产品化实现阶段。**

理由：

1. **阶段 4-3 的核心目标是 Agent 接入 LLM Pipeline**，已完成：三类 Agent 均已接入 LLM + fallback
2. **4-3.9 是衔接前端的设计阶段**，4-3.9.0/9.1/9.2 都是为前端实现做设计准备
3. **前端产品化实现是全新的工程阶段**，涉及 API client、路由、组件、页面、Mock 对齐等多维度改造，不宜塞在 4-3 内
4. **4-3 的剩余任务（4-3.9 字段策略、4-3.10/4-3.11 集成验收汇总）** 可以与 4-4 并行或串行，不冲突

### 3.2 4-3 与 4-4 的边界

| 维度 | 4-3（Agent 接入 LLM） | 4-4（前端产品化实现） |
|------|----------------------|---------------------|
| 核心目标 | Agent 接入 LLM Pipeline | 前端展示 Agent 结果 |
| 修改范围 | server/ + docs/ | web/ + docs/ |
| 是否改前端 | ❌ 不改 | ✅ 主要改前端 |
| 是否改后端 | ✅ 主要改后端 | ❌ 不改后端接口 |
| 验收对象 | Agent LLM 输出质量 + fallback | 前端页面展示 + API 对接 |

### 3.3 4-3 剩余任务

4-3 尚有收口任务，与 4-4 独立：

- 4-3.9 业务 Agent 接入后的 RunResult 字段策略落地
- 4-3.10 三类业务 Agent 集成验收
- 4-3.11 阶段 4-3 汇总

这些任务不影响 4-4 启动，可以并行推进。

## 4. 是否进入 4-4 前端产品化实现阶段

**✅ 是，建议进入 4-4 前端产品化实现阶段。**

理由：

1. 三类 Agent 后端能力已闭环（LLM + fallback）
2. 前端模块映射方案已设计完成（4-3.9.1）

## 7. 4-4.1 前端 API Client 与类型定义

### 目标

新增统一 API client，支持调用三类后端接口。

### 输入

- 4-4.0 的 TypeScript 类型定义
- 三类 Agent 接口文档

### 输出

- `web/src/api/client.ts`：统一请求层
- `web/src/api/agent.ts`：三类 Agent API 封装
- `web/src/api/types.ts`：请求/响应类型
- 错误处理和 loading 状态工具

### 具体工作

1. **API Client 选型**：使用 `fetch` + 自定义封装（不引入 axios）
   - 理由：项目已使用现代浏览器 API，fetch 满足需求，无需额外依赖
   - 封装内容：统一 baseUrl、错误处理、响应解析、loading 状态
2. **环境变量**：使用 `VITE_API_BASE_URL`
   - 开发环境：`http://localhost:8080`（Nginx 代理后可改为 `/api`）
   - 当前 Nginx 已配置 `/api` 代理到后端
3. **API 封装**：
   - `fetchRecommendation(resumeId: number)` → `RecommendationResult`
   - `fetchMatchAnalysis(resumeId: number, jobId: number)` → `MatchAnalysisResult`
   - `fetchResumeOptimization(resumeId: number, jobId: number)` → `ResumeOptimizationResult`
4. **错误处理**：
   - 网络错误 → 展示错误提示
   - 401 → 跳转登录
   - 500 → 展示降级提示
   - LLM 降级 → 正常展示（generated_by / agent_status 标识）
5. **loading 状态**：返回 `{ data, loading, error }` 三元组

### 允许修改范围

- `web/src/api/`：新增 API client 文件
- `web/src/types/`：补充 API 相关类型
- `docs/`：新增 API 对接文档

### 禁止修改范围

- 页面组件
- 路由配置
- 后端代码
- Prompt / Schema / Go Model
- Mock 数据文件

### 验收标准

1. API client 可编译通过
2. 三类 Agent 接口封装完整
3. 错误处理覆盖常见场景
4. loading / error 状态工具可用
5. 不调用真实 LLM，只调用本地后端接口或 Mock fallback

### 是否可以跳过

❌ 不可以跳过。API 对接层是后续页面改造的基础。

### 依赖阶段

4-4.0（TypeScript 类型定义）

### 风险点

1. Nginx 代理路径需要确认
2. 后端接口认证方式（JWT）需要处理
3. 如果后端接口返回结构与 Go Model 不一致，需要额外映射

## 9. 4-4.3 三 Agent 共享决策组件

### 目标

先实现三类 Agent 共用的 P0 组件，为后续页面改造提供可复用组件。

### 输入

- 4-4.0 的 TypeScript 类型定义

### 输出

- `web/src/components/agent/ApplyReadinessCard.tsx`
- `web/src/components/agent/OptimizationStopSignalCard.tsx`
- `web/src/components/agent/TopFixItems.tsx`
- `web/src/components/agent/AgentStatusBadge.tsx`
- `web/src/components/agent/RiskCard.tsx`（基础版）

### 具体工作

1. **投递准备度卡片** `ApplyReadinessCard`
   - Props：`applyReadiness: ApplyReadiness`
   - 展示：四色四态（绿色可以投递 / 黄色先修几项 / 红色暂不建议 / 灰色信息不足）
   - 支持三类 Agent 复用

2. **优化停止信号卡片** `OptimizationStopSignalCard`
   - Props：`signal: OptimizationStopSignal`
   - 展示：四色四态（绿色可以投了 / 黄色修完再投 / 红色需补证据 / 红色方向不匹配）
   - 支持三类 Agent 复用

3. **Top 3 快速修复任务** `TopFixItems`
   - Props：`items: TopFixItem[]`
   - 展示：任务卡 / checklist，每项含 issue / why_it_matters / action / example_reference / self_check_question / estimated_effort
   - 支持三类 Agent 复用

4. **结果来源状态标签** `AgentStatusBadge`
   - Props：`generatedBy: string, agentStatus: string`
   - 展示：小标签（"AI 分析" / "规则分析" / "AI 降级分析"）
   - 支持三类 Agent 复用

5. **风险提示卡基础版** `RiskCard`
   - Props：`risks: string[]`
   - 展示：简单风险列表（Go Model 当前为 string[]）
   - 后续可升级为结构体版

### 允许修改范围

- 后端代码
- API client
- Prompt / Schema / Go Model

1. 五个共享组件可独立渲染

3. 投递准备度和停止信号有四种状态展示
4. Top Fix 任务可展示 issue/action/effort
5. 组件样式与当前设计 token 一致

## 16. 总体验收标准

### 16.1 不合格的验收

1. ❌ 页面只显示一段 AI 文本
2. ❌ 只把 JSON stringify 出来
3. ❌ 三类 Agent 只展示其中一个
4. ❌ 没有 apply_readiness
5. ❌ 没有 optimization_stop_signal
6. ❌ 没有 top_fix_items
7. ❌ 没有证据链
8. ❌ 没有用户核实提醒
9. ❌ 没有 loading / error 态
10. ❌ 没有 Mock fallback 展示

### 16.2 合格验收

1. ✅ 三类 Agent 都有明确页面或模块
2. ✅ 三类 Agent 共享字段统一展示
3. ✅ 关键字段拆成卡片 / 表格 / 任务 / 看板 / 核实清单
4. ✅ 推荐结果可排序或分组
5. ✅ 匹配分析有 JD 证据链
6. ✅ 简历优化有 Top Fix 和用户核实
7. ✅ 前端可展示 generated_by / agent_status
8. ✅ loading / error / fallback 状态清晰
9. ✅ Mock 数据与真实接口结构一致
10. ✅ Demo 讲解路径完整

### 16.3 优秀验收

1. ✅ 闭环导航流畅（推荐→分析→优化→确认）
2. ✅ 移动端体验基本可用
3. ✅ 投递前确认清单完整
4. ✅ 所有 P0 模块实现
5. ✅ 至少 3 个 P1 模块实现

## 17. 不可混做事项

| # | 禁止事项 | 原因 |
|---|---------|------|
| 1 | 不要在 API client 阶段顺手大改页面 | API 层独立，不影响展示层 |
| 2 | 不要在路由阶段顺手接真实 LLM | 路由改造不涉及 API 调用 |
| 3 | 不要在 Recommendation 页面阶段顺手做 ResumeOptimization | 每个页面独立改造，避免混乱 |
| 4 | 不要在共享组件阶段顺手改后端接口 | 共享组件只消费数据，不改变数据源 |
| 5 | 不要在前端实现阶段修改 Prompt / Schema | Prompt / Schema 是后端契约，前端不改 |
| 6 | 不要把 P2 可视化图表提前塞进 P0 | P2 依赖额外依赖和设计，不应阻塞 P0 |
| 7 | 不要为了好看牺牲数据真实性 | 展示必须基于真实 Agent 输出，不是编造 |
| 8 | 不要把 AI 输出又退化成一段文本 | 结构化展示是核心产品化目标 |
