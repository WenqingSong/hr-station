### 5-1.3 认证与前端请求适配（P0 必须）

**目标**：前端 API Client 能通过 JWT 认证调用后端接口。

**当前状态**：
- 前端无 API Client、无 token 管理
- 后端所有 Agent 接口需要 `Authorization: Bearer <token>` 头
- 后端 Auth Middleware 从 JWT 提取 `userID`

**修改范围**：
- 前端新增 `web/src/api/client.ts`（统一 fetch 封装）
- 前端新增 `web/src/api/auth.ts`（登录注册）
- 前端新增 token 存储（localStorage）
- 可选：Demo 模式下禁用 Auth Middleware 或使用固定 token

**验收标准**：
1. 前端能成功调用 `POST /api/auth/login` 获取 token
2. 前端能携带 token 调用推荐/匹配/优化接口
3. Demo 模式下可通过预设 token 直接使用（免登录）

**是否改数据库**：否
**是否改 Prompt/Schema**：否
**是否改前端**：是（新增 API client）

### 5-1.4 简历数据前端 Mock 标准对齐（P0 移入前端）

**目标**：前端 Mock 简历数据与后端接口返回结构对齐。

**当前状态**：
- 前端直接使用 TypeScript interface（Resume、Project、Education 等）

**修改范围**：
- 前端新增 `web/src/types/agent.ts`（Agent 返回类型）
- 前端新增 `web/src/types/resume.ts`（简历类型）
- 前端新增 `web/src/mocks/` 目录（独立 Mock 数据文件）

**验收标准**：
1. 前端 TypeScript 类型与后端data.result结构一致
2. Mock 数据文件与真实接口返回结构同形
3. 所有页面可切换为从 Mock 文件读取数据

**是否改数据库**：否
**是否改 Prompt/Schema**：否
**是否改前端**：是（新增 types + mocks）

## 7. 核心发现

1. **后端接口完整性优秀**：三类 Agent 接口、岗位接口、简历接口均已实现且返回 `data.result + data.meta` 统一结构
2. **前端结构完整但无 API 对接**：Figma Make 已生成 9 个页面 + 25+ 组件，但 100% 硬编码 Mock 数据
3. **Navbar 完美对齐冻结形态**：单条 Navbar，左侧品牌 + 右侧"我的简历"
4. **ResumeOptimization P0 字段充足**：Go Model 7 个核心字段足以支撑前端 P0 模块，Schema 理想字段列 P1
5. **认证是主要阻塞点**：所有后端 Agent 接口需要 JWT 认证，前端需要上线 API Client + token 管理
6. **后端几乎不需要 5-1 改动**：5-1 的主要工作在**前端侧**（API Client、TypeScript 类型、Mock 标准化）

## 8. 下一步建议

进入 **5-1.3 认证与前端请求适配** 或 **5-1.4 简历数据前端 Mock 标准对齐**。
