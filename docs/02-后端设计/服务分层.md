# 服务分层

> 最后更新：2026-05-29（阶段 3-6 实现岗位推荐 Mock 接口）

## 当前状态

阶段 3-6 已完成，岗位推荐 Mock 接口已实现。认证模块、简历模块、岗位模块和推荐模块均完成 Handler → Service → Repository → Model 分层，推荐模块新增 Agent Mock 层。下一步 3-7 将实现岗位匹配分析 Mock 接口。

## 分层架构

```
HTTP Handler（控制器层）
  ↓
Service（业务逻辑层）
  ↓
Repository（数据访问层）  ←→  Agent Mock（Mock 数据生成）
  ↓
Model（数据模型）
```

### 基础设施支撑层

```
Config（配置读取）
Database（数据库连接）
Response（统一响应）
AppError（错误定义）
Middleware（中间件）
Health（健康检查）
```

## 各层详细说明

### Handler 层

- 接收 HTTP 请求，参数校验
- 调用 Service 层处理业务
- 返回统一格式的响应
- 当前实现：`/healthz` Handler
- 阶段 3 新增：auth_handler / resume_handler / job_handler / recommendation_handler / match_handler / version_compare_handler

**关键原则**：Handler 只处理 HTTP 入参出参，不在 Handler 里堆业务逻辑。

### Service 层

- 业务逻辑处理
- 调用 Repository 层操作数据
- 调用 Agent Mock 层获取 Mock 结果
- 事务管理
- 阶段 3 新增：auth_service / resume_service / job_service / recommendation_service / match_service / version_compare_service

### Repository 层

- 数据库 CRUD 操作
- 封装 SQL 查询
- 数据模型转换
- 阶段 3 新增：user_repository / resume_repository / job_repository / recommendation_repository / match_repository / version_compare_repository

### Model 层

- 数据结构定义
- 对应数据库表
- JSON 序列化/反序列化标签
- 阶段 3 新增：user / resume / job / recommendation / match / version_compare

### Agent Mock 层

- 阶段 3 Mock 数据生成
- 推荐结果 Mock
- 匹配分析结果 Mock
- 版本对比结果 Mock
- 阶段 4 替换为真实 LLM

**关键原则**：Agent Mock 生成结构化结果，不调用真实 LLM。

### LLM 层

- LLM API 客户端封装
- 模型调用与响应解析
- 当前未实现（阶段 4）

```
┌──────────────────────────────────────────────────────────┐
│                    HTTP Handler 层                        │

│  ── 只处理 HTTP 入参出参，不堆业务逻辑 ──                │
├──────────────────────────────────────────────────────────┤
│                    Service 层                             │

│  user_repository                  │  recommendation_mock  │
│  resume_repository               │  match_mock           │
│  job_repository                  │  version_compare_mock  │
│  recommendation_repository       │                       │
│  match_repository                │  ── 生成结构化        │
│  version_compare_repository      │     Mock 结果 ──      │
│  ── 封装 SQL 查询 ──            │                       │
├──────────────────────────────────────────────────────────┤
│                    Model 层                               │
│  user / resume / job / recommendation                     │
│  match / version_compare                                  │
│  ── 数据结构定义，对应数据库表 ──                        │
├──────────────────────────────────────────────────────────┤
│                基础设施层（阶段 2 已完成）                 │
│  Config / Database / Response / AppError                   │
│  Middleware / Health                                       │
└──────────────────────────────────────────────────────────┘
```

### 各层调用规则

| 调用方 | 被调用方 | 允许 |
|--------|---------|------|
| Handler | Service | ✅ 允许 |
| Handler | Repository | ❌ 禁止（通过 Service） |
| Handler | Agent Mock | ❌ 禁止（通过 Service） |
| Service | Repository | ✅ 允许 |
| Service | Agent Mock | ✅ 允许 |
| Service | Model | ✅ 允许 |
| Repository | Model | ✅ 允许 |
| Repository | Service | ❌ 禁止（反向依赖） |
| Agent Mock | Repository | ❌ 禁止（Agent 不访问数据库） |

### 基础设施层（阶段 2 已完成）

| 层 | 文件 | 职责 | 实现任务 |
|----|------|------|---------|
| Config | `internal/config/config.go` | 读取环境变量，分组配置 | 2-2 增强 |
| Database | `internal/database/mysql.go` | MySQL 连接管理、Ping、连接池 | 2-5 ✅ 已实现 |
| Response | `internal/response/response.go` | 统一响应结构、Success/Error 辅助函数 | 2-3 新增 |
| AppError | `internal/errors/error.go` | 应用错误类型、错误码常量 | 2-3 新增 |
| Middleware | `internal/middleware/*.go` | RequestLogger / CORS / Recover | 2-4 ✅ 已实现 |
| Health | `internal/health/service.go` | 健康检查逻辑，聚合 app/database 状态 | 2-6 ✅ 已实现 |

### Database 连接管理（2-5 已实现）

- `internal/database/mysql.go`：使用 `database/sql` + `go-sql-driver/mysql`
- `NewMySQL(cfg)`：从 DatabaseConfig.DSN 创建连接，配置连接池参数
- `Ping(ctx)`：带 context 的连接验证
- `Close()`：关闭连接释放资源
- 连接池参数：MaxOpenConns=10、MaxIdleConns=5、ConnMaxLifetime=30m、ConnMaxIdleTime=10m
- 当前 database 只负责连接管理，repository 层阶段 3 再实现
- 阶段 3 repository 通过 database 提供的 `*sql.DB` 实现业务查询

### Health 健康检查（2-6 已实现）

- `internal/health/service.go`：健康检查服务，聚合 app 和 database 状态
- `DatabasePinger` 接口：定义数据库 Ping 能力，`database.MySQL` 已实现该接口
- `Service` 结构体：持有 AppName、AppEnv、DB（DatabasePinger）
- `Check(ctx)` 方法：返回 Status 结构（service/env/app/database）+ 健康布尔值
- health 属于基础设施层，不属于业务 service
- health 依赖 database 的 Ping 能力，不引入业务依赖
- 业务 service 层阶段 3 才开始实现

### Config 配置结构（2-2 已增强）

Config 提供后续 database、middleware、service、agent、llm 的基础配置：

| 分组 | 对应后续使用 | 说明 |
|------|------------|------|
| App | 全局 | 应用名称和运行环境 |
| Server | HTTP Server | 端口配置 |
| Database | 阶段 2-5 ✅ | MySQL 连接参数，已在 main.go 中使用 |
| JWT | 阶段 3-3 | 认证配置，当前仅读取不使用 |
| LLM | 阶段 4 | 模型 API 配置，当前仅读取不使用 |
| Feature | 阶段 3 | Mock Agent 开关，当前仅读取不使用 |
| Log | 全局 | 日志级别 |

### Middleware 中间件层（2-4 已实现）

| 中间件 | 文件 | 说明 |
|--------|------|------|
| Recover | `internal/middleware/recover.go` | 捕获 panic，返回统一错误（复用 AppError.ErrInternal） |
| CORS | `internal/middleware/cors.go` | 跨域处理，允许 localhost:5173 |
| RequestLogger | `internal/middleware/logger.go` | 请求日志记录 |

阶段 3-3 将新增 JWT Auth 中间件（`internal/middleware/auth.go`）。

业务层不应手动处理 CORS、不应手动 recover panic。后续业务 handler 自动处于中间件链之下。

### Response 与 AppError（2-3 已实现）

| 组件 | 文件 | 被使用层 | 说明 |
|------|------|---------|------|
| Response | `internal/response/response.go` | HTTP 层、中间件层、业务层 | 统一 JSON 响应结构，阶段 3 所有业务接口必须使用 |
| AppError | `internal/errors/error.go`（包名 apperror） | HTTP 层、中间件层、业务层 | 应用错误类型和基础错误码 |
