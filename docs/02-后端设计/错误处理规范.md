# 错误处理规范

> 最后更新：2026-05-28（阶段 2-4 实现请求日志与 CORS 中间件）

## 1. 规范目标

所有 API 响应必须使用统一的 JSON 格式，包括成功和错误场景。这样前端可以一致地处理响应，降低对接复杂度。

## 2. 统一成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | int | 业务状态码，0 表示成功 |
| message | string | 状态描述，成功时为 "ok" |
| data | any | 业务数据，成功时为实际数据 |

### 工具函数

| 函数 | 说明 |
|------|------|
| `response.OK(w, data)` | 返回 code=0, message="ok" |
| `response.OKWithMessage(w, message, data)` | 返回 code=0, 自定义 message |
| `response.JSON(w, statusCode, payload)` | 完全自定义响应 |

## 3. 统一错误响应

```json
{
  "code": 40001,
  "message": "invalid parameter",
  "data": null
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | int | 业务错误码，非 0 |
| message | string | 错误描述，面向开发者，不暴露底层细节 |
| data | null | 错误响应固定为 null |

### 工具函数

| 函数 | 说明 |
|------|------|
| `response.Error(w, httpStatus, code, message)` | 返回错误响应，data=null |

## 4. 基础错误码

| 错误码 | 常量名 | 说明 | HTTP 状态码 |
|--------|--------|------|------------|
| 0 | CodeOK | 成功 | 200 |
| 40000 | CodeBadRequest | 请求错误 | 400 |
| 40001 | CodeInvalidParam | 参数错误 | 400 |
| 40100 | CodeUnauthorized | 未认证 | 401 |
| 40300 | CodeForbidden | 无权限 | 403 |
| 40400 | CodeNotFound | 资源不存在 | 404 |
| 40500 | CodeMethodNotAllowed | 方法不允许 | 405 |
| 50000 | CodeInternal | 服务内部错误 | 500 |
| 50300 | CodeDependencyUnavailable | 外部依赖不可用 | 503 |

### 错误码范围规划

| 范围 | 说明 |
|------|------|
| 0 | 成功 |
| 40000-40999 | 通用错误（参数错误、未授权等） |
| 41000-41999 | 用户相关错误（阶段 3） |
| 42000-42999 | 简历相关错误（阶段 3） |
| 43000-43999 | 岗位相关错误（阶段 3） |
| 44000-44999 | 推荐相关错误（阶段 3） |
| 45000-45999 | 匹配分析相关错误（阶段 3） |
| 50000-59999 | 服务端错误（内部错误、外部依赖不可用） |

## 5. AppError 结构

```go
type AppError struct {
    Code       int    // 业务错误码
    Message    string // 错误描述
    HTTPStatus int    // HTTP 状态码
    Err        error  // 底层错误（不返回给前端）
}
```

### 预定义错误

| 变量 | 错误码 | Message | HTTP 状态 |
|------|--------|---------|----------|
| ErrBadRequest | 40000 | bad request | 400 |
| ErrInvalidParam | 40001 | invalid parameter | 400 |
| ErrUnauthorized | 40100 | unauthorized | 401 |
| ErrForbidden | 40300 | forbidden | 403 |
| ErrNotFound | 40400 | not found | 404 |
| ErrMethodNotAllowed | 40500 | method not allowed | 405 |
| ErrInternal | 50000 | internal server error | 500 |
| ErrDependencyUnavailable | 50300 | dependency unavailable | 503 |

### 构造函数

| 函数 | 说明 |
|------|------|
| `apperror.New(code, message, httpStatus)` | 创建新的 AppError |
| `apperror.Wrap(code, message, httpStatus, err)` | 包装底层错误 |

## 6. 错误返回规则

1. 所有 API 错误必须返回统一 JSON 格式 `{code, message, data:null}`
2. HTTP 状态码与业务错误码必须匹配
3. Handler 中遇到 `*AppError` 时，使用其 HTTPStatus、Code、Message 返回
4. 成功响应 code=0，错误响应 code 非 0
5. 错误响应 data 固定为 null

## 7. 敏感信息处理

1. **不暴露底层错误**：`AppError.Err` 字段仅用于服务端日志，不返回给前端
2. **不暴露堆栈**：Recover 中间件捕获 panic 时返回通用 "internal server error"
3. **不暴露数据库错误**：数据库错误统一包装为 `ErrInternal` 或 `ErrDependencyUnavailable`
4. **不暴露敏感配置**：JWT_SECRET、LLM_API_KEY 等不出现在错误响应中

## 9. 后续阶段扩展

| 阶段 | 扩展内容 |
|------|---------|
| 阶段 2-4 ✅ | Recover 中间件捕获 panic，返回 `{code:50000, message:"internal server error", data:null}` |
| 阶段 3 | 业务错误码（41000-45999），所有业务接口必须使用统一响应 |
| 阶段 4 | LLM 相关错误码，模型调用失败处理 |

## 10. 业务接口使用要求

阶段 3 所有业务接口必须遵守以下规则：

1. 成功响应使用 `response.OK(w, data)` 或 `response.OKWithMessage(w, message, data)`
2. 错误响应使用 `response.Error(w, httpStatus, code, message)` 或基于 `AppError` 返回
3. 不允许直接使用 `json.NewEncoder(w).Encode()` 返回非统一格式
4. 业务错误码使用 `apperror.New()` 创建，不硬编码
5. 底层错误使用 `apperror.Wrap()` 包装，不直接暴露给前端
