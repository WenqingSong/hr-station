# 中间件设计

> 最后更新：2026-05-28（阶段 2-4 实现请求日志与 CORS 中间件）

## 1. 设计目标

为 Go HTTP Server 提供横切关注点的统一处理能力，包括请求日志、跨域、panic 恢复等。所有中间件采用 Go 标准库 `net/http` 的函数包装模式，不引入第三方框架。

## 2. 当前已实现中间件

| 中间件 | 文件 | 说明 |
|--------|------|------|
| Recover | `internal/middleware/recover.go` | 捕获 panic，返回统一错误响应 |
| CORS | `internal/middleware/cors.go` | 处理跨域请求和 OPTIONS 预检 |
| RequestLogger | `internal/middleware/logger.go` | 记录请求日志 |

## 3. RequestLogger

### 功能

记录每个 HTTP 请求的关键信息到标准日志输出。

### 日志字段

| 字段 | 来源 | 说明 |
|------|------|------|
| method | `r.Method` | 请求方法 |
| path | `r.URL.Path` | 请求路径 |
| status | ResponseWriter 包装 | HTTP 响应状态码（默认 200） |
| duration | `time.Since(start)` | 请求耗时 |
| remote | `r.RemoteAddr` | 客户端地址 |
| user_agent | `r.UserAgent()` | 用户代理 |

### 日志格式

```
method=GET path=/healthz status=200 duration=123.456µs remote=127.0.0.1:12345 user_agent=curl/8.0
```

### 安全要求

- 不打印请求 body
- 不打印 Authorization 头
- 不打印 Cookie
- 不打印 LLM_API_KEY、JWT_SECRET 等敏感信息

### 实现方式

使用自定义 `responseWriter` 包装器捕获 `WriteHeader` 调用的状态码。如果 handler 未调用 `WriteHeader`，默认记录 200。

## 4. CORS

### 允许来源

| 来源 | 说明 |
|------|------|
| `http://localhost:5173` | Vite 默认开发地址 |
| `http://127.0.0.1:5173` | 同上，IP 形式 |

对于本地开发便利，任何 `http://localhost:*` 或 `http://127.0.0.1:*` 端口的 Origin 均被接受用于预检请求。

### 配置项

| 配置项 | 值 | 说明 |
|--------|-----|------|
| Access-Control-Allow-Origin | 动态匹配 | 仅返回请求的 Origin（如匹配允许列表） |
| Access-Control-Allow-Methods | GET, POST, PUT, PATCH, DELETE, OPTIONS | 允许的 HTTP 方法 |
| Access-Control-Allow-Headers | Content-Type, Authorization, X-Requested-With | 允许的请求头 |
| Access-Control-Allow-Credentials | true | 允许携带凭证 |
| Access-Control-Max-Age | 86400 | 预检缓存 24 小时 |

### OPTIONS 预检处理

1. 读取请求头 `Origin`
2. 如果 Origin 在允许列表中（或为 localhost/127.0.0.1），返回 204 No Content + CORS 头
3. 如果 Origin 不在允许列表中，不设置 CORS 头，由后续 handler 处理

### 安全说明

- 当前为开发环境宽松策略，生产环境需收紧 AllowOrigins
- 提前允许 `Authorization` 头，方便阶段 3 JWT 使用
- 不引入第三方 CORS 库

## 5. Recover

### 功能

捕获下游 handler 中的 panic，避免服务崩溃，返回统一错误响应。

### 处理流程

1. 使用 `defer` + `recover()` 捕获 panic
2. 使用 `log.Printf` 记录 panic 值和完整堆栈
3. 返回统一错误响应

### 响应格式

```json
{
  "code": 50000,
  "message": "internal server error",
  "data": null
}
```

HTTP 状态码：500

### 安全要求

- **不暴露 panic 细节**：message 固定为 "internal server error"
- **不暴露堆栈信息**：堆栈仅写入服务端日志
- 复用 `apperror.ErrInternal` 和 `response.Error()`

## 6. 中间件链路顺序

```
Recover（最外层，捕获所有 panic）
  ↓
CORS（处理跨域和预检）
  ↓
RequestLogger（记录请求日志）
  ↓
Handler（业务处理）
```

### 顺序说明

1. **Recover 最外层**：确保任何中间件或 Handler 中的 panic 都能被捕获
2. **CORS 其次**：预检请求在日志之前处理，OPTIONS 请求不经过 RequestLogger
3. **RequestLogger 最内层**：记录所有经过中间件链的实际请求

### 代码实现

```go
handler := middleware.RequestLogger(mux)
handler = middleware.CORS(handler)
handler = middleware.Recover(handler)
return handler
```


## 9. 风险与注意事项

| 风险 | 说明 |
|------|------|
| CORS 策略较宽松 | 当前允许所有 localhost 端口，生产环境需收紧 |
| RequestLogger 不记录 OPTIONS | OPTIONS 由 CORS 短路返回 204，不经过 RequestLogger |
| Recover 不区分 panic 类型 | 所有 panic 统一返回 500，不区分业务 panic 和系统 panic |
| 不修改 main.go | 中间件链在 NewRouter() 中组装，main.go 无需感知 |
