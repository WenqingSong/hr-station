## 1. 阶段目标

阶段 2 不是业务开发阶段，而是后端基础设施建设阶段。

阶段 2 完成后，Go 后端应从当前的"只具备 `/healthz` 的最小服务"升级为具备以下能力：

1. 完整环境变量配置读取
2. 统一响应结构
3. 基础错误处理机制
4. 请求日志中间件（RequestLogger）
5. Recover 中间件（Panic 恢复）
6. CORS 中间件（跨域支持）
7. MySQL 数据库连接
8. 增强健康检查
9. 可支撑阶段 3 的业务接口开发

1. ❌ 用户注册登录
2. ❌ JWT 鉴权
3. ❌ 简历业务接口
4. ❌ 岗位业务接口
5. ❌ 推荐接口
6. ❌ 匹配分析接口
7. ❌ Agent
8. ❌ 模型 API
9. ❌ 前端接后端

这些留给阶段 3 及以后。

```go
type Config struct {

```

### 配置加载方式

使用 Go 标准库 `os.Getenv()` 读取进程环境变量。

**重要说明**：

1. Go 标准库不会自动读取 `.env` 文件
2. 当前配置读取依赖进程环境变量（由 shell 或 Makefile 传入）
3. `.env.example` 是模板，`.env` 由 `make init` 创建
4. 当前不在代码中自动读取 `.env` 文件，不引入 `godotenv`
5. 如果需要让 `make dev-server` 自动加载 `.env`，应单独开 Prompt 授权修改 Makefile
6. 辅助函数：`getEnv()`、`getEnvAsInt()`、`getEnvAsBool()`

## 7. 中间件方案

阶段 2-4 建议实现三个中间件：

### RequestLogger

记录以下信息：

| 字段 | 说明 |
|------|------|
| method | 请求方法 |
| path | 请求路径 |
| status | 响应状态码 |
| duration | 请求耗时 |
| remote_addr | 客户端地址 |
| user_agent | 用户代理 |

实现方式：使用 Go 标准库 `net/http` 的中间件模式（函数包装 `http.Handler`）。

### CORS

开发环境允许的来源：

```text
http://localhost:5173
http://127.0.0.1:5173
```

策略说明：

1. `local` 环境下使用较宽松策略
2. 允许 GET / POST / PUT / DELETE / OPTIONS
3. 允许 Content-Type / Authorization 请求头
4. 允许携带凭证（Credentials）
5. 文档中明确写清楚策略和原因

### Recover

1. 捕获 panic
2. 返回统一错误响应（code: 50000）
3. 记录 panic 堆栈到日志
4. 避免服务直接崩溃

## 10. 数据库 SQL 文件策略

### 约定

本项目 Demo 阶段不使用复杂迁移工具。

后续数据库表结构和种子数据统一写入：

```text
server/sql/init.sql
```

### 原因

1. 用户会频繁使用 `make up`、`make down`、`make restart`
2. 如需清空数据库，可使用危险命令清理 volume
3. 清理后可通过单 SQL 文件重新导入
4. 对 Demo 和比赛项目更直观
5. 降低迁移系统复杂度

### 数据卷与数据关系

| 命令 | 是否删除数据 | 说明 |
|------|------------|------|
| `make up` | ❌ 不删除 | 启动容器，保留数据 |
| `make down` | ❌ 不删除 | 停止容器，保留数据卷 |
| `make restart` | ❌ 不删除 | 重启容器，保留数据 |
| `make reset` | ✅ 删除 | 清空 volume，需手动确认 |

### 重要约定

1. `make up` / `make down` / `make restart` 不应清空数据
2. `make reset` 才会清空 volume
3. 后续如果要"清空 volume + 重新导入 init.sql"，需要单独设计明确命令
4. 不要在阶段 2 自动导入 SQL
5. 阶段 3 再写真实表结构和种子数据

6. 阶段 3 可以写业务接口、数据模型、repository、service
7. 阶段 3 可以写 JWT 认证
