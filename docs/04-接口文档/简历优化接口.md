# 简历优化接口

## 1. 接口背景

简历优化接口是 Offer 捕手系统的核心能力之一，基于目标岗位 JD 对用户当前简历提供投递前优化建议。该接口吸收了 4-3.5.B ~ 4-3.5.H 的战略转型成果，区分"投递前快速优化"和"长期提升"，给出明确的投递边界和停止信号。

## 2. 当前阶段定位

当前阶段（4-3.7）仅提供 Mock 业务链路：

- ✅ 已有 Mock Agent 返回稳定结果
- ❌ 未接入真实 LLM Pipeline
- ❌ 未修改 Prompt / Schema 文件
- ❌ 未实现 Quality Gate 工程逻辑
- ❌ 未修改前端

后续 4-3.8 将接入真实 LLM Pipeline。

## 3. 接口路径

```
POST /api/resumes/optimize
```

需要认证（Authorization: Bearer <token>）。

## 4. 请求方法

POST

## 5. 请求体

```json
{
  "resume_text": "用户当前简历文本",
  "target_job": {
    "job_id": "可选，岗位 ID",
    "title": "Go 后端开发工程师",
    "location": "深圳",
    "jd_text": "岗位 JD 原文或摘要"
  },
  "target_section": "可选，用户希望重点优化的简历段落",
  "user_intention": {
    "target_roles": ["Go 后端开发"],
    "expected_locations": ["深圳", "北京"],
    "accept_relocation": true
  }
}
```

### 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `resume_text` | string | ✅ 是 | 用户当前简历文本或 ResumeContextText |
| `target_job` | object | ✅ 是 | 目标岗位信息 |
| `target_job.job_id` | string | 否 | 岗位 ID（预留，暂不消费） |
| `target_job.title` | string | 条件必填 | 岗位标题，与 jd_text 至少一个 |
| `target_job.location` | string | 否 | 岗位地点 |
| `target_job.jd_text` | string | 条件必填 | 岗位 JD 原文，与 title 至少一个 |
| `target_section` | string | 否 | 用户希望重点优化的段落 |
| `user_intention` | object | 否 | 用户求职意向 |
| `user_intention.target_roles` | string[] | 否 | 目标岗位方向 |
| `user_intention.expected_locations` | string[] | 否 | 期望工作城市 |
| `user_intention.accept_relocation` | bool | 否 | 是否接受异地 |

## 7. 字段说明

### apply_readiness 枚举

| 值 | 定义 | 投递建议 |
|---|------|---------|
| `ready_to_apply` | 核心能力已覆盖 | 建议投递 |
| `quick_fix_before_apply` | 有匹配基础，2-3 个短时可修复问题 | 快速修复后投递 |
| `not_ready_for_this_role` | 与岗位关键要求差距明显 | 不建议投递该岗位 |
| `insufficient_information` | 信息不足，无法稳定判断 | 先补充信息 |

### optimization_stop_signal 枚举

| 值 | 对应 apply_readiness |
|---|---------------------|
| `stop_and_apply` | ready_to_apply |
| `fix_top_3_then_apply` | quick_fix_before_apply |
| `needs_more_evidence` | not_ready_for_this_role / insufficient_information |
| `target_role_mismatch` | not_ready_for_this_role |

### evidence_strength 枚举

| 值 | 定义 |
|---|------|
| `strong` | 直接、具体、可验证的经历证据 |
| `medium` | 有相关经历但表达不完整 |
| `weak` | 只有关键词或泛泛描述 |
| `missing` | 完全没有对应证据 |

### match_judgement 枚举

| 值 | 定义 |
|---|------|
| `matched` | 完全匹配 |
| `partially_matched` | 部分匹配 |
| `missing` | 未匹配 |
| `risky` | 有风险 |

### screening_risk 枚举

| 值 | 定义 |
|---|------|
| `keyword_missing` | 关键词缺失 |
| `responsibility_unclear` | 职责表达不清 |
| `result_missing` | 缺少成果 |
| `tech_stack_not_supported` | 技术栈不匹配 |
| `scope_unclear` | 范围不清 |
| `experience_missing` | 经验缺失 |
| `role_mismatch` | 角色不匹配 |
| `authenticity_risk` | 真实性风险 |
| `location_or_preference_risk` | 地点或偏好风险 |

## 8. Mock 返回策略

当前阶段使用 `ResumeOptimizationMockAgent` 返回 Mock 结果：

- `generated_by` 始终为 `mock_agent`
- `agent_status` 始终为 `mock_success`
- `fallback_required` 始终为 `false`
- `repair_applied` 始终为 `false`
- 根据简历文本和 JD 关键词重叠度判断 `apply_readiness`
- 简历文本过短（< 50 字符）时返回 `insufficient_information`
- `top_fix_items` 最多 3 项
- `long_term_improvement` 每项都包含"不建议延后当前投递"提醒
- 不使用"建议改为"，统一使用"示例参考"
- 不编造具体指标（QPS、DAU、百分比）

## 9. 参数校验规则

| 规则 | 错误码 | 错误信息 |
|------|--------|---------|
| `resume_text` 为空 | 40001 | resume_text is required |
| `resume_text` 仅空白 | 40001 | resume_text is required |
| `target_job` 为空 | 40001 | target_job is required |
| `target_job.title` 和 `target_job.jd_text` 都为空 | 40001 | target_job.title or target_job.jd_text is required |
| 请求体 JSON 格式错误 | 40001 | invalid request body |
| 未认证 | 40100 | unauthorized |

## 10. 与版本对比接口的区别

| 维度 | 版本对比 | 简历优化 |
|------|---------|---------|
| 接口路径 | GET /api/resumes/versions/compare | POST /api/resumes/optimize |
| 输入 | 两个简历版本号 | 简历文本 + 目标岗位 JD |
| 核心问题 | "我改了什么、变好了吗" | "我该怎么改才能通过初筛、什么时候可以投" |
| 战略关联 | 无 | 4-3.5 核心杀手锏之一 |
| apply_readiness | 无 | 有 |
| optimization_stop_signal | 无 | 有 |
| jd_evidence_chain | 无 | 有 |
| verification_notice | 无 | 有 |

## 11. 与 ResumeOptimizationAgent Pipeline 的关系

当前阶段通过 Mock Agent 返回结果，未接入 LLM Pipeline。后续 4-3.8 将实现：

1. LLM 优先 + Mock fallback（与 MatchAnalysis / Recommendation 一致）
2. Prompt / Schema 已预留（`resume_optimization_v1.md` / `resume_optimization_schema.json`）
3. Pipeline 已预留 `TargetResumeOptimization`

接入 Pipeline 后，Mock Agent 将作为 fallback 保障。

## 12. 安全边界

- 不编造经历、指标、项目、职责
- 不输出录用承诺
- 不评价用户本人能力，只评价"当前简历 x 当前岗位 JD"的匹配
- 不基于性别/年龄/家庭背景/地域/学校等判断
- verification_notice 提醒用户核实后使用
- 不泄露内部错误栈或 .env 信息

### 现状核验备注（4-4.0）

> 2026-05-31 核验

1. **meta 字段必填**：agent_status / generated_by / fallback_required / repair_applied 是必填字段（无 omitempty），与 Match/Rec 的 omitempty 不同
2. **fallback_required 存在**：ResumeOptimization 是三类 Agent 中唯一有 `fallback_required` 字段的
3. **agent_status Mock direct 值**：为 `"mock_success"`（Match/Rec 为 `"mock"`），4-4.1 应统一
4. **generated_by 双重设置**：`data.generated_by` 和 `data.result.generated_by` 同时存在
5. 详见 `docs/04-接口文档/三类Agent接口返回结构现状核验.md`

### 目标契约（4-4.1 冻结，待 4-4.2 落地）

> 2026-05-31 冻结

1. **新增 `data.meta`**：作为唯一可信状态来源，包含 agent_name / generated_by / agent_status / fallback_reason / error_code / repair_applied / schema_valid / request_id
2. **generated_by 唯一可信位置**：`data.meta.generated_by`，旧字段标记 deprecated
