# 统一接口返回契约设计

> 创建时间：2026-05-31
> 所属阶段：4-4.1
> 设计人：CodeBuddy
> 依据：4-4.0 三类 Agent 接口返回结构现状核验
> 状态：**已冻结** — 待 4-4.2 工程落地

## 1. 背景

4-4.0 已核验三类 Agent 接口当前返回结构，发现以下关键问题：

1. **meta 字段位置不一致**：MatchAnalysis/ResumeOptimization 的 meta 在 `data.result` 内，Recommendation 的在 `data.recommended_jobs[i]` 内
2. **agent_status 值不一致**：Mock direct 时 Match/Rec 为 `"mock"`，ResumeOpt 为 `"mock_success"`
3. **generated_by 双重设置**：`data.generated_by` 和业务结果内的 `generated_by` 同时存在
4. **fallback_required 仅 ResumeOptimization 有**：Match/Rec 缺失
5. **schema_valid / request_id 三类接口都缺失**
6. **omitempty 导致 Mock 时字段缺失**：前端需处理 undefined

本阶段只做契约设计冻结，不做工程改造。

## 2. 设计目标

1. 前端能从统一位置读取业务结果和系统状态
2. 前端能稳定识别五种返回路径：LLM success / JSON repair / LLM error fallback / Mock direct / handler error
3. 三类 Agent 接口返回结构一致，前端不需要三套适配逻辑
4. 兼容旧字段，不破坏已有测试

## 3. 当前问题摘要

| 问题 | 严重度 | 当前状态 |
|------|--------|---------|
| meta 字段位置不一致 | 🔴 高 | Match/ResumeOpt 在 result 内，Rec 在 jobs[i] 内 |
| agent_status Mock direct 值不一致 | 🔴 高 | Match/Rec: "mock"，ResumeOpt: "mock_success" |
| generated_by 双重设置 | 🔴 高 | data + result/jobs[i] 两层 |
| fallback_required 仅 ResumeOpt 有 | 🟡 中 | Match/Rec 缺失 |
| omitempty 导致字段缺失 | 🟡 中 | Mock direct 时部分字段不返回 |
| schema_valid 缺失 | 🟡 中 | 三类接口都没有 |
| request_id 缺失 | 🟢 低 | 三类接口都没有 |
| 接口文档示例滞后 | 🟡 中 | 未展示 LLM 后新增字段 |

## 4. 统一 Response Envelope

### 4.1 HTTP 外层（保持不变）

三类接口均保持现有 HTTP 外层 envelope：

```json
{
  "code": 0,
  "message": "ok",
  "data": { ... }
}
```

- `code`：0 表示成功，非 0 表示业务错误
- `message`：成功时为 "ok"，错误时为错误描述
- `data`：业务数据容器

### 4.2 data 内层（目标结构）

**目标结构**：

```json
{
  "data": {
    "result": { ... },
    "meta": {
      "agent_name": "match_analysis",
      "generated_by": "llm_agent",
      "agent_status": "success",
      "fallback_reason": "none",
      "error_code": "none",
      "repair_applied": false,
      "schema_valid": true,
      "request_id": ""
    }
  }
}
```

**职责边界**：

- `data.result`：只放业务结果，不含系统状态字段
- `data.meta`：只放系统状态、来源、fallback、repair、schema、trace 信息，不含业务字段

## 5. data.result 业务结果规则

### 5.1 MatchAnalysis

```json
{
  "data": {
    "result": {
      "match_score": 82,
      "screening_result": "likely",
      "apply_readiness": "quick_fix_before_apply",
      "optimization_stop_signal": "fix_top_3_then_apply",
      "top_fix_items": [],
      "evidence_chain": [],
      "match_highlights": [],
      "risk_points": [],
      "optimization_suggestions": [],
      "next_steps": [],
      "authenticity_notice": "...",
      "analysis_basis": { ... }
    },
    "meta": { ... }
  }
}
```

**保留辅助字段**：`analysis_id`、`created_at` 放在 `data` 顶层（与 result/meta 同级）。

### 5.2 Recommendation

**必须将 `recommended_jobs` 放入 `data.result.recommended_jobs`**。

```json
{
  "data": {
    "result": {
      "recommended_jobs": [
        {
          "job_id": 1,
          "title": "Go 后端开发工程师",
          "priority": "strong_recommend",
          "recommendation_score": 95,
          "recommendation_reason": "...",
          "match_highlights": [],
          "risk_points": [],
          "suggested_action": "...",
          "apply_readiness": "quick_fix_before_apply",
          "optimization_stop_signal": "fix_top_3_then_apply",
          "top_fix_items": []
        }
      ]
    },
    "meta": { ... }
  }
}
```

**不再让 Recommendation 直接在 `data` 层放 `recommended_jobs`**。

原因：三类 Agent 前端适配必须统一从 `data.result` 读取业务结果。

**保留辅助字段**：`resume_version_id`、`resume_version_no`、`summary`、`created_at` 放在 `data` 顶层（与 result/meta 同级）。

### 5.3 ResumeOptimization

```json
{
  "data": {
    "result": {
      "apply_readiness": "quick_fix_before_apply",
      "optimization_stop_signal": "fix_top_3_then_apply",
      "top_fix_items": [],
      "summary": "...",
      "long_term_improvement": [],
      "jd_evidence_chain": [],
      "verification_notice": "..."
    },
    "meta": { ... }
  }
}
```

**保留辅助字段**：`optimization_id`、`created_at` 放在 `data` 顶层（与 result/meta 同级）。

## 6. data.meta 系统状态规则

### 6.1 meta 字段总览

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| agent_name | string | ✅ | Agent 名称标识 |
| generated_by | string | ✅ | 结果来源 |
| agent_status | string | ✅ | Agent 状态 |
| fallback_reason | string | ✅ | fallback 原因 |
| error_code | string | ✅ | 错误码 |
| repair_applied | bool | ✅ | 是否经过 JSON repair |
| schema_valid | bool | ✅ | 最终结果是否满足契约 |
| request_id | string | ✅ | 请求追踪 ID |

**所有 meta 字段均为必填，不使用 omitempty**。

## 7. agent_name 规则

### 7.1 类型

`string`

### 7.2 枚举

| 值 | 说明 |
|---|------|
| `match_analysis` | 匹配分析 Agent |
| `recommendation` | 推荐 Agent |
| `resume_optimization` | 简历优化 Agent |

### 7.3 用途

前端识别当前结果属于哪个 Agent，便于统一处理或按类型分发。

## 8. generated_by 规则

### 8.1 类型

`string`

### 8.2 枚举

| 值 | 说明 |
|---|------|
| `llm_agent` | LLM 生成（success 或 repaired） |
| `mock_agent` | Mock 生成（fallback 或 Mock direct） |

### 8.3 规则

| 场景 | generated_by |
|------|-------------|
| LLM success | `llm_agent` |
| LLM repaired | `llm_agent` |
| LLM error fallback | `mock_agent` |
| Mock direct | `mock_agent` |

### 8.4 唯一可信位置

```
data.meta.generated_by
```

**不再使用双层 generated_by**。`data.result` / `data.result.recommended_jobs[i]` 内的 `generated_by` 保留但标记 deprecated，前端不应读取。

### 8.5 旧字段处理

- `data.generated_by`（顶层）：保留但标记 **deprecated**，前端不应读取
- `data.result.generated_by` / `data.recommended_jobs[i].generated_by`：保留但标记 **deprecated**

## 9. agent_status 枚举

### 9.1 类型

`string`

### 9.2 枚举

| 值 | 含义 |
|---|------|
| `success` | LLM 正常成功，未 repair，未 fallback |
| `repaired` | LLM 原始输出异常，JSON repair 成功，使用修复后结果 |
| `fallback` | LLM 调用失败或 repair 失败，使用 Mock fallback 返回可用结果 |
| `mock_success` | LLM 未启用或主动使用 Mock，Mock 直接返回成功 |
| `error` | 没有可用结果，接口返回错误 |

### 9.3 统一要求

**Mock direct 一律使用 `mock_success`**，不再使用 `mock`。

### 9.4 与 generated_by 的对应关系

| agent_status | generated_by |
|-------------|-------------|
| success | llm_agent |
| repaired | llm_agent |
| fallback | mock_agent |
| mock_success | mock_agent |
| error | mock_agent 或 llm_agent（视错误来源） |

## 10. fallback_reason 枚举

### 10.1 类型

`string`

### 10.2 枚举

| 值 | 说明 |
|---|------|
| `none` | 无 fallback |
| `llm_disabled` | LLM 未启用 |
| `llm_error` | LLM 调用出错 |
| `llm_timeout` | LLM 响应超时 |
| `json_parse_failed` | LLM 输出 JSON 解析失败 |
| `json_repair_failed` | JSON repair 修复失败 |
| `schema_invalid` | LLM 输出 Schema 校验失败 |
| `pipeline_error` | Agent Pipeline 执行异常 |
| `unknown` | 未知原因 |

### 10.3 规则

| agent_status | fallback_reason |
|-------------|----------------|
| success | `none` |
| repaired | `none` |
| mock_success | `none` |
| fallback | **必须为非 none** |
| error | 如有错误来源，填写对应 reason |

## 11. error_code 枚举

### 11.1 类型

`string`

### 11.2 枚举

| 值 | 说明 |
|---|------|
| `none` | 无错误 |
| `LLM_DISABLED` | LLM 未启用 |
| `LLM_ERROR` | LLM 调用出错 |
| `LLM_TIMEOUT` | LLM 响应超时 |
| `JSON_PARSE_FAILED` | LLM 输出 JSON 解析失败 |
| `JSON_REPAIR_FAILED` | JSON repair 修复失败 |
| `SCHEMA_INVALID` | LLM 结果结构不符合契约 |
| `PIPELINE_ERROR` | Agent Pipeline 执行异常 |
| `MOCK_FALLBACK_USED` | 当前展示兜底结果 |
| `VALIDATION_ERROR` | 请求参数不完整或格式错误 |
| `INTERNAL_ERROR` | 服务内部异常 |
| `UNKNOWN_ERROR` | 未知异常 |

### 11.3 规则

| 场景 | error_code |
|------|-----------|
| success / repaired / mock_success | `none` |
| fallback | 可以是触发 fallback 的原因（如 `LLM_ERROR` / `JSON_REPAIR_FAILED` / `SCHEMA_INVALID`） |
| error | 必须稳定可识别 |

### 11.4 注意

`error_code` 用于前端判断状态展示，不等同于 HTTP `code`。

## 12. repair_applied 规则

### 12.1 类型

`bool`

### 12.2 规则

| 场景 | repair_applied | agent_status |
|------|---------------|-------------|
| LLM 正常成功 | `false` | success |
| LLM 原始输出异常，repair 成功使用修复结果 | `true` | repaired |
| LLM repair 失败，fallback 到 Mock | `false` | fallback |
| Mock direct | `false` | mock_success |

### 12.3 与 agent_status 对应

- `repair_applied = true` 时，`agent_status` 必须为 `repaired`
- `agent_status = repaired` 时，`repair_applied` 必须为 `true`

## 13. schema_valid 规则

### 13.1 类型

`bool`

### 13.2 规则

| 场景 | schema_valid |
|------|-------------|
| 最终返回的 result 满足当前后端契约 | `true` |
| 最终 result 不满足契约，且无法 fallback | `false`（agent_status = error） |

### 13.3 说明

- `schema_valid` 表示**最终返回结构**可被前端消费，不是指 LLM 原始输出是否合法
- 只要前端能稳定消费 result，schema_valid 就应为 true
- 只有极端异常（无法生成任何可用结果）时 schema_valid 才为 false

## 14. request_id 规则

### 14.1 类型

`string`

### 14.2 规则

- 每次接口响应都应有 `request_id`
- 如当前请求链路已有 `request_id`，应透传
- 4-4.2 可根据当前工程能力决定先填空字符串还是生成简单 ID

### 14.3 用途

- 前端报错时附上 request_id
- 日志排查和问题定位
- 演示问题追踪

### 14.4 4-4.1 决策

`request_id` 是目标字段。4-4.2 可以根据工程能力选择：
- 方案 A：生成 UUID 或时间戳+随机数
- 方案 B：先填空字符串，后续阶段再实现

## 15. 兼容旧字段策略

### 15.1 策略

1. 4-4.2 **新增** `data.meta` 作为唯一可信状态来源
2. **短期保留** result / recommended_jobs[i] 内现有 `generated_by` / `agent_status` / `fallback_reason` / `error_code` / `repair_applied` / `fallback_required` 字段，避免破坏已有测试
3. **文档明确**前端只能读取 `data.meta`
4. **后续阶段**再决定是否清理 result 内重复 meta 字段
5. `data.generated_by` 顶层旧字段不再作为可信来源，若保留也标记 **deprecated**

### 15.2 唯一可信来源

```
data.meta.generated_by
data.meta.agent_status
data.meta.fallback_reason
data.meta.error_code
data.meta.repair_applied
data.meta.schema_valid
data.meta.request_id
```

### 15.3 deprecated 字段（4-4.2 保留，前端不应读取）

```
data.generated_by                    → deprecated
data.result.generated_by             → deprecated
data.result.agent_status             → deprecated
data.result.fallback_reason          → deprecated
data.result.error_code               → deprecated
data.result.repair_applied           → deprecated
data.result.fallback_required        → deprecated（ResumeOptimization 特有）
data.recommended_jobs[i].generated_by   → deprecated
data.recommended_jobs[i].agent_status   → deprecated
data.recommended_jobs[i].fallback_reason → deprecated
data.recommended_jobs[i].error_code     → deprecated
data.recommended_jobs[i].repair_applied → deprecated
```

## 17. 前端展示规则

### 17.1 LLM success

**条件**：

```
meta.generated_by = "llm_agent"
meta.agent_status = "success"
meta.repair_applied = false
```

**前端展示**：

- 正常结果
- 显示"LLM 生成"标识
- 不显示 warning

### 17.2 Repaired

**条件**：

```
meta.generated_by = "llm_agent"
meta.agent_status = "repaired"
meta.repair_applied = true
```

**前端展示**：

- 正常结果
- 显示"已自动修复结构"轻量提示
- 不打断用户

### 17.3 Fallback

**条件**：

```
meta.generated_by = "mock_agent"
meta.agent_status = "fallback"
meta.fallback_reason != "none"
```

**前端展示**：

- 显示可用结果
- 显示"已使用兜底结果"提示
- 展示 `fallback_reason` 的友好说明
- 不展示系统错误堆栈

### 17.4 Mock direct

**条件**：

```
meta.generated_by = "mock_agent"
meta.agent_status = "mock_success"
```

**前端展示**：

- 显示 Mock / 演示结果标签
- 用于本地 Demo 或 LLM 未启用场景

### 17.5 Error

**条件**：

```
meta.agent_status = "error"
或 code != 0
```

**前端展示**：

- 显示错误态
- 展示 `error_code` 的友好说明
- 允许用户重试

## 18. error_code 到前端文案映射
