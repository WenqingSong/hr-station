## 1. 背景

当前项目已完成到阶段 4-3.7（简历优化业务链路补齐），4-3.7.B.0 已完成项目启动与部署现状核验。核验发现以下主要问题：

1. 无 Nginx 统一入口，前后端分离访问，CORS 风险
2. CORS Origin 硬编码 localhost，生产部署时不可用
3. README 严重过时，仍显示"阶段 1"
4. 前后端不在 Docker 中，本地进程管理不利于部署
5. 无生产环境配置，开发/部署环境未区分
6. 前端无 API 对接层，全部硬编码 Mock
7. .env.example 含疑似真实 API Key

用户目标是实现专业化一键启动、Nginx 代理、CORS 修复、开发/部署环境区分和上线部署准备。本阶段只做方案设计，不修改工程文件。

## 3. 标准化目标

1. `make up` 一键启动整个项目（含 Nginx）
2. `make restart` 安全重启，不清空 volume
3. 破坏性命令（清 volume）必须 CONFIRM=yes
4. 后端和前端都后台运行
5. 所有 make 指令运行成功后打印专业信息
6. Nginx 反向代理统一入口
7. 后端 CORS 配置化，避免前端 CORS 问题
8. 明确开发环境和部署环境
9. 为平台上线部署做好准备
10. README 全面更新

## 4. 总体设计原则

1. **渐进改造**：按 B.2 ~ B.8 分阶段实施，每阶段可独立验证
2. **开发优先**：先保证开发环境稳定，再扩展部署环境
3. **安全第一**：破坏性命令必须确认，密钥不入仓库
4. **语义清晰**：命令名称和行为语义一致，避免歧义
5. **同源优先**：Nginx 代理后前端走 /api 同源，减少 CORS 依赖
6. **配置外置**：CORS Origin、端口、环境变量均可通过 .env 配置

## 5. Makefile 标准化方案

### 5.1 命令分组

建议后续 Makefile 命令按以下分组组织：

```
基础命令：
  make help          查看所有命令
  make doctor        检查开发环境
  make ensure-env    确保 .env 存在
  make init          初始化开发环境

开发环境：
  make up            一键启动完整开发环境
  make down          停止所有服务，保留 volume
  make stop          停止前后端进程，保留 Docker
  make restart       软重启（stop + up，不清 volume）
  make restart-soft  同 restart
  make reset         关闭并清空 volume（需 CONFIRM=yes）
  make reset-up      清空 volume 后重新启动（需 CONFIRM=yes）
  make status        查看服务运行状态
  make ps            显示容器状态
  make health        聚合健康检查
  make logs          聚合日志
  make backend-logs  后端日志
  make frontend-logs 前端日志（= web-logs）
  make nginx-logs    Nginx 日志
  make db-logs       MySQL 日志

后端：
  make backend-up / backend-stop / backend-restart / backend-status / backend-health

前端：
  make web-install / web-up / web-stop / web-restart / web-status / web-health

数据库：
  make db-import / db-reset / db-shell / db-check

测试与检查：
  make test / backend-test / frontend-check / lint / build / ci

Agent / LLM：
  make agent-env / agent-check / llm-help / llm-check / llm-smoke

部署预留：
  make prod-build    构建生产镜像
  make prod-up       启动生产环境
  make prod-down     停止生产环境
  make prod-logs     查看生产日志

清理：
  make clean / clean-logs / clean-pids / clean-volume
```

### 5.2 命令命名统一

当前 Makefile 中前端命令使用 `web-*` 前缀（如 `web-up`、`web-logs`），与日志命令 `logs-web` 存在命名不一致。

建议：
- 保留 `web-*` 命令（已使用较久，改动成本高）
- 新增 `frontend-logs` / `nginx-logs` 作为日志命令别名
- `backend-logs` 已有（等同于 `logs-backend`）

## 7. restart / reset / reset-up 命令语义

### 7.1 主推荐方案

| 命令 | 行为 | 清空 volume | 需要 CONFIRM |
|------|------|------------|-------------|
| `make restart` | 软重启 = stop + up | ❌ 否 | ❌ 否 |
| `make restart-soft` | 同 restart | ❌ 否 | ❌ 否 |
| `make reset` | 停止 + 清空 volume | ✅ 是 | ✅ 是 |
| `make reset-up` | 停止 + 清空 volume + 重启 | ✅ 是 | ✅ 是 |

### 7.2 设计理由

1. **restart 在行业习惯中通常不代表删除数据**：`docker compose restart` 不删 volume，`make restart` 也应保持一致
2. **清空 volume 是破坏性操作**：容易误删数据库，必须明确确认
3. **开发阶段可以提供 reset-up**：满足用户"快速重置"需求，但有 CONFIRM 保护
4. **生产环境必须禁止清空 volume**：reset/reset-up 仅开发环境可用
5. **命令语义清楚比"一个命令做所有事"更专业**

### 7.3 备选方案（不推荐）

如果用户坚持 `make restart` 必须清空 volume：

| 命令 | 行为 | 需要 CONFIRM |
|------|------|-------------|
| `make restart` | 停止 + 清空 volume + 重启 | ✅ 是 |
| `make restart-soft` | 软重启 = stop + up | ❌ 否 |

不推荐原因：`restart` 隐含破坏性违反行业惯例，容易误操作。

### 7.4 当前 Makefile 现状对比

| 当前命令 | 当前行为 | 标准化后行为 | 变更 |
|---------|---------|------------|------|
| `make restart` | stop + up（不清 volume） | 不变 | 无 |
| `make rebuild` | 清理 + 重建（需 CONFIRM） | 保留或重命名 | 小改 |
| - | - | `make reset` 新增 | 新增 |
| - | - | `make reset-up` 新增 | 新增 |
| - | - | `make restart-soft` 新增 | 新增 |

所有破坏性命令必须 CONFIRM=yes：

## 8. Docker Compose 标准化方案

### 8.1 文件结构

```
docker-compose.yml         # 基础服务定义（公共 network、volume）
docker-compose.dev.yml     # 开发环境覆盖（挂载源码、暴露调试端口）
docker-compose.prod.yml    # 生产环境覆盖（构建镜像、不挂载源码）
```

### 8.2 docker-compose.yml（基础）

定位：定义所有服务的公共配置，不含环境特化。

```yaml
services:
  mysql:
    image: mysql:8.0
    # ... 现有配置保留 ...

  backend:
    build:
      context: ./server
      dockerfile: Dockerfile
    environment:
      - APP_ENV=${APP_ENV:-local}
      - DB_HOST=${DB_HOST:-mysql}
      - DB_PORT=${DB_PORT:-3306}
      - SERVER_PORT=${SERVER_PORT:-8080}
      - CORS_ALLOWED_ORIGINS=${CORS_ALLOWED_ORIGINS:-http://localhost,http://localhost:5173}
    depends_on:
      mysql:
        condition: service_healthy
    networks:
      - offer_catcher_net

  frontend:
    build:
      context: ./web
      dockerfile: Dockerfile
    environment:
      - VITE_API_BASE_URL=/api
    networks:
      - offer_catcher_net

  nginx:
    image: nginx:alpine
    ports:
      - "${NGINX_PORT:-80}:80"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
    depends_on:
      - backend
      - frontend
    networks:
      - offer_catcher_net

volumes:
  mysql_data:

networks:
  offer_catcher_net:
    driver: bridge
```

### 8.3 docker-compose.dev.yml（开发环境）

定位：本地开发环境覆盖，挂载源码、暴露调试端口。

```yaml
services:
  backend:
    command: go run ./cmd/server
    volumes:
      - ./server:/app
    ports:
      - "${SERVER_PORT:-8080}:8080"  # 暴露用于调试
    environment:
      - APP_ENV=development

  frontend:
    command: npm run dev -- --host 0.0.0.0
    volumes:
      - ./web:/app
      - /app/node_modules
    ports:
      - "${WEB_PORT:-5173}:5173"  # 暴露用于调试
    environment:
      - VITE_API_BASE_URL=http://localhost:8080/api
```

### 8.4 docker-compose.prod.yml（生产环境）

定位：部署环境，使用构建后的静态资源和二进制。

```yaml
services:
  backend:
    # 使用预构建镜像
    image: offer-catcher-backend:latest
    environment:
      - APP_ENV=production
    # 不暴露端口，只通过 Nginx 访问
    expose:
      - "8080"
    # 不挂载源码

  frontend:
    # 前端构建产物由 Nginx 直接托管
    # 此服务可以省略，Nginx 直接 serve 静态文件

  nginx:
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/ssl:/etc/nginx/ssl:ro  # HTTPS 证书

  mysql:
    # 不暴露 3306 到宿主机
    ports: !override []
```

### 8.5 启动命令

```bash
# 开发环境
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d

# 生产环境
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

### 8.6 渐进实施策略

考虑到当前 Makefile 通过本地进程管理前后端，建议 B.3 阶段不立即全量容器化，而是：

1. **B.3 先接入 Nginx**：在 docker-compose.yml 中新增 nginx 服务
2. **B.3 前后端仍本地进程**：保持当前 PID 管理方式
3. **后续可选容器化**：如果需要完整 Docker 化，再新增 backend / frontend 容器

这样可以在不大幅改动现有启动脚本的情况下，先获得 Nginx 统一入口的好处。

## 10. Nginx 统一入口方案

### 10.1 目标

统一入口：`http://localhost/`

- `/` → frontend（前端页面）
- `/api/` → backend:8080（后端 API）
- `/healthz` → backend:8080/healthz（健康检查）

### 10.2 推荐代理策略

```nginx
server {
    listen 80;
    server_name localhost;

    # 前端页面
    location / {
        proxy_pass http://frontend:5173;    # 开发环境
        # 或 root /usr/share/nginx/html;    # 生产环境（静态文件）
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Vite HMR WebSocket 支持
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }

    # 后端 API
    location /api/ {
        proxy_pass http://backend:8080/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # SSE / 长连接支持预留
        proxy_buffering off;
        proxy_read_timeout 300s;
    }

    # 健康检查
    location /healthz {
        proxy_pass http://backend:8080/healthz;
        access_log off;
    }
}
```

### 10.3 配置文件结构

```
nginx/
├── conf.d/
│   └── default.conf    # 主站点配置
└── ssl/                # HTTPS 证书（生产环境，不入仓库）
    ├── cert.pem
    └── key.pem
```

### 10.4 关键设计决策

1. **前端默认走 Nginx `/`**：不直接访问 :5173
2. **API 默认走 Nginx `/api`**：不直接访问 :8080
3. **Vite HMR WebSocket 代理**：开发环境需要
4. **SSE / 长连接预留**：proxy_buffering off + proxy_read_timeout
5. **Nginx 统一入口可减少 CORS 问题**：前端和后端同源

### 10.5 开发环境直连模式

开发时也可以选择直连模式（不走 Nginx）：

```env
# 直连模式：前端直连后端 8080
VITE_API_BASE_URL=http://localhost:8080/api

# Nginx 代理模式：前端走 /api 同源
VITE_API_BASE_URL=/api
```

## 11. 后端 CORS 配置化方案

### 11.1 当前问题

```go
// 当前硬编码
var allowedOrigins = map[string]bool{
    "http://localhost:5173": true,
    "http://127.0.0.1:5173": true,
}

// isAllowedOrigin() 允许任何 localhost 端口（宽松）
```

问题：
- 生产部署时需修改代码
- 不支持动态域名
- isAllowedOrigin 宽松策略在生产不安全

### 11.2 配置化方案

新增环境变量：

```env
# CORS 允许的 Origin，逗号分隔
CORS_ALLOWED_ORIGINS=http://localhost,http://localhost:5173,http://127.0.0.1:5173

# CORS 允许的方法
CORS_ALLOWED_METHODS=GET,POST,PUT,PATCH,DELETE,OPTIONS

# CORS 允许的 Headers
CORS_ALLOWED_HEADERS=Content-Type,Authorization,X-Requested-With
```

### 11.3 Go 代码改造方向

```go
func NewCORSMiddleware() func(http.Handler) http.Handler {
    origins := strings.Split(os.Getenv("CORS_ALLOWED_ORIGINS"), ",")
    allowedSet := make(map[string]bool)
    for _, o := range origins {
        o = strings.TrimSpace(o)
        if o != "" {
            allowedSet[o] = true
        }
    }

    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            origin := r.Header.Get("Origin")
            if allowedSet[origin] {
                w.Header().Set("Access-Control-Allow-Origin", origin)
            }
            // ... 其余 CORS 头 ...
        })
    }
}
```

### 11.4 环境区分

| 环境 | CORS_ALLOWED_ORIGINS | 说明 |
|------|---------------------|------|
| 开发 | `http://localhost,http://localhost:5173,http://127.0.0.1:5173` | 允许 localhost |
| 生产 | `https://your-domain.com` | 只允许正式域名 |

### 11.5 Nginx 同源后 CORS 收紧

Nginx 接入后，前端通过 `/api` 同源请求后端，CORS 理论上不再必需。但建议保留 CORS 配置：

1. 开发直连模式仍需要 CORS
2. API 可能被第三方调用
3. Nginx 代理是运维层面，CORS 是应用层面，不应互相替代

## 12. 前端 API 配置方案

### 12.1 当前问题

- VITE_API_BASE_URL 预留但未使用
- 全部硬编码 Mock 数据
- 无 axios 实例 / api 目录

### 12.2 配置策略

| 模式 | VITE_API_BASE_URL | 适用场景 |
|------|-------------------|---------|
| 开发直连 | `http://localhost:8080/api` | 不走 Nginx，直连后端 |
| Nginx 代理 | `/api` | 走 Nginx 统一入口 |
| 生产部署 | `/api` | Nginx 托管 |

### 12.3 推荐主方案

**前端默认使用 `/api`**，通过 Nginx 代理访问后端。

### 12.4 Vite proxy 配置（本地 dev 不走 Nginx 时）

```typescript
// vite.config.ts
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
      },
    },
  },
});
```

### 12.5 三层代理关系

```
场景 1：make up（Nginx 模式）
  浏览器 → Nginx :80 → /api → backend :8080

场景 2：Vite dev proxy（无 Nginx）
  浏览器 → Vite :5173 → /api proxy → backend :8080

场景 3：直连（开发调试）
  浏览器 → Vite :5173 → http://localhost:8080/api（需 CORS）
```

**主推荐场景 1，开发备选场景 2，场景 3 仅调试用。**

## 13. 开发环境与部署环境区分

### 13.1 环境类型定义

| 环境 | APP_ENV | 说明 |
|------|---------|------|
| 本地开发 | `development` | 本地 npm run dev + go run |
| 容器化开发 | `development` | Docker Compose + 源码挂载 |
| 生产部署 | `production` | Docker Compose + 构建镜像 |

沿用当前项目 `APP_ENV` 变量，但值从 `local` 扩展为 `development` / `production`。

### 13.2 开发环境特征

- 允许 localhost CORS
- 允许暴露 MySQL 端口到宿主机
- 允许 `make reset` / `make reset-up`
