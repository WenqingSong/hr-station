# 阶段1工程初始化方案

阶段 1 不做业务功能，只完成工程初始化能力。

阶段 1 完成后，项目应具备：

1. 可重复启动的开发环境
2. 可恢复的云原生开发环境
3. 标准 Makefile 入口
4. 标准环境变量示例
5. 可用的 Docker Compose 基础服务（MySQL）
6. 初始化完成的 Go 后端工程结构
7. 前后端本地运行说明
8. 阶段 2 后端基础设施开发的准备条件

## 2. CNB 云原生开发环境重启场景

用户会反复重启云原生开发环境，工程方案必须明确：

| 场景 | 恢复策略 |
|------|---------|
| 环境重启后如何快速恢复 | `make doctor` 检查 → `make init` 补齐 → `make up` 启动服务 |
| `.env` 不存在时 | `make init` 从 `.env.example` 复制 |
| 前端依赖丢失时 | `make init` 执行 `npm install` |
| Docker 服务停止后 | `make up` 重新启动，数据卷保留 |
| MySQL 容器重新启动 | `make up` 启动，`make restart` 重启，数据卷不丢失 |
| Go 依赖重新下载 | `make dev-server` 时 `go mod download` 自动恢复 |
| 检查环境是否可用 | `make doctor` 只读检查 |
| 避免误删数据库卷 | `make down` 不删除卷，`make reset` 才删除（需确认） |
| 通过 Makefile 暴露稳定入口 | 所有操作通过 `make` 命令执行 |
| 降低重复初始化破坏风险 | 所有命令幂等，重复执行不破坏环境 |

### 核心恢复命令链路

```bash
# 1. 检查环境
make doctor

# 2. 初始化（幂等，可重复执行）
make init

# 3. 启动基础服务
make up

# 4. 启动前端开发
make dev-web

# 5. 启动后端开发
make dev-server
```

### 辅助命令

```bash
make status      # 查看容器状态
make logs        # 查看服务日志
make logs-mysql  # 查看 MySQL 日志
make down        # 停止服务（不删卷）
make restart     # 重启服务
```

## 3. Makefile 设计方案

### 设计目标

1. 云环境重启后快速恢复
2. 本地开发命令统一
3. 前端、后端、Docker 服务分开控制
4. 后续阶段持续扩展
5. 新模型 / 新开发者快速接手

### 命令规划

| 命令 | 目标 | 只读 | 有副作用 | 适合重启后执行 |
|------|------|------|---------|--------------|
| `make help` | 查看所有命令 | ✅ | ❌ | ✅ |
| `make doctor` | 只读检查开发环境 | ✅ | ❌ | ✅ |
| `make init` | 初始化开发环境（复制 .env、安装依赖） | ❌ | ⚠️ 创建文件 | ✅ |
| `make up` | 启动 docker-compose 服务 | ❌ | ⚠️ 启动容器 | ✅ |
| `make down` | 停止 docker-compose 服务（不删卷） | ❌ | ⚠️ 停止容器 | ❌ |
| `make restart` | 重启 docker-compose 服务 | ❌ | ⚠️ 重启容器 | ✅ |
| `make status` | 查看容器状态 | ✅ | ❌ | ✅ |
| `make logs` | 查看全部服务日志 | ✅ | ❌ | ✅ |
| `make logs-mysql` | 查看 MySQL 日志 | ✅ | ❌ | ✅ |
| `make dev-web` | 启动前端开发服务 | ❌ | ⚠️ 启动进程 | ✅ |
| `make dev-server` | 启动后端开发服务 | ❌ | ⚠️ 启动进程 | ✅ |
| `make dev` | 输出开发启动提示 | ✅ | ❌ | ✅ |
| `make build-web` | 构建前端 | ❌ | ⚠️ 生成产物 | ❌ |
| `make build-server` | 构建后端 | ❌ | ⚠️ 生成产物 | ❌ |
| `make build` | 构建前后端 | ❌ | ⚠️ 生成产物 | ❌ |
| `make test-server` | 运行后端测试 | ✅ | ❌ | ✅ |
| `make check` | 执行基础检查 | ✅ | ❌ | ✅ |
| `make clean` | 清理构建产物 | ❌ | ⚠️ 删除产物 | ❌ |
| `make reset` | ⚠️ 危险：停止并清理容器卷 | ❌ | 🔴 删除数据 | ❌ |

### 关键规则

1. `make doctor` 只检查，不修改任何文件
2. `make init` 幂等：`.env` 已存在则跳过，依赖已安装则跳过
3. `make up` 只启动 Docker Compose
4. `make reset` 必须在说明中标记为危险命令
5. 不把真实密钥写进 Makefile
6. 命令尽量幂等，重复执行不破坏环境
7. 命令失败时输出清晰提示

### `make doctor` 检查项

```
✓ Go 是否安装
✓ Node.js 是否安装
✓ npm 是否安装
✓ docker 是否安装
✓ docker-compose 是否安装
✓ .env 是否存在
✓ node_modules 是否存在
✓ go.mod 是否存在
✓ MySQL 容器是否运行
✓ 端口 3306 是否可用
✓ 端口 5173 是否可用
✓ 端口 8080 是否可用
```

### `make init` 执行项

```
1. 如果 .env 不存在，从 .env.example 复制
2. 如果 node_modules 不存在，执行 npm install
3. 如果 go.mod 不存在，执行 go mod init
4. 输出初始化完成提示
```

## 4. 环境变量方案

### .env.example 内容

```env
# 应用环境
APP_ENV=local

# 前端端口
WEB_PORT=5173

# 后端端口
SERVER_PORT=8080

# MySQL
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=offer_catcher
DB_USER=root
DB_PASSWORD=password
DB_DSN=root:password@tcp(127.0.0.1:3306)/offer_catcher?charset=utf8mb4&parseTime=True&loc=Local

# JWT
JWT_SECRET=change-me-in-local

# LLM（阶段 4 使用）
LLM_BASE_URL=
LLM_API_KEY=
LLM_MODEL=
```

### 规则

1. `.env.example` 可以提交到 git
2. `.env` 不提交，加入 `.gitignore`
3. 本地开发时由 `make init` 从 `.env.example` 复制
4. LLM 相关变量阶段 4 才真正使用，阶段 1 留空
5. 阶段 1 只规划，不接模型

### Docker Compose 内部服务名差异

| 场景 | DB_HOST | 说明 |
|------|---------|------|
| 本地运行（make dev-server） | `127.0.0.1` | Go 直接连本地 Docker MySQL |
| Docker Compose 内运行 | `mysql` | 服务名作为主机名 |

阶段 1 默认使用本地运行模式，DB_HOST 为 `127.0.0.1`。

## 5. Docker Compose 方案

### 第一版规划：只稳定 MySQL

```yaml
version: '3.8'
services:
  mysql:
    image: mysql:8.0
    container_name: offer-catcher-mysql
    restart: unless-stopped
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: password
      MYSQL_DATABASE: offer_catcher
      MYSQL_CHARSET: utf8mb4
      MYSQL_COLLATION: utf8mb4_unicode_ci
    volumes:
      - mysql_data:/var/lib/mysql

volumes:
  mysql_data:
```

### 为什么第一版只稳定 MySQL

1. CNB 开发环境中，前端和后端更适合通过本地命令开发，便于热更新
2. MySQL 更适合通过 Docker 保持一致
3. 阶段 1 先降低复杂度
4. 阶段 2 后端基础设施再连接数据库
5. 阶段 7 交付部署时再考虑完整容器化 web/server

### 数据卷保护

| 命令 | 是否删除数据卷 |
|------|--------------|
| `make down` | ❌ 不删除 |
| `make restart` | ❌ 不删除 |
| `make reset` | ✅ 删除（危险操作，需确认） |

### 各阶段 Docker 扩展计划

| 阶段 | 新增服务 |
|------|---------|
| 阶段 1 | mysql |
| 阶段 2 | 无（后端连已有 MySQL） |
| 阶段 3 | 无 |
| 阶段 4 | 无 |
| 阶段 7 | redis、web、server（完整容器化） |

| 业务接口 | 阶段 3 |
| Agent / Mock | 阶段 3 |
| 模型接入 | 阶段 4 |

### `main.go` 最小实现

```go
package main

import (
    "log"
    "net/http"

    "github.com/gin-gonic/gin"
)

func main() {
    r := gin.Default()
    r.GET("/healthz", func(c *gin.Context) {
        c.JSON(http.StatusOK, gin.H{"status": "ok"})
    })
    log.Println("Server starting on :8080")
    if err := r.Run(":8080"); err != nil {
        log.Fatal(err)
    }
}
```

### Go 依赖
