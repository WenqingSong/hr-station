## 1. 背景

项目在 4-3.7.B 阶段经历了方案 A（全容器开发模式）和方案 B（混合式开发环境）的评估。

方案 A 已在 `backup/full-container-dev` 分支保留（HEAD: 86335ee），包含 B.3 ~ B.5 的完整改造：
- B.3 Nginx 接入与 Docker Compose 标准化（commit: 64816bb）
- B.3.1 全容器开发模式补齐（commit: 21aeec5）
- B.4 后端 CORS 与代理策略修复（commit: 2e4cb6b）
- B.5 开发环境与部署环境区分（commit: 86335ee）

经过评估，决定采用方案 B：混合式开发环境。本分支 `rework/hybrid-dev` 从 B.2 稳定点 `d9432c0` 开出，不直接继承方案 A 的任何改造。

## 2. 为什么从方案 A 调整为方案 B

1. **当前项目核心目标是 Demo 稳定交付和开发效率**，而非云原生架构完备性
2. **全容器开发虽然更云原生，但对当前阶段过重**：后端容器热重启、前端容器 HMR、node_modules volume、Go module cache volume 等配置复杂度高，调试困难
3. **Go 后端本机运行更利于调试**：可以直接使用 IDE 断点、dlv 调试、实时修改代码，无需处理容器挂载延迟
4. **Vite 本机运行更利于 HMR**：原生文件系统监听，无容器 inotify 限制，热更新响应更快
5. **MySQL / Nginx 用容器即可保证基础设施一致性**：这两个服务不需要频繁修改代码，容器化收益高成本低
6. **make up 对用户仍然是一键启动完整项目**：内部实现差异对用户透明
7. **内部实现不必强制所有服务容器化**：选择每项服务的最优运行方式即可
8. **生产部署后续可以单独设计 prod compose / Dockerfile**：开发环境的选择不影响生产部署架构

## 4. 最终开发环境架构

```
┌──────────────────────────────────────────────────────────┐
│                   Docker Compose                          │
│  ┌─────────────┐    ┌─────────────┐                      │
│  │  MySQL :3306 │    │  Nginx :80   │                      │
│  │  (容器)      │    │  (容器)      │                      │
│  └─────────────┘    └──────┬──────┘                      │
│                            │                              │
└────────────────────────────┼──────────────────────────────┘
                             │ host.docker.internal
                   ┌─────────┴─────────┐
                   │                   │
              ┌────▼────┐        ┌─────▼───┐
              │Backend   │        │Frontend  │
              │:8080     │        │:5173     │
              │(本机进程) │        │(本机进程) │
              └─────────┘        └──────────┘
```

### 组件职责

| 组件 | 运行方式 | 端口 | 职责 |
|------|---------|------|------|
| MySQL | Docker Compose 容器 | 3306 | 数据库服务 |
| Nginx | Docker Compose 容器 | 80 | 统一反向代理入口 |
| Backend | 本机后台进程（go run / air） | 8080 | Go 后端 API 服务 |
| Frontend | 本机后台进程（npm run dev / Vite） | 5173 | 前端开发服务器 |

### 访问方式

| 入口 | 目标 | 说明 |
|------|------|------|
| `http://localhost/` | host.docker.internal:5173 | 前端页面（Nginx 代理） |
| `http://localhost/api/` | host.docker.internal:8080 | 后端 API（Nginx 代理） |
| `http://localhost/healthz` | host.docker.internal:8080/healthz | 健康检查（Nginx 代理） |
| `http://localhost:5173/` | 前端直连 | 开发调试用 |
| `http://localhost:8080/` | 后端直连 | 开发调试用 |

## 5. Docker Compose 职责

Docker Compose **仅管理**以下两个服务：

### 5.1 MySQL

```yaml
mysql:
  image: mysql:8.0
  # 现有配置保留
  ports:
    - "${MYSQL_PORT:-3306}:3306"
  volumes:
    - mysql_data:/var/lib/mysql
```

### 5.2 Nginx

```yaml
nginx:
  image: nginx:alpine
  ports:
    - "${NGINX_PORT:-80}:80"
  volumes:
    - ./nginx/conf.d:/etc/nginx/conf.d:ro
  extra_hosts:
    - "host.docker.internal:host-gateway"  # Linux 必需
  depends_on:
    - mysql  # 确保 Docker 网络就绪
```

### 5.3 不再包含的服务

| 服务 | 方案 A | 方案 B |
|------|--------|--------|
| backend 容器 | ✅ 有 | ❌ 无（本机进程） |
| frontend 容器 | ✅ 有 | ❌ 无（本机进程） |

### 5.4 host.docker.internal

- **macOS / Windows**：Docker Desktop 自动支持 `host.docker.internal`
- **Linux**：必须添加 `extra_hosts: host.docker.internal:host-gateway`
- 这确保 Nginx 容器可以通过 `host.docker.internal` 访问宿主机上运行的后端和前端服务

## 6. Backend 本机后台进程职责

### 6.1 运行方式

- 启动命令：`cd server && go run ./cmd/server` 或 `air`（热重载）
- 后台管理：Makefile 通过 `scripts/dev/backend.sh` 管理 PID
- PID 文件：`.run/server.pid`
- 日志文件：`.logs/server.log`
- 默认端口：8080

### 6.2 优势

- IDE 断点调试（dlv debug）
- 代码修改即时生效（air 热重载）
- 无容器挂载延迟
- 无需管理 Go module cache volume
- 日志直接输出到宿主机文件

### 6.3 环境变量

- 从 `.env` 读取配置
- `DB_HOST=127.0.0.1`（而非容器名 `mysql`）
- `SERVER_PORT=8080`
- `CORS_ALLOWED_ORIGINS` 待后续 R.3 实现

## 7. Frontend 本机后台进程职责

### 7.1 运行方式

- 启动命令：`cd web && npm run dev`
- 后台管理：Makefile 通过 `scripts/dev/web.sh` 管理 PID
- PID 文件：`.run/web.pid`
- 日志文件：`.logs/web.log`
- 默认端口：5173

### 7.2 优势

- 原生 HMR（Vite 文件系统监听，无容器 inotify 限制）
- 无需管理 node_modules volume
- npm install 直接在宿主机执行
- 浏览器 DevTools 调试方便

### 7.3 环境变量

- `VITE_API_BASE_URL=/api`（走 Nginx 代理）
- 或 `VITE_API_BASE_URL=http://localhost:8080/api`（开发直连）

## 8. Nginx 统一入口与代理规则

### 8.1 代理路由

```nginx
server {
    listen 80;
    server_name localhost;

    # 前端页面
    location / {
        proxy_pass http://host.docker.internal:5173;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Vite HMR WebSocket
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }

    # 后端 API
    location /api/ {
        proxy_pass http://host.docker.internal:8080/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # SSE / 长连接预留
        proxy_buffering off;
        proxy_read_timeout 300s;
    }

    # 健康检查
    location /healthz {
        proxy_pass http://host.docker.internal:8080/healthz;
        access_log off;
    }
}
```

### 8.2 关键规则

1. **`/api/` 不 strip `/api` 前缀**：如果后端接口是 `/api/resumes/optimize`，Nginx 转发后后端仍收到 `/api/resumes/optimize`
2. **Vite HMR WebSocket 代理**：开发环境必须支持，否则 HMR 无法工作
3. **SSE / 长连接预留**：`proxy_buffering off` + `proxy_read_timeout 300s`
4. **Linux 需要 `extra_hosts`**：`host.docker.internal:host-gateway`

### 8.3 开发直连模式

开发时也可不走 Nginx，直接访问：
- 前端：`http://localhost:5173`
- 后端：`http://localhost:8080`
- 此模式需要后端 CORS 支持

## 9. make 命令契约冻结

### 9.1 用户语义不变

| 命令 | 语义 | 说明 |
|------|------|------|
| `make up` | 启动完整混合式开发环境 | 内部：Docker(MySQL+Nginx) + 本机(Backend+Frontend) |
| `make down` | 关闭完整混合式开发环境，不清 volume | 内部：Docker down + 本机进程 stop |
| `make restart` | 软重启完整混合式开发环境，不清 volume | 内部：stop + up |
| `make restart-soft` | 同 restart | |
| `make reset` | 清开发 volume，必须 CONFIRM=yes | 内部：Docker volume rm + 重启 |
| `make reset-up` | 清开发 volume 后重启，必须 CONFIRM=yes | |
| `make status` | 查看完整开发环境状态 | 包含 Docker 容器 + 本机进程状态 |
| `make logs` | 查看完整开发环境日志 | 包含 MySQL + Nginx + Backend + Frontend |

### 9.2 make up 内部执行流

```
1. ensure-env           → 确保 .env 存在
2. doctor               → 检查 Docker / Go / Node / npm / .env / 端口
3. init                 → 创建目录、初始化
4. infra-up             → 启动 Docker Compose（MySQL + Nginx）
5. db-check             → 检查数据库就绪
6. backend-up           → 启动后端本机后台进程
7. web-up               → 启动前端本机后台进程
8. health               → 健康检查
9. 输出专业信息          → Access 段含 http://localhost/
```

### 9.3 make up 输出

```
==========================================
  ✅ Offer Catcher 开发环境已启动
==========================================

Access:
  App:        http://localhost/
  API:        http://localhost/api
  Health:     http://localhost/api/healthz
  MySQL:      localhost:3306

Useful commands:
  make status       查看服务状态
  make logs         查看日志
  make restart-soft 软重启（不清空数据）
  make reset-up     ⚠️ 清空数据并重启（CONFIRM=yes）
  make down         停止所有服务
```

### 9.4 冻结声明

**以上 make 命令用户语义在本项目生命周期内不再变更。** 后续只调整内部实现，不改变命令名和行为语义。

## 10. CORS 后续策略

### 10.1 推荐访问方式

```
http://localhost/ 页面通过 /api/ 调用后端
→ 属于 Nginx 同源代理，无需 CORS
```

### 10.2 开发直连方式

```
http://localhost:5173 → http://localhost:8080/api
→ 需要后端 CORS 支持
```

### 10.3 后续 R.3 或对应阶段重新实现 CORS 配置化

推荐环境变量：

```env
CORS_ALLOWED_ORIGINS=http://localhost,http://localhost:5173
CORS_ALLOWED_METHODS=GET,POST,PUT,PATCH,DELETE,OPTIONS
CORS_ALLOWED_HEADERS=Content-Type,Authorization,X-Requested-With
CORS_ALLOW_CREDENTIALS=true
```

### 10.4 不直接 cherry-pick 方案 A 的 B.4

方案 A 的 B.4 提交 `2e4cb6b` 包含有价值的 CORS 中间件代码（`server/internal/middleware/cors.go`），但也修改了 `docker-compose.yml` 和 `.env.example` 等与全容器模式耦合的文件。后续 R.3 实现时应重新编写，可参考 B.4 的设计思路，但不整体 cherry-pick。
